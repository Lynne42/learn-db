# 02.01 Docker 部署 MySQL 8.4

> **故事线与承上启下**：
> *在第一节课中，你仅仅敲入了一行 `docker compose up -d`，我们的电商数据库环境就如同变魔术一般启动了。但在真实的生产环境中，把数据库跑在容器里绝不能是黑盒操作。今天，我们将用架构师的解剖刀，切开这个 `docker-compose.yml`，看看里面藏着哪些关乎数据生死存亡的秘密。*

## ⚡ 速查摘要

- **容器本质**：容器是无状态的、即用即抛的隔离进程。
- **持久化 (Volumes)**：必须通过挂载宿主机目录（`./data/mysql:/var/lib/mysql`）来保证容器销毁后，数据库文件不丢失。
- **端口映射 (Ports)**：`3306:3306` 是将宿主机的端口打通到容器内部，使得外部客户端可以连接。
- **初始化脚本 (Initdb)**：放入 `/docker-entrypoint-initdb.d/` 的 `.sql` 文件，会在 MySQL 首次启动时自动执行，是实现“一键建表”的利器。

## 🎯 学习目标 + 验收标准

- **目标**：透彻理解 `docker-compose.yml` 中 `volumes`、`ports` 和 `environment` 的底层机制，搞懂如何防止容器化数据库“删库跑路”。
- **验收标准**：能够准确找出本机的物理数据存储目录，并理解其与容器内部路径的映射关系。

## 📖 概念全景

### 1. 为什么数据库也要用 Docker？
传统的 MySQL 部署方式需要在操作系统上手动执行 `apt-get install`、修改 `/etc/my.cnf`，步骤繁琐且极易因为操作系统版本不同而产生依赖冲突。
Docker 将 MySQL 的**运行程序、依赖库、系统环境**打包成了一个镜像 (Image)。只要安装了 Docker，任何电脑都能在 1 秒内拉起一个环境绝对一致的 MySQL。

### 2. docker-compose.yml 核心配置项深度解析

当我们查看项目根目录下的配置时：

```yaml
services:
  mysql-learn:
    image: mysql:8.4
    ports:
      - "3306:3306"
    environment:
      MYSQL_ROOT_PASSWORD: root123
    volumes:
      - ./data/mysql:/var/lib/mysql
```

#### A. 环境变量 (Environment)
这是 Docker 向容器内部传递配置信息的通道。MySQL 官方镜像规定，首次启动时**必须**传入 `MYSQL_ROOT_PASSWORD`，否则为了安全起见，容器会拒绝启动（或生成随机密码）。

#### B. 端口映射 (Ports)
MySQL 服务默认在容器内部监听 3306 端口。但容器有一道“次元壁”，外部机器无法直接访问。
`"3306:3306"` 的格式是 `宿主机端口 : 容器内部端口`。它在次元壁上开了一个洞，把你电脑本地的 3306 流量全部转发给容器内部的 3306。

#### C. 数据持久化 (Volumes) —— 数据库的生命线
这是容器化数据库**最最最重要**的概念。
**【底层机制】**：Docker 容器默认是**无状态**的。当容器被销毁 (`docker compose down`) 时，容器内部产生的所有文件（包括你辛辛苦苦存的一亿条订单记录）都会灰飞烟灭。
为了解决这个问题，我们需要使用 **Volume 映射**。

```mermaid
flowchart LR
    subgraph Host ["宿主机 (你的Mac/Linux)"]
        A["物理硬盘目录 ./data/mysql"]
    end
    
    subgraph Container ["MySQL 容器 (隔离环境)"]
        B["容器内存储路径 /var/lib/mysql"]
    end
    
    A <-->|"Volume 映射 (软链接思想)"| B
```
当你在容器内部的 MySQL 里写入一条数据时，MySQL 以为自己写在了 `/var/lib/mysql` 下，但实际上，Docker 驱动将数据直接写在了宿主机的 `./data/mysql` 文件夹中。**哪怕容器被炸飞，数据依然安稳地躺在你的物理硬盘里！**

### 3. 神奇的自动初始化机制 (Initdb)
MySQL 官方镜像内置了一个非常贴心的机制：
如果你在宿主机把带有建表语句的 `.sql` 脚本，或者 `.sh` 脚本，挂载到了容器的 `/docker-entrypoint-initdb.d/` 目录下：
**在且仅在**第一次初始化数据目录时，MySQL 启动前会依次自动执行这个目录里的所有脚本。这是我们做项目“一键启动即就绪”的最佳实践。

## 💻 命令行实操

虽然不需要写 SQL，但你应该掌握以下排查 Docker 环境的命令：

```bash
# 查看当前正在运行的容器
docker compose ps

# 查看 MySQL 容器的启动日志（排查报错神器）
docker logs mysql-learn

# 停止并摧毁容器（不用怕，由于配置了 volume，数据不会丢）
docker compose down

# 重新拉起容器（瞬间恢复原状）
docker compose up -d
```

## 🏗️ 项目实战 —— 订单系统场景

作为电商架构师，你需要确保我们的 `learn-mysql` 环境是绝对安全的。
昨晚，由于之前错误配置了 `mysql_native_password` 插件，导致容器启动崩溃。你果断使用了 `rm -rf ./data` 删除了宿主机上的数据目录，清除了损坏的底座，随后重启容器，MySQL 立即识别到空数据目录，并重新进行了崭新的初始化。
这一切的掌控力，都来源于你对 Volume 映射机制的深刻理解。

## ⚠️ 常见坑点

- **强行使用旧数据目录**：当你试图更改 MySQL 大版本（如 5.7 升 8.0）时，如果宿主机上的 `data` 目录仍保留着旧版的数据文件，启动时大概率会报错崩溃。此时需要手动处理升级流程，或者清空数据目录（测试环境下）。

# 延伸和深度学习

## /docker-entrypoint-initdb.d/ 的“一次性”陷阱
文档中提到了这个初始化目录，但顶尖开发者都知道它有一个非常凶残的失效判定标准：

1. 失效规则：这个目录下的脚本只有在 ./data/mysql 文件夹完全为空时才会执行。

2. 灾难场景：假设你第一次启动了容器，MySQL 执行了里面的 init.sql 创建了单表。第二天，你修改了 init.sql 想加一个字段，然后执行 docker compose restart。

3. 结果：完全无效！ MySQL 只要检测到 ./data/mysql 里已经有数据文件了，就会直接跳过这个目录。你改得再天花乱坠，它也绝对不会执行第二次。

4. 正确重置路径：如果是在测试环境，可以销毁数据卷重新拉起，它才会再次生效：
```sql
docker compose down -v  # -v 会连同挂载的临时匿名卷一起删掉
rm -rf ./data/mysql     # 必须手动清空宿主机目录
docker compose up -d    # 重新触发初始化脚本
```

但通常， 不应该销毁数据卷，尤其是在线上环境，或者持续运行很久的开发环境，都不应该销毁数据卷， 而是采用数据迁移的方式
