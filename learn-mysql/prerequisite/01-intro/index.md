# 模块 01: 数据库概论

> **模块定位**：本模块是整个【先导篇】的第一关。在正式敲击键盘写 SQL 之前，帮你重塑对“数据存储”的系统级认知。告别写一行算一行的散漫思维，建立起架构师级别的顶层视野。

## 🎯 知识边界与生态位

**本模块覆盖**：
- 关系型、内存型和文档型数据库（MySQL, Redis, MongoDB）的生态位分工与选型。
- ACID 事务模型的严格定义及其在金融交易中的兜底作用。
- MySQL 底层三层架构模型（连接层、服务层、引擎层）的宏观流转机制。
- 从现实世界到二维表格的降维映射（实体、属性、主键、外键）。
- 1:1、1:N、N:M 三种核心关系的白板建模与设计范式。

**本模块不覆盖**：
- MySQL 底层 B+ 树的细节结构（见【模块 16】）。
- 事务隔离级别的具体实现与 MVCC 机制（见【模块 22】）。
- 建表（CREATE TABLE）的具体语法（见【模块 06】）。

## 🗺️ 完整知识地图 (Knowledge Map)

> 从架构师的视角，重新梳理本章知识点的因果关系。

| 核心知识点 | 本质/定义 | 架构师视角 (Why & When) | 学习位置 |
|------------|-----------|-------------------------|----------|
| **关系型数据库选型** | 数据呈严谨的行列二维表格 | 当数据是不可丢失的资金、订单、核心资产时，必须选用 RDBMS (如 MySQL) | 01.01 |
| **内存 KV 数据库选型** | 极速内存读写，键值对结构 | 当应对高并发秒杀、排行榜、热点数据时，使用 Redis 作为前置缓冲 | 01.01 |
| **ACID - 原子性 (A)** | 多个操作同生共死 | 解决“钱扣了但订单没生成”的灾难问题，靠 Undo Log 实现 | 01.01 |
| **ACID - 持久性 (D)** | 落盘即永恒 | 解决“支付成功下一秒机房断电”的信任问题，靠 Redo Log 实现 | 01.01 |
| **MySQL 三层架构** | 连接层 -> 服务层 -> 引擎层 | 插件式引擎让 MySQL 独霸天下；优化器决定了 SQL 跑得快不快 | 01.01 |
| **主键 (PK) 设计** | 数据的唯一标识符 | 在 InnoDB 中，主键不仅是标识，更是数据物理排序的依据。强烈建议使用业务无关的无意义代理键 | 01.02 |
| **外键 (FK) 映射** | 表与表的羁绊纽带 | 互联网系统常抛弃数据库层面的物理外键，转而在应用层维护“逻辑外键”以提升并发性能 | 01.02 |
| **多对多 (N:M) 模型** | 一个订单有多个商品，商品也在多个订单中 | **绝对不能**直接在原表中加逗号分割字段，必须引入第三张**中间表**进行解耦 | 01.02 |

## ⚡ 速查与避坑指南 (Cheat Sheet)

> 快速查阅本章最常用的命令、最佳实践或最容易踩坑的设定。

| 场景/操作 | 最佳实践 / 核心命令 | ⚠️ 常见避坑提示 |
|-----------|--------------------|----------------|
| **探针测试** | `SELECT VERSION();`<br>`SELECT 1 + 1;` | 忘记在 SQL 客户端输入分号 `;` 会导致终端一直等待换行输入。 |
| **主键选型** | 使用自增数字或分布式雪花算法 ID | **绝对不要**使用手机号、邮箱等业务字段做主键。业务一旦变更（如换绑手机），会导致灾难性的全盘数据更新。 |
| **复杂关联存储** | 乖乖建立多张表，通过外键 ID 关联 | 严禁在关系型数据库中滥用逗号拼串（如 `products: "1,2,3"`），这会破坏第一范式，导致完全无法使用 SQL 统计。 |
