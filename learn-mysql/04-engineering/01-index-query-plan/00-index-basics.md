## 📖 概念全景

### 1. B+ 树索引的物理直觉

在 MySQL 的默认存储引擎 InnoDB 中，数据是**按索引顺序来组织的**。
- **聚簇索引（Clustered Index）**：
  就是表本身。InnoDB 会自动根据主键 `id` 建立一棵 B+ 树。这棵树的叶子节点直接存放了每一行的**所有完整数据**。
- **二级索引（Secondary Index，即辅助索引）**：
  为了加速通过其他非主键列（例如 `created_at`）进行的检索，我们为该列单独建立一棵二级 B+ 树。
  **极其重要**：这棵二级树的叶子节点里，**只存放了索引列自己的值以及对应的“主键 ID”**。它并不包含该行记录的其它字段（如邮箱、密码等）。

```
[二级索引 B+ 树 (以 created_at 排序)]
          [根/枝节点]
            /     \
    [2026-06-01]  [2026-06-30]  <-- 索引列值
    [主键 id=10]  [主键 id=25]  <-- 挂载的主键值
          \         /
           \       /  (需要回表时)
            v     v
[聚簇索引 B+ 树 (以主键 id 排序，即物理数据行)]
          [根/枝节点]
            /     \
       [id = 10]  [id = 25]
       [包含用户名、邮箱、密码等全行数据]
```

### 2. 什么是回表（Row Look-up）？

当我们执行：
```sql
SELECT username, email FROM users WHERE created_at = '2026-06-30 00:00:00';
```
如果我们在 `created_at` 上建了索引，MySQL 的检索流程如下：
1. 沿着 `created_at` 的二级树往下爬，找到 `'2026-06-30 00:00:00'` 这一项，提取出对应的主键 ID `25`。
2. 拿着主键 ID `25`，去聚簇索引树（也就是主物理表树）里从根节点重新检索，定位到 `id = 25` 的数据行，读取出 `username` 和 `email`。

这个**“从辅助索引拿到主键值，再通过主键值去聚簇索引里拿完整行数据”**的二次检索过程，就叫做 **“回表”**。
如果回表的数据行很多（比如几十万行），会在磁盘上造成大量的**随机 I/O** 查找，查询速度会急剧变慢。

### 3. EXPLAIN：SQL 优化的核武器

在任何 SQL 前面加上 `EXPLAIN`，MySQL 优化器就会吐出它打算如何执行这个查询：
- **`type`**：表示访问类型。最核心的性能指标。
  - `ALL`：全表扫描，性能最烂，必须消除。
  - `index`：全索引扫描。比 ALL 强，但仍需遍历整棵树。
  - `range`：索引范围扫描。通过索引检索出特定区间的行，性能较好。
  - `ref`：非唯一性索引扫描。匹配单个非唯一索引值，非常快。
  - `const`：常数级查询。通常是通过主键或唯一索引等值过滤，性能极佳。
- **`key`**：实际走到的索引名。如果是 `NULL`，代表没有走任何索引。
- **`rows`**：预估需要扫描的记录行数。越小性能越好。
- **`Extra`**：核心附加信息。
  - `Using filesort`：说明 MySQL 需要把数据放到内存或磁盘中重新排序，性能较差，应当尽量利用索引自身的顺序性规避。

## 💻 SQL 语法

### 1. 创建普通二级索引

```sql
CREATE INDEX idx_users_created_at ON users (created_at);
```

### 2. 使用 EXPLAIN 探测执行计划

```sql
EXPLAIN SELECT * FROM users WHERE created_at > '2026-06-01 00:00:00';
```

## 🛒 订单系统实战

**业务场景：**
我们要治理商户管理端因为通过“注册时间段”筛选新注册用户而导致全表扫描引发 CPU 飙升的问题。
我们需要为 `users` 表的 `created_at` 字段建立普通索引。

**实战 SQL：**

```sql
-- 1. 为 users 的创建时间追加普通辅助索引
CREATE INDEX idx_users_created_at ON users (created_at);

-- 2. 验证索引是否能够消除全表扫描
EXPLAIN SELECT * FROM users WHERE created_at = '2026-06-29 10:00:00';
```

在建立索引之前，`EXPLAIN` 结果中的 `type` 为 `ALL`（全表扫描），`key` 为 `NULL`；
建立索引之后，`EXPLAIN` 结果中的 `type` 会升级为 `ref` 或者是 `range`，而 `key` 会正确显示 `idx_users_created_at`，扫描行数大大缩减。

## ⚠️ 常见坑点

- 💣 **坑点 1：盲目给每个字段都建个索引**
  - **现象**：为了觉得好，把用户表的 `username`、`email`、`status`、`created_at` 全都单独建了索引。结果发现数据插入（`INSERT`）时，速度变慢了数倍。
  - **对策**：记住，**索引是有物理成本的**。每次写入、更新或删除一行记录，MySQL 都必须同步维护和改写所有相关的 B+ 二级索引树。索引过多会导致写入性能暴跌，并占用巨量磁盘空间。
- 💣 **坑点 2：忽略低区分度字段建索引的失效问题**
  - **现象**：为状态字段 `status`（只有 0:禁用，1:启用 两个值）建了二级索引，但是查询时发现 `EXPLAIN` 显示 `type` 仍然是 `ALL`，根本没走索引。
  - **对策**：优化器非常聪明。如果它评估需要扫描回表的数据行占总行数的比例很高（通常在 20%~30% 以上），它会认为“回表造成的随机 I/O 开销还不如我一次性全表顺序扫完”，从而直接**废弃索引走全表扫描**。因此，性别、状态等高重复、低区分度的字段绝不建议建单列索引。
