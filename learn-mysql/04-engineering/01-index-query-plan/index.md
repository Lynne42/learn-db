# 模块 04.01: 索引基础与查询计划

> **模块定位**：在实际业务中，当表的数据量达到数十万甚至数百万级时，数据库查询性能的优劣几乎完全取决于索引设计。没有索引的表就像是一本没有目录的书，每次寻找内容都必须从第一页翻到最后一页（全表扫描），对磁盘 I/O 和 CPU 都是毁灭性的灾难。然而，索引不是建得越多越好。本模块专注于 B+ 树索引物理直觉、联合索引的最左前缀匹配法则、覆盖索引免回表优化，帮你筑牢高性能查询的设计根基。

## 🎯 知识边界与生态位

**本模块覆盖**：
- B+ 树索引结构：主键索引（聚簇索引）与二级索引（辅助索引）在 InnoDB 底层的存储结构。
- 回表（Look-up）开销：通过二级索引查到主键，再通过主键定位行记录的物理过程。
- 覆盖索引（Covering Index）优化：如何直接在索引中满足 SELECT 列，实现免回表的磁盘 I/O 节省。
- 联合索引与最左前缀法则：多字段索引的数据组织与匹配边界。
- 读 EXPLAIN 计划：理解 key, type, rows, Extra（Using index / Using index condition）等核心字段含义。

**本模块不覆盖**：
- 哈希（Hash）索引与全文（Full-text）索引（MySQL 主要使用 B+Tree，Hash 仅由 Memory 引擎或 InnoDB 内部自适应哈希使用）。
- 锁与索引的结合关系：如 Next-Key Lock 锁在二级索引上的加锁路径（详见【模块 04.03】）。

## 🗺️ 完整知识地图 (Knowledge Map)

> 从架构师的视角，重新梳理本章知识点的因果关系。

| 核心知识点 | 本质/原理 | 架构师视角 (Why & When) | 学习位置 |
|------------|-----------|-------------------------|----------|
| **聚簇索引 (Clustered Index)** | 以主键物理排序的 B+ 树 | InnoDB 表必有聚簇索引，叶子节点直接存放行记录的所有数据。主键查询只需一次树查找，效率最高。 | 04.01.00 |
| **二级索引 (Secondary Index)** | 辅助 B+ 树，以定义列排序 | 叶子节点只存储该索引列值和对应的“主键值”。查询如果不满足覆盖索引，必须通过主键值回到聚簇索引（回表）找完整数据。 | 04.01.00 |
| **回表 (Row Look-up)** | 二次索引检索过程 | 通过二级索引找到主键 id 后，再根据主键 id 到聚簇索引检索数据行的过程。多一次树遍历，伴随大量随机 I/O，是慢 SQL 的元凶。 | 04.01.00 |
| **联合索引 (Composite Index)** | 按多列进行组合排序的二级索引 | 按字段声明顺序依次排序。仅当查询条件满足最左字段匹配时才能走索引过滤，能够有效减少二级索引数量。 | 04.01.01 |
| **覆盖索引 (Covering Index)** | 索引中包含所有需要查询的列 | 二级索引的叶子节点已有全部所需数据，MySQL 无需执行回表操作，直接在二级索引树中返回结果。EXPLAIN 显示 `Using index`。 | 04.01.01 |
| **执行计划 (EXPLAIN)** | 优化器选择的访问路径 | 用 `type`、`key`、`rows`、`Extra` 验证索引是否实际生效，并识别回表和额外排序。 | 04.01.02 |

## ⚡ 速查与避坑指南 (Cheat Sheet)

> 快速查阅本章最常用的命令、最佳实践或最容易踩坑的设定。

| 场景/操作 | 最佳实践 / 核心命令 | ⚠️ 常见避坑提示 |
|-----------|--------------------|----------------|
| **创建普通索引** | `CREATE INDEX idx_name ON table_name (column_name);` | 索引会占用磁盘空间，并且在每次 `INSERT/UPDATE/DELETE` 时都会重建部分 B+ 树分支。切忌对低区分度列（如 `status` 性别、状态等）单独建索引。 |
| **查看执行计划** | `EXPLAIN SELECT ...;` | 核心看 `type`（希望在 `ref/range` 以上，避免 `ALL`），`key`（实际走到的索引），`Extra`（是否 Using index 或 Using filesort 内存排序）。 |
| **防止隐式类型转换** | 确保 SQL 传入类型与列类型一致 | 若 `phone` 字段是 `VARCHAR`，写成 `WHERE phone = 13800000000`（数字类型）会导致 MySQL 对列隐式调用 CAST 函数，使**索引彻底失效**。 |
