# 模块 02.02: 字符集与排序规则

> **模块定位**：学习数据库时，很多人都曾被乱码问题困扰。在关系型数据库中，字符集 (Character Set) 与排序规则 (Collation) 决定了数据如何被编码存储、如何比较大小、以及如何进行排序。如果在此处缺乏清晰的底座认知，后续进行多语言存储、敏感大小写检索，甚至跨表 Join 关联时，都会踩入乱码或性能灾难的深坑。本模块带你解构 MySQL 的多级字符集架构，彻底理清大小写敏感性的控制。

## 🎯 知识边界与生态位

**本模块覆盖**：
- 字符集与排序规则的关系与定义。
- 历史遗留问题：MySQL `utf8` (utf8mb3) 的缺陷，与为什么必须在生产中强制使用 `utf8mb4`。
- 排序规则中的大小写与重音敏感性（以 `_ci`、`_cs`、`_bin` 结尾的 Collation 的物理含义与表现）。
- 字符集与排序规则的“库-表-列”三级继承机制。
- 连接字符集（Client-Connection-Results）的编码转换链路以及常见乱码的根源。

**本模块不覆盖**：
- 因为关联列的字符集或排序规则不一致导致无法利用索引的 Join 性能优化（详见【模块 04.02】）。
- 排序规则对分组（GROUP BY）与排序（ORDER BY）的具体执行计划层面的物理开销分析（详见【模块 04.02】）。

## 🗺️ 完整知识地图 (Knowledge Map)

> 从架构师的视角，重新梳理本章知识点的因果关系。

| 核心知识点 | 本质/语法 | 架构师视角 (Why & When) | 学习位置 |
|------------|-----------|-------------------------|----------|
| **utf8mb4 字符集** | `CHARACTER SET utf8mb4` | MySQL 原生的完整 UTF-8 实现。为了支持 4 字节的 Emoji 表情或复杂的东亚字符，防止存储特殊符号时发生 `Incorrect string value` 报错，生产环境必须强制使用 `utf8mb4`。 | 02.02.00 |
| **排序规则 (Collation)** | `COLLATE utf8mb4_...` | 决定了字符之间的大小比较、等于判断与排序。即使字符编码相同，在不同的排序规则下，判断相等与排序的结果也会截然不同。 | 02.02.00 |
| **大小写不敏感 (_ci)** | `utf8mb4_0900_ai_ci` | Case Insensitive。MySQL 8.0+ 默认的排序规则。在 WHERE 查询或 UNIQUE 键中，`admin` 与 `Admin` 会被判定为完全等价，在保存主键或唯一约束时极易造成意料之外的冲突。 | 02.02.00 |
| **二进制排序规则 (_bin)** | `utf8mb4_bin` | Binary Collation。按照字符对应的二进制编码字节直接进行比较。是区分大小写最安全、速度最快的首选方式。 | 02.02.00 |
| **多级继承机制** | 库 → 表 → 列 | 库级设定只影响未指定字符集的表，表级设定只影响未指定字符集的列。最终物理落地的仍然是列级的字符集。可以实现同一张表中不同列使用不同的 Collation。 | 02.02.00 |
| **连接字符集翻译链** | client → connection → results | 客户端的数据首先翻译为 client，然后转换为 connection 进行计算，最后转化为 results 传回。链路中任何一环配置不匹配都会导致传输乱码。 | 02.02.00 |

## ⚡ 速查与避坑指南 (Cheat Sheet)

> 快速查阅本章最常用的命令、最佳实践或最容易踩坑的设定。

| 场景/操作 | 最佳实践 / 核心命令 | ⚠️ 常见避坑提示 |
|-----------|--------------------|----------------|
| **全球化表情字符存储** | `CREATE TABLE ... DEFAULT CHARSET=utf8mb4` | 绝不能为了省事选择旧版的 `utf8`（本质是 `utf8mb3`），否则一旦用户在评论或用户名中输入 emoji 字符，MySQL 就会直接截断或报错。 |
| **密码/Token大小写敏感校验**| `VARCHAR(255) CHARACTER SET utf8mb4 COLLATE utf8mb4_bin` | 密码哈希、激活 Token、用户名等重要字段如果不设为 `_bin`，在默认的 `_ci` 下 `token_AbCd` 和 `token_abcd` 会被判定为同一个值，可能带来安全风险或唯一索引冲突。 |
| **客户端控制台乱码** | `SET NAMES utf8mb4;` | 遇到乱码时，通过此快捷命令能一次性重置客户端、连接以及结果的字符集，常用来排查终端与数据库编码不一致的问题。 |
| **三级继承陷阱** | 在定义列时如果显式指定过字符集，后期 `ALTER TABLE` 修改表字符集时，**已有列 of 字符集不会被自动级联修改**。必须单独对列进行 `MODIFY` 变更。 |
| **时区与字符集环境配置** | 在 `docker-compose.yml` 中使用 `--character-set-server=utf8mb4` | 在初始化数据库服务器时就直接指定全局默认字符编码，避免建库建表时遗忘导致使用旧的 `latin1`。 |
