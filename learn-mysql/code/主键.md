**主键**是每一行数据的**唯一标识符**。
- **唯一性**：表中任意两行的主键值绝不相同。
- **不可空**：主键绝对不能是空值（NULL）。
- **不可变性**：一旦分配，通常不应再修改。
*(底层提示：在 InnoDB 引擎中，主键不仅仅是标识，整张表的数据在磁盘上就是**按照主键顺序物理排列**的。这被称为“聚簇索引”。)*

## 1. 任何表都需要主键
在 MySQL 最常用的 InnoDB 存储引擎中，数据并不是随便扔在硬盘上的，而是强制和主键绑定在一起，形成一棵 B+ 树（这叫聚簇索引）。 如果你建表时不给它定主键：

- InnoDB 就会去表里找有没有 UNIQUE 且 NOT NULL 的列来顶替。

- 如果连这个也没有，InnoDB 会在底层偷偷为你生成一个不可见的、6 字节长的隐藏列（Row ID）来做主键。这不仅会带来额外的性能损耗，而且在高并发插入时极易产生全局锁冲突。 

结论：与其让底层悄悄搞小动作，不如我们把主动权握在手里，必须显式声明主键。

## 2. 为什么绝对不要用业务字段（如手机号、身份证、邮箱）做主键？（业务演进）
用业务字段做主键叫作**自然键** (Natural Key)。这在理论上看似完美（毕竟身份证号绝不重复），但在现实业务中是灾难：

1. 灾难场景 1（牵一发而动全身）：假设你用“手机号”做主键。某天用户换号了，要求修改。因为主键一旦变动，所有关联该主键的外键（订单表、购物车表、积分流水表）统统都要跟着级联更新！ 这种海量数据同时更新会瞬间锁死整个数据库。

2. 灾难场景 2（B+树页分裂）：如果你用无序的字符串（如普通的 UUID 或邮箱）做主键，每次插入新数据时，InnoDB 需要在树的中间强行塞入数据，导致数据页频繁分裂、移动碎片，写入性能会大幅雪崩。

## 3. 为什么推荐使用“无意义的自增 ID 或雪花算法”作为主键
用完全无关业务的数字做主键叫作**代理键** (Surrogate Key)。

1. 与业务解耦：这串数字没有任何现实含义，用户换手机、改名字，随便改！我们的主键和底层外键关联岿然不动。
2. 写入极快：无论是 MySQL 自带的 AUTO_INCREMENT（自增） 还是分布式系统爱用的 雪花算法 (Snowflake ID)，它们都有一个共同特征——趋势递增。新数据永远是往 B+ 树的末尾追加，几乎不产生碎片，写入性能达到巅峰！
3. 节约空间：主键越短，其他索引就越小（因为其他索引底层存的都是主键的值）。

## 4. 何时使用自增ID/雪花算法作为主键

### 核心判断
维度 | 自增 ID (AUTO_INCREMENT) | 雪花算法 (Snowflake ID) | 
| -- | -- | -- |
核心本质 | 集中式状态控制（由单台数据库死守计数器） | 分布式状态生成（由算法在各个节点本地计算） | 
适用架构 | 单机数据库、读写分离、轻量级项目 | 分布式微服务、分库分表、高并发架构 | 
物理写入 | 绝对递增，B+树页吞吐性能达到理论极限 | 趋势递增，偶有小范围波动，页吞吐性能极高 | 
安全性 | 零安全性。信息极易泄漏（如订单量、用户量） | 高安全性。ID 离散，无法通过单号推测业务量 | 
存储空间 | 占用空间小（通常 INT 4字节 或 BIGINT 8字节） | 固定占用 BIGINT（8字节/64位） | 

### 什么时候【绝对不能】使用自增 ID？
遇到以下三个场景，哪怕你的系统现在用户量只有 100 个，也必须一票否决自增 ID：
1. 分布式或需要分库分表的系统原因：

当数据量大到一张表放不下，需要拆分到 db_1 和 db_2 时，如果两边都各自自增，会出现严重的 ID 冲突（两边都有 id=100 的数据），导致数据无法合并和关联。

2. 对外暴露、具有商业敏感性的业务对象

- 例如：订单号（order_id）、用户 ID（user_id）、商家 ID（merchant_id）。
- 原因：自增意味着连续。竞争对手可以通过今天注册一个号（uid=1000），明天注册一个号（uid=1015），直接算出你一天的净注册用户是 15 人。

3. 前端直接处理 64 位自增整型（特殊避坑）

- 原因：如果自增到了 BIGINT 且超过了 $2^{53} - 1$（如 9007199254740991），JavaScript 在处理该长整型时会发生精度丢失（变为末尾带 0 的近似值），导致前后端数据对不上。
- (注：雪花算法同样有此问题，但雪花算法在落地时，业界标准是强制在后端将其转为 String 类型再跨网络传输)。


### 什么时候【绝对不要】使用雪花算法？
雪花算法不是银弹，在以下场景使用属于“过度设计”或“引入隐患”：

1. 完全不需要分库分表的辅助表/字典表

例如：权限表（permissions）、配置表（configs）、商品分类表（categories）。

原因：这些表数据量极小（通常几百到几万条），永远不需要分库分表，也不存在并发写入瓶颈。用雪花算法纯属增加系统复杂度和存储开销。

2. 极度依赖物理连续存储、高频范围查询的流水表

原因：雪花算法虽然整体趋势递增，但在同一毫秒内，不同机器生成的 ID 大小是随机的。如果你有极其严苛的 ORDER BY id ASC 且要求物理完全连续的场景，自增 ID 对 B+ 树的聚簇索引更友好。

3. 无法解决“时钟回拨”风险的基建环境

原因：雪花算法严重依赖系统本地时间。如果你的服务器集群时钟同步触发了时钟回拨（机器时间往回跳了几秒），雪花算法会瞬间发生 ID 重复碰撞，导致线上大面积写入报错。如果团队没有能力处理时钟回拨的容错（如预留等待、号段降级），慎用。
