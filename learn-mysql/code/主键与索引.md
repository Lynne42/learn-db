# 主键与索引的关系
主键是一种“业务约束”，而索引是实现这种约束的“物理数据结构”

概念 | 属于什么层面 | 数量限制 | 叶子节点存什么 | 核心目的 | 
| -- | -- | -- | -- | -- |
主键 (PK) | 业务逻辑层 + 物理存储层 | 一张表必须有且仅有 1 个 | 完整的整行数据 | 保证数据的唯一性与物理存储的有序性 | 
索引 (Index) | 性能优化层 (纯技术手段) | 一张表可以有 多个 (建议不超 5 个) | 主键的值 (如果是二级索引) | 为了提高查询速度，消除全表扫描 | 

## 核心大白话：图书与目录的类比
没有索引的表：就像一本 1000 页的字典，没有目录，所有字随机排列。你想找一个字，必须从第 1 页一页一页翻到第 1000 页（这在数据库里叫 全表扫描 Full Table Scan，高并发下必死）。

- **索引（Index）**：就是这本字典的目录。它是一个独立抽离出来的结构，帮你快速定位到数据在第几页。

- **主键（Primary Key）**：是这个目录里最特殊的一条硬性规定——“第一章的编号必须叫 1，且整本书只能有一个第 1 章，内容绝对不准重复”。

## 深度剖析：InnoDB 下的“生死同盟”
在 MySQL 的 InnoDB 引擎中，主键和索引的关系比你想的还要紧密，它们在物理盘片上是长在一起的。

### 1. 聚簇索引（Clustered Index）—— 主键的肉身
当你在一张表上声明了 PRIMARY KEY，MySQL 会在底层自动为你创建一棵 B+ 树。这棵树的叶子节点，存放的是整行数据的完整内容。

主键不是一个简单的标记，它就是这棵树的“键值（Key）”。

因为整张表的数据就是按照主键的顺序在磁盘上排布的，所以一张表有且只能有一个主键（因为数据在磁盘上没办法同时按两种物理顺序排列）。

这个由主键自动生成的 B+ 树，就叫做聚簇索引（或主键索引）。

### 2. 二级索引（Secondary Index）—— 影子军队
你在业务中，不可能只用主键查数据。比如你经常要根据 cellphone（手机号）查找用户，或者根据 order_sn（订单号）查询订单。
这时候，如果你不给手机号加索引，每一次查询都是灾难性的全表扫描。

于是你通过 SQL 给手机号创建了一个索引：
```sql
CREATE INDEX idx_cellphone ON users(cellphone);
```

这时候，MySQL 会在底层额外再建一棵 B+ 树。这棵树就是二级索引（也叫辅助索引）。

这棵树的 Key 是手机号。

【致命核心】：这棵树的叶子节点，不存放用户的完整数据（如名字、密码、年龄），它只存放主键的值！

### 3. 联动查询：什么是“回表”？
当我们执行这行 SQL 时，底层发生了什么：
```sql
SELECT id, name, cellphone FROM users WHERE cellphone = '13800000000';
```

- MySQL 先跑到 idx_cellphone 这棵二级索引树上，顺着手机号一路往下找，找到了 13800000000。

- 在叶子节点上，MySQL 拿到了这个手机号对应的主键 ID，假设是 id = 9527。

- 因为你的 SQL 里还要查询 name（姓名），而二级索引树上没有 name 的数据。

- MySQL 必须拿着 id = 9527，转过头去跑第二趟，到主键聚簇索引树上重新查一遍，从而拿到 name = 张三。

这个“先查二级索引拿到主键，再用主键去查聚簇索引”的过程，在数据库底层叫做 回表（Lookup）。

# 索引设计
### 索引设计的第一金律：三星索引法则（Three-Star System）
由数据库专家 O'Neil 提出的“三星索引”是顶级架构师设计索引的终极追求。对于一条特定的查询 SQL，如果一个索引能同时做到以下三点，它就是“满分索引”：

1. ⭐ 一星：最小化扫描范围
将所有等值条件（如 WHERE status = 1 AND zone = 'A'）的列放在索引最前面。这样可以把查询范围瞬间缩小到磁盘的一小块地方。

2. ⭐⭐ 二星：消除排序（Avoid Sort）
如果 SQL 里有 ORDER BY create_time，把 create_time 顺着加到索引里。因为索引本身就是有序的，这样 MySQL 就不需要在内存中进行痛苦的物理排序（FileSort），直接顺着索引树拿结果。

3. ⭐⭐⭐ 三星：消除回表（Covering Index / 覆盖索引）
如果你的索引树里，已经包含了你 SELECT 后面需要的全部列，MySQL 就再也不需要拿着主键去查聚簇索引了（回表次数直接降为 0）。这种索引叫作覆盖索引，速度达到物理极限。

## 索引设计的四大铁律（落地规矩）
### 铁律一：最左前缀法则（The Leftmost Prefix Rule）
如果你创建了一个联合索引（包含多个列的索引），比如 idx_user_course(user_id, course_id, status)。

它是按从左到右的顺序在树里排序的。

正确姿势：你的 WHERE 条件里必须包含最左边的 user_id，索引才能生效。

崩溃翻车：如果你直接 WHERE course_id = 5，跳过了最左边的 user_id，这个联合索引将彻底失效，直接降级为全表扫描。


### 铁律二：高辨识度（高离散度）列才配建索引
公式：COUNT(DISTINCT 列名) / COUNT(*) 结果越接近 1，越适合建索引。

崩溃场景：永远不要在“性别”（男/女）或“状态”（有效/无效）这种离散度极低的列上单独建索引。因为无论怎么筛选，依然要剩下 50% 的数据，MySQL 发现查了索引还要回表 50% 次，由于随机 I/O 太高，底层引擎会直接放弃索引，改成全表扫描。这属于白白浪费磁盘空间的自嗨式索引。

### 铁律三：索引列上绝不能搞“骚操作”（保持列干净）
不要在 WHERE 条件的索引列上做任何函数、计算、或类型转换。

WHERE YEAR(create_time) = 2026 ❌（导致 create_time 索引失效）

WHERE age + 1 > 18 ❌（导致 age 索引失效）

底层原理：B+ 树里存的是列的原始值。你加了函数或计算，MySQL 无法在树的节点上进行计算后再比对，只能硬生生演变成全表扫描。


### 铁律四：严控单表索引数量（认知负债的实体化）
硬性指标：单张表的索引数量尽量控制在 5 个以内。

原因：每一条索引都是一棵独立的 B+ 树。每次你执行 INSERT、UPDATE 或 DELETE 时，MySQL 除了要改数据，还要同步去修补和调整这 5 棵索引树的结构（引发页分裂、树平衡）。高并发下，这会导致写入性能雪崩。
