# 03.02.03. 主键、唯一键与业务唯一性

> **故事线与承上启下**：
> 在上一模块中，我们安全地演进了 `users` 表结构，增加了时间追踪，并引入了用于检索优化的虚拟列。但很快你会发现一个大漏洞：如果我们用相同的用户名或邮箱重复注册多条用户记录，数据库居然允许它们静默写入！这是因为我们目前仅用 `id` 做了主键，而没有设置任何“业务唯一性”拦截。本节我们将探讨主键与唯一键（`UNIQUE KEY`）的深层设计抉择，并为系统构筑这层核心安全拦截网。

## ⚡ 速查摘要

- **主键 (Primary Key)**：物理数据的存储依托（每张表有且仅有一个，绝不能为 NULL）。
- **唯一键 (Unique Key)**：拦截重复数据的逻辑栅栏（一张表可以有多个，**允许存入多个 NULL**）。
- **增加唯一键语法**：
  ```sql
  ALTER TABLE <表名> ADD CONSTRAINT <约束名> UNIQUE (<列名>);
  ```

## 📖 概念全景

### 1. 技术主键 vs 业务/自然主键

在设计表结构时，通常有两派路线：
- **技术主键（代理主键）**：选用与业务毫无瓜葛的自增 ID（如 `id INT AUTO_INCREMENT`）或分布式 UUID 做主键。
  > 💡 **架构师视角**：
  > 在 InnoDB 底层，数据是紧凑地排列在主键的 B+ 树叶子页上的。如果使用自增主键，新记录永远是顺序追加写入磁盘的，这极大地减少了数据页分裂（Page Split）和随机磁盘 I/O。因此，**技术主键是生产环境当之无愧的首选**。
  
- **业务主键（自然主键）**：直接选用具有现实含义且天然唯一的列（如“邮箱地址”、“手机号”或“身份证号”）做主键。
  > ⚠️ **缺陷警告**：
  > 1. 业务主键通常较宽（如 `VARCHAR(100)`），主键太宽会导致每一个二级索引（它底层都必须挂载主键值）的体积成倍增加，浪费内存。
  > 2. 现实中的业务唯一值也是可能改变的（比如用户想换邮箱、学校想重编学号）。主键一旦发生修改，将导致所有子表的关联外键跟着全局连带修改，开销极其庞大。

### 2. 主键与唯一键的差异比对

既然选择技术主键 id 充当了主键，那么我们该如何防止用户注册相同的“邮箱”呢？答案就是使用 **唯一键（UNIQUE KEY）**。

| 维度 | 主键 (PRIMARY KEY) | 唯一键 (UNIQUE KEY) |
|---|---|---|
| **数量限制** | 一张表**有且仅能有一个**。 | 一张表可以设置**多个**。 |
| **可空性 (NULL)**| **绝对不允许为 NULL** (Implicitly NOT NULL)。 | **允许为 NULL**（可以存入多行 NULL）。 |
| **物理存储** | 作为主干索引（聚簇索引），直接关联数据行。 | 作为辅助索引（二级索引），底层叶子节点挂载主键值。 |
| **应用目的** | 保证物理记录的独一无二。 | 拦截业务重复，防止逻辑冲突。 |

### 3. 为什么唯一键允许“重复的 NULL”？

在 MySQL 的唯一键（`UNIQUE KEY`）列上，你可以畅通无阻地插入多行含有 `NULL` 的数据。
这是因为在 SQL 标准及 MySQL 的实现中，`NULL` 代表“未知”（Unknown）。任何一个未知值，都不等于另一个未知值（在 SQL 里，`NULL = NULL` 的判定结果是 `UNKNOWN`，而不是 `TRUE`）。
因此，两个 `NULL` 并不会被判定为“重复数据”，所以不会触发唯一键冲突。

## 💻 SQL 语法

### 1. 在建表时声明唯一约束

```sql
CREATE TABLE test_uq (
    id INT PRIMARY KEY,
    email VARCHAR(100) NOT NULL,
    -- 表级声明唯一约束
    UNIQUE KEY uk_email (email)
);
```

### 2. 对已有表追加唯一约束

```sql
-- 推荐：显式命名约束，方便后期排错和删除
ALTER TABLE users 
  ADD CONSTRAINT uk_users_username UNIQUE (username);

-- 同时也为 email 追加唯一键
ALTER TABLE users 
  ADD CONSTRAINT uk_users_email UNIQUE (email);
```

## 🛒 订单系统实战

**业务场景：**
前几节我们创建的 `users` 基础表中，`username` 和 `email` 仅仅加上了 `NOT NULL`，这导致商户端接口在高并发下可以无限制注册相同账号。
我们需要立即为这两个列追加 `UNIQUE KEY` 拦截，杜绝重复数据。

**实战 SQL：**

```sql
-- 追加用户名唯一键
ALTER TABLE users 
  ADD CONSTRAINT uk_users_username UNIQUE (username);

-- 追加邮箱唯一键
ALTER TABLE users 
  ADD CONSTRAINT uk_users_email UNIQUE (email);
```

## ⚠️ 常见坑点

- 💣 **坑点 1：把 UUID 或邮箱直接用作 InnoDB 主键**
  - **现象**：高并发插入数据时，随着数据量变大，写入越来越卡，CPU 飙升。
  - **对策**：UUID 是随机无序的，插入会导致 InnoDB 的 B+ 树产生剧烈的页合并与页分裂（磁盘页不断重新挪位置），引起大量随机写。应该使用自增 ID 或有序雪花 ID 做主键，而把 UUID 设为唯一键。
- 💣 **坑点 2：在高并发环境下用 SELECT -> 判断 -> INSERT**
  - **现象**：在代码里写：`SELECT COUNT(*) FROM users WHERE username = 'admin'`。如果返回 0，就执行 `INSERT`。但在高并发下，两个线程同时跑 SELECT 都返回 0，接着同时插入，成功写入了两个重名用户，绕过了校验。
  - **对策**：代码校验不具备原子性。必须在数据库层设置 `UNIQUE KEY`，以此作为兜底的安全大闸。

# 扩展与延伸

## 为什么要给唯一约束（`UNIQUE`）起一个清晰的名字（如 `uk_users_email`）

在 MySQL（尤其是 InnoDB 引擎）中，创建唯一约束（`UNIQUE`）时，如果你不显式指定名字，系统会自动用**字段名**作为索引名。

从架构师和高并发运维的视角来看，显式且规范地命名唯一约束（如 `uk_users_email`），是为了在**线上崩溃、代码异常和数据库迁移**时，提供关键的“救命线”。

核心原因有以下三点：

---

### 1. 线上日志排查：快速定位报错源头

当高并发业务下发生唯一键冲突时（例如两个用户同时用同一个邮箱注册），数据库会抛出 `1062` 错误（Duplicate entry）。

* **不命名的默认表现**：
> `Error 1062: Duplicate entry 'test@mail.com' for key 'users.email'`


这看起来似乎能认出来是 `email` 字段冲突。但如果是联合唯一索引（比如 `tenant_id` + `user_code`），系统默认起的名字可能是 `tenant_id`，这会极其误导排查人员，你根本分不清到底是单列冲突还是组合列冲突。
* **显式命名 `uk_users_email` 的表现**：
> `Error 1062: Duplicate entry 'test@mail.com' for key 'users.uk_users_email'`


在微服务架构中，这个错误会原封不动地抛给后端日志系统（如 ELK）。开发人员甚至不需要去查表结构，单看日志里的 `uk_users_email` 就能**在 1 秒内断定：这是用户表（users）的邮箱（email）唯一性约束（uk）触发了冲突**。

---

### 2. 精准 DDL 变更：防止误删索引

随着业务演进，唯一约束可能需要调整（例如：从原先的“邮箱唯一”，变成“租户 ID + 邮箱联合唯一”）。此时你需要先删掉旧的唯一约束，再建新的。

如果你没有命名旧的唯一约束，你必须先去线上执行 `SHOW CREATE TABLE` 捉迷藏一样去人眼确认系统给它生成的随机名或默认名。
更危险的是，在自动化迁移脚本（如 Flyway、Liquibase）中，如果无法确定准确的约束名，你就无法写出确定性的 `DROP INDEX` 语句：

```sql
-- 如果起好了名字，变更脚本极其清晰、安全
ALTER TABLE users DROP INDEX uk_users_email;

```

如果名字是随机的，脚本在不同环境（测试环境 vs 生产环境）执行时，系统生成的默认名可能不一致，直接导致**线上生产环境的发布脚本执行报错、中断甚至删错索引**。

---

### 3. 底层原理：唯一约束的本质就是索引

在 InnoDB 中，**唯一约束的底层完全依赖唯一索引（Unique Index）来实现**。
当你定义 `UNIQUE` 时，数据库会在后台构建一棵 B+Tree。规范的命名（以 `uk_` 开头，`uk` 即 Unique Key）可以让 DBA 或开发人员在查看执行计划（`EXPLAIN`）或排查慢查询时，一眼看清优化器到底选用了哪个索引。

---

### 规范命名模板

> **`uk_表名_字段名1[_字段名2]`**

* **单列唯一**：`uk_users_mobile`（用户表手机号唯一）
* **多列联合唯一**：`uk_orders_tenant_no`（订单表在同一租户下订单号唯一）

**立即开始的核心**：严禁写 `CREATE TABLE` 时直接在字段后面缀一个孤零零的 `UNIQUE`。必须在建表语句的底部，或者通过单独的 DDL 显式赋予其姓名：

```sql
-- 推荐的标准写法
CREATE TABLE users (
    id BIGINT NOT NULL AUTO_INCREMENT PRIMARY KEY,
    email VARCHAR(100) NOT NULL,
    -- 显式指定约束名与索引名
    CONSTRAINT uk_users_email UNIQUE (email)
);

```
