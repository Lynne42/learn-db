# 应用层逻辑外键与软删除

## 一、逻辑外键：用代码替代数据库约束

### 1.1 什么是逻辑外键

**逻辑外键（Logical Foreign Key）**：表结构中保留外键列（如 `user_id`），但**不创建 `FOREIGN KEY` 约束**，引用完整性由应用代码保证。

```sql
-- 物理外键（禁止）
CREATE TABLE orders (
    id      BIGINT PRIMARY KEY,
    user_id BIGINT,
    FOREIGN KEY (user_id) REFERENCES users(id)  -- ← 不要这行
);

-- 逻辑外键（推荐）
CREATE TABLE orders (
    id      BIGINT PRIMARY KEY,
    user_id BIGINT NOT NULL,
    INDEX idx_user_id (user_id)  -- ← 保留索引，查询需要
    -- 没有 FOREIGN KEY 约束，引用关系在应用层维护
);
```

**关键区别**：

| 维度 | 物理外键 | 逻辑外键 |
|------|---------|---------|
| 约束位置 | 数据库引擎 | 应用代码 |
| 锁行为 | 子表 INSERT 给父表加 S 锁 | 无额外锁 |
| 一致性保证 | 强一致（引擎级） | 最终一致（代码 + 兜底任务） |
| 绕过可能性 | 几乎不可能（除非 `SET FOREIGN_KEY_CHECKS=0`） | 直连数据库操作可绕过 |
| 性能影响 | 有（锁扩散 + 额外索引查找） | 无 |
| 分库分表兼容 | 不兼容 | 兼容 |

### 1.2 逻辑外键的表设计规范

```sql
-- 完整的逻辑外键表设计示例

CREATE TABLE users (
    id         BIGINT AUTO_INCREMENT PRIMARY KEY,
    username   VARCHAR(50)  NOT NULL,
    email      VARCHAR(100) NOT NULL,
    is_deleted TINYINT(1)   NOT NULL DEFAULT 0,   -- 软删除标记
    created_at DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
) ENGINE=InnoDB;

CREATE TABLE orders (
    id         BIGINT AUTO_INCREMENT PRIMARY KEY,
    user_id    BIGINT       NOT NULL,              -- 逻辑外键，引用 users.id
    amount     DECIMAL(10,2) NOT NULL,
    status     TINYINT      NOT NULL DEFAULT 0,
    is_deleted TINYINT(1)   NOT NULL DEFAULT 0,
    created_at DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,

    INDEX idx_user_id (user_id)                    -- 必须建索引，JOIN 查询要用
) ENGINE=InnoDB;

CREATE TABLE order_items (
    id         BIGINT AUTO_INCREMENT PRIMARY KEY,
    order_id   BIGINT       NOT NULL,              -- 逻辑外键，引用 orders.id
    product_id BIGINT       NOT NULL,              -- 逻辑外键，引用 products.id
    quantity   INT          NOT NULL,
    price      DECIMAL(10,2) NOT NULL,
    is_deleted TINYINT(1)   NOT NULL DEFAULT 0,
    created_at DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,

    INDEX idx_order_id (order_id),
    INDEX idx_product_id (product_id)
) ENGINE=InnoDB;
```

**注意**：`user_id`、`order_id`、`product_id` 这些列仍然需要建索引。索引是为了**查询性能**，和外键约束是两回事。

## 二、Service 层维护引用一致性

### 2.1 核心模式：先查父记录 → 再写子记录

物理外键的本质是"INSERT 子记录时检查父记录是否存在"。应用层做同样的事：

```
物理外键流程:
  INSERT orders → InnoDB 内部检查 users.id 是否存在 → 存在则写入

应用层流程:
  Service 代码查 users.id 是否存在 → 存在则 INSERT orders → 不存在则报错
```

### 2.2 Java/Spring 代码实现

以创建订单为例，完整的 Service 层代码：

```java
/**
 * 订单服务：负责订单创建和管理。
 * 通过应用层逻辑外键维护与 users 表的引用关系。
 */
@Service
public class OrderService {

    private final UserRepository userRepository;
    private final OrderRepository orderRepository;

    public OrderService(UserRepository userRepository, OrderRepository orderRepository) {
        this.userRepository = userRepository;
        this.orderRepository = orderRepository;
    }

    /**
     * 创建订单。
     * 先验证用户存在性，再写入订单记录，两步在同一事务内完成。
     *
     * @param userId 用户 ID，逻辑外键
     * @param amount 订单金额
     * @return 创建成功的订单
     * @throws BusinessException 用户不存在时抛出
     */
    @Transactional(rollbackFor = Exception.class)
    public Order createOrder(Long userId, BigDecimal amount) {
        // 步骤 1: 验证父记录存在（等价于外键检查）
        User user = userRepository.findById(userId)
                .orElseThrow(() -> new BusinessException("用户不存在: " + userId));

        // 步骤 1.5: 验证父记录未被软删除
        if (user.getIsDeleted() == 1) {
            throw new BusinessException("用户已注销: " + userId);
        }

        // 步骤 2: 创建子记录
        Order order = new Order();
        order.setUserId(userId);
        order.setAmount(amount);
        order.setStatus(OrderStatus.CREATED);

        return orderRepository.save(order);
    }
}
```

### 2.3 时序图：应用层外键检查 vs 物理外键

```
应用层逻辑外键:

  Client          OrderService         UserRepo         OrderRepo         MySQL
    │                 │                   │                 │                │
    │  createOrder()  │                   │                 │                │
    ├────────────────→│                   │                 │                │
    │                 │   findById(100)   │                 │                │
    │                 ├──────────────────→│                 │                │
    │                 │                   │  SELECT * FROM  │                │
    │                 │                   │  users WHERE    │                │
    │                 │                   │  id=100         │                │
    │                 │                   ├────────────────────────────────→ │
    │                 │                   │                 │   返回 user    │
    │                 │                   │←────────────────────────────────┤
    │                 │   User 对象       │                 │                │
    │                 │←──────────────────┤                 │                │
    │                 │                   │                 │                │
    │                 │  检查: user != null                 │                │
    │                 │  检查: isDeleted != 1               │                │
    │                 │                   │                 │                │
    │                 │   save(order)     │                 │                │
    │                 ├──────────────────────────────────→ │                │
    │                 │                   │                 │  INSERT INTO   │
    │                 │                   │                 │  orders ...    │
    │                 │                   │                 ├───────────────→│
    │                 │                   │                 │   无 S 锁！     │
    │                 │                   │                 │←──────────────┤
    │                 │   order 对象      │                 │                │
    │                 │←──────────────────────────────────┤                │
    │   返回 order    │                   │                 │                │
    │←────────────────┤                   │                 │                │
```

**关键差异**：应用层的 `SELECT` 查父记录是一个**普通的快照读**（在 MVCC 下），不加任何锁。后续的 `INSERT` 也只锁子表行。**父表完全不受影响**。

### 2.4 并发问题：TOCTOU（Time of Check to Time of Use）

应用层检查存在一个理论上的竞态条件：

```
事务 A (创建订单):                    事务 B (删除用户):
  T1: SELECT * FROM users             
      WHERE id=100  → 存在 ✓
                                       T2: DELETE FROM users WHERE id=100
                                           → 成功 ✓
  T3: INSERT INTO orders 
      (user_id=100)  → 成功 ✓
      → 但此时 users.id=100 已经不存在了！
      → 产生了孤儿记录 ❌
```

这就是 **TOCTOU 问题**（Time of Check to Time of Use）。应对方案：

| 方案 | 实现方式 | 适用场景 |
|------|---------|---------|
| **容忍 + 兜底** | 允许短暂不一致，定时任务清理孤儿记录 | 大多数业务（推荐） |
| **SELECT ... FOR UPDATE** | 查父记录时加 X 锁，阻止并发删除 | 强一致性场景（少用） |
| **软删除** | 不物理删除父记录，只标记 `is_deleted=1` | 最常用（详见第三节） |

方案 2 的代码（仅在必须强一致时使用）：

```java
/**
 * 强一致性版本的订单创建。
 * 使用 SELECT FOR UPDATE 锁定父记录，防止并发删除导致孤儿记录。
 * 注意：这会引入父表行锁，仅在业务要求强一致性时使用。
 *
 * @param userId 用户 ID
 * @param amount 订单金额
 * @return 创建成功的订单
 */
@Transactional(rollbackFor = Exception.class)
public Order createOrderStrict(Long userId, BigDecimal amount) {
    // SELECT ... FOR UPDATE 锁定父记录，阻止并发删除/修改
    User user = userRepository.findByIdForUpdate(userId)
            .orElseThrow(() -> new BusinessException("用户不存在: " + userId));

    Order order = new Order();
    order.setUserId(userId);
    order.setAmount(amount);
    return orderRepository.save(order);
}
```

```java
/**
 * UserRepository: 提供用户数据访问。
 */
public interface UserRepository extends JpaRepository<User, Long> {

    /**
     * 通过 SELECT ... FOR UPDATE 悲观锁查询用户。
     * 持有行级 X 锁直到事务提交。
     *
     * @param id 用户 ID
     * @return 用户实体（如存在）
     */
    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("SELECT u FROM User u WHERE u.id = :id")
    Optional<User> findByIdForUpdate(@Param("id") Long id);
}
```

**注意**：`SELECT ... FOR UPDATE` 本质上就是自己手动加了物理外键做的事（父表行锁），只是更可控——你可以选择哪些场景需要、哪些不需要。

### 2.5 删除父记录时的引用检查

物理外键会阻止删除被引用的父记录。应用层需要手动实现：

```java
/**
 * 用户服务：删除用户前检查是否有未完成的关联数据。
 */
@Service
public class UserService {

    private final UserRepository userRepository;
    private final OrderRepository orderRepository;

    public UserService(UserRepository userRepository, OrderRepository orderRepository) {
        this.userRepository = userRepository;
        this.orderRepository = orderRepository;
    }

    /**
     * 删除用户（软删除）。
     * 先检查是否有未完成的订单引用该用户，如有则拒绝删除。
     *
     * @param userId 用户 ID
     * @throws BusinessException 存在未完成订单时抛出
     */
    @Transactional(rollbackFor = Exception.class)
    public void deleteUser(Long userId) {
        User user = userRepository.findById(userId)
                .orElseThrow(() -> new BusinessException("用户不存在: " + userId));

        // 等价于物理外键的 ON DELETE RESTRICT
        // 检查是否有活跃的子记录引用该用户
        long activeOrderCount = orderRepository.countByUserIdAndIsDeleted(userId, 0);
        if (activeOrderCount > 0) {
            throw new BusinessException(
                "无法删除用户，存在 " + activeOrderCount + " 条未完成订单");
        }

        // 软删除（详见第三节）
        user.setIsDeleted(1);
        user.setDeletedAt(LocalDateTime.now());
        userRepository.save(user);
    }
}
```

## 三、软删除替代物理删除

### 3.1 为什么要软删除

物理删除（`DELETE FROM`）的问题：

```
物理删除:
  DELETE FROM users WHERE id = 100;
  → 数据永久消失
  → 所有引用 user_id=100 的子记录变成孤儿
  → 无法审计追踪
  → 误删无法恢复（除非有备份）

软删除:
  UPDATE users SET is_deleted = 1, deleted_at = NOW() WHERE id = 100;
  → 数据还在，只是被标记
  → 子记录仍然可以关联到父记录
  → 可审计、可恢复
  → TOCTOU 问题自然消失（父记录永远存在）
```

### 3.2 软删除的表设计

```sql
CREATE TABLE users (
    id         BIGINT AUTO_INCREMENT PRIMARY KEY,
    username   VARCHAR(50) NOT NULL,
    email      VARCHAR(100) NOT NULL,

    -- 软删除字段
    is_deleted TINYINT(1) NOT NULL DEFAULT 0 COMMENT '0=正常 1=已删除',
    deleted_at DATETIME   DEFAULT NULL       COMMENT '删除时间，未删除时为 NULL',

    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,

    -- 软删除下的唯一约束处理（见 3.3 节）
    UNIQUE KEY uk_email_deleted (email, is_deleted)
) ENGINE=InnoDB;
```

### 3.3 软删除的唯一约束陷阱

假设 `email` 字段要求唯一。用户 A 注册了 `a@test.com`，然后注销（软删除），用户 B 想用 `a@test.com` 注册：

```
场景:
  1. 用户 A: email='a@test.com', is_deleted=0  → 正常
  2. 用户 A 注销: is_deleted=1
  3. 用户 B 注册: email='a@test.com', is_deleted=0
     → 如果唯一约束只在 email 上：UNIQUE(email)
     → 冲突！用户 B 无法注册
```

**解决方案**：使用 `deleted_at` 替代 `is_deleted` 参与唯一索引：

```sql
-- 方案 1: UNIQUE(email, deleted_at)
-- deleted_at 为 NULL 时表示未删除
-- 多次软删除会产生不同的 deleted_at 值，不冲突
ALTER TABLE users DROP INDEX uk_email_deleted;
ALTER TABLE users ADD UNIQUE KEY uk_email_alive (email, deleted_at);
```

```
场景回放:
  用户 A: email='a@test.com', deleted_at=NULL        → 唯一组合 ('a@test.com', NULL)
  用户 A 注销: deleted_at='2025-01-01 12:00:00'      → 唯一组合 ('a@test.com', '2025-01-01 12:00:00')
  用户 B 注册: email='a@test.com', deleted_at=NULL    → 唯一组合 ('a@test.com', NULL)
  → 不冲突 ✓
```

**注意 MySQL 的 NULL 行为**：在唯一索引中，MySQL 认为 `NULL != NULL`，所以多个 `deleted_at=NULL` 的行不会冲突——但这恰恰是我们不想要的（同一 email 只能有一个活跃用户）。需要额外约束：

```sql
-- 更安全的方案：用一个计算列
-- MySQL 8.0+ 支持生成列
ALTER TABLE users
    ADD COLUMN delete_token BIGINT GENERATED ALWAYS AS (
        CASE WHEN is_deleted = 0 THEN 0 ELSE id END
    ) STORED;

ALTER TABLE users ADD UNIQUE KEY uk_email_active (email, delete_token);
```

```
场景回放:
  用户 A 活跃: email='a@test.com', delete_token=0    → ('a@test.com', 0) ← 唯一
  用户 A 注销: delete_token=用户A的id                  → ('a@test.com', 42)
  用户 B 注册: email='a@test.com', delete_token=0     → ('a@test.com', 0) ← 唯一
  → 活跃用户中 email 唯一 ✓
  → 已删除用户不影响新注册 ✓
```

### 3.4 软删除的查询规范

所有业务查询**必须**加上 `is_deleted = 0` 条件：

```sql
-- ✗ 错误：可能查到已删除的数据
SELECT * FROM users WHERE id = 100;

-- ✓ 正确：只查活跃数据
SELECT * FROM users WHERE id = 100 AND is_deleted = 0;

-- ✓ 正确：JOIN 时两表都要过滤
SELECT o.id, o.amount, u.username
FROM orders o
JOIN users u ON o.user_id = u.id
WHERE o.is_deleted = 0
  AND u.is_deleted = 0;
```

在 ORM 层全局处理，避免遗漏：

```java
/**
 * 用户实体：使用 Hibernate @Where 注解自动过滤已删除记录。
 * 所有通过 JPA 的查询自动附加 is_deleted=0 条件。
 */
@Entity
@Table(name = "users")
@Where(clause = "is_deleted = 0")   // Hibernate 自动追加过滤条件
public class User {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String username;
    private String email;

    @Column(name = "is_deleted")
    private Integer isDeleted = 0;

    @Column(name = "deleted_at")
    private LocalDateTime deletedAt;

    // getter/setter 省略
}
```

### 3.5 软删除数据的生命周期

软删除的数据不应永久保留，需要有清理策略：

```
数据生命周期:

  创建 ──→ 活跃使用 ──→ 软删除 ──→ 冷存归档 ──→ 物理清除
  │         │            │           │            │
  │         │            │           │            └── 超过保留期限
  │         │            │           │                DELETE FROM + 归档表
  │         │            │           │
  │         │            │           └── 30~90 天后
  │         │            │               迁移到归档表/冷存储
  │         │            │
  │         │            └── is_deleted=1
  │         │                deleted_at=NOW()
  │         │
  │         └── is_deleted=0
  │             正常 CRUD
  │
  └── INSERT
```

定期清理脚本：

```sql
-- 将超过 90 天的软删除数据迁移到归档表
INSERT INTO users_archive
SELECT * FROM users
WHERE is_deleted = 1
  AND deleted_at < DATE_SUB(NOW(), INTERVAL 90 DAY);

-- 确认归档成功后，物理删除原表数据
DELETE FROM users
WHERE is_deleted = 1
  AND deleted_at < DATE_SUB(NOW(), INTERVAL 90 DAY)
LIMIT 1000;  -- 分批删除，避免大事务
```

## 四、数据一致性兜底：定时任务扫描孤儿记录

### 4.1 为什么需要兜底

即使 Service 层的代码写得完美，仍然有几种途径会产生孤儿记录：

```
孤儿记录产生的途径:
  ┌───────────────────────────────────────────────────┐
  │                                                   │
  │  1. TOCTOU 竞态: 查父记录时存在，写子记录前被删    │
  │  2. 直连数据库: DBA 手动操作跳过 Service 层        │
  │  3. 代码 Bug: 某个新功能忘了做存在性检查           │
  │  4. 消息队列: 异步消息中的 ID 指向已删除的记录      │
  │  5. 数据迁移: 迁移脚本中数据不完整                 │
  │                                                   │
  └───────────────────────────────────────────────────┘
```

**逻辑外键的一致性保证是"最终一致"，不是"强一致"。** 定时任务是实现最终一致的关键环节。

### 4.2 孤儿记录扫描 SQL

```sql
-- 扫描 orders 表中引用了不存在用户的记录
-- 使用 LEFT JOIN + IS NULL 模式
SELECT o.id AS orphan_order_id,
       o.user_id AS missing_user_id,
       o.created_at
FROM orders o
LEFT JOIN users u ON o.user_id = u.id
WHERE u.id IS NULL
  AND o.is_deleted = 0;
```

**如果使用软删除，还需要检查父记录是否已软删除**：

```sql
-- 扫描引用了已软删除用户的活跃订单
SELECT o.id AS orphan_order_id,
       o.user_id,
       u.deleted_at AS user_deleted_at
FROM orders o
JOIN users u ON o.user_id = u.id
WHERE u.is_deleted = 1     -- 父记录已软删除
  AND o.is_deleted = 0     -- 子记录仍然活跃
  AND u.deleted_at < DATE_SUB(NOW(), INTERVAL 7 DAY);  -- 给业务一定的宽限期
```

### 4.3 定时任务实现

```java
/**
 * 孤儿记录清理任务。
 * 定时扫描引用关系不完整的记录，根据策略进行修复或标记。
 *
 * 执行频率: 每天凌晨 2:00
 * 修复策略: 软删除孤儿子记录 + 告警通知
 */
@Component
public class OrphanRecordCleanupTask {

    private static final Logger log = LoggerFactory.getLogger(OrphanRecordCleanupTask.class);

    private final JdbcTemplate jdbcTemplate;
    private final AlertService alertService;

    // 每批处理的最大记录数，避免单次操作过多
    private static final int BATCH_SIZE = 500;

    public OrphanRecordCleanupTask(JdbcTemplate jdbcTemplate, AlertService alertService) {
        this.jdbcTemplate = jdbcTemplate;
        this.alertService = alertService;
    }

    /**
     * 定时执行: 每天 02:00。
     * 扫描并处理 orders 表中的孤儿记录。
     */
    @Scheduled(cron = "0 0 2 * * ?")
    public void cleanOrphanOrders() {
        log.info("开始扫描 orders 表孤儿记录");

        // 步骤 1: 扫描孤儿记录（父记录物理不存在）
        List<Long> orphanIds = jdbcTemplate.queryForList(
            "SELECT o.id FROM orders o " +
            "LEFT JOIN users u ON o.user_id = u.id " +
            "WHERE u.id IS NULL AND o.is_deleted = 0 " +
            "LIMIT ?",
            Long.class,
            BATCH_SIZE
        );

        if (!orphanIds.isEmpty()) {
            log.warn("发现 {} 条孤儿订单记录", orphanIds.size());

            // 步骤 2: 告警（可能是 Bug 导致的，需要人工确认）
            alertService.sendAlert(
                "孤儿记录告警",
                String.format("orders 表发现 %d 条孤儿记录，ID: %s",
                    orphanIds.size(),
                    orphanIds.subList(0, Math.min(10, orphanIds.size())))
            );

            // 步骤 3: 软删除孤儿记录
            // 注意：分批更新，每批不超过 BATCH_SIZE
            int updated = jdbcTemplate.update(
                "UPDATE orders SET is_deleted = 1, deleted_at = NOW() " +
                "WHERE id IN (" +
                    orphanIds.stream()
                        .map(String::valueOf)
                        .collect(Collectors.joining(",")) +
                ") AND is_deleted = 0"
            );
            log.info("已软删除 {} 条孤儿订单记录", updated);
        } else {
            log.info("未发现孤儿记录");
        }
    }
}
```

### 4.4 完整的孤儿扫描覆盖矩阵

对于一个中型系统，需要扫描所有逻辑外键关系：

```
┌────────────────────────────────────────────────────────┐
│              孤儿记录扫描覆盖矩阵                       │
├──────────────┬───────────────┬────────────┬────────────┤
│ 子表         │ 逻辑外键列    │ 父表       │ 扫描 SQL   │
├──────────────┼───────────────┼────────────┼────────────┤
│ orders       │ user_id       │ users      │ ✓ 已配置   │
│ order_items  │ order_id      │ orders     │ ✓ 已配置   │
│ order_items  │ product_id    │ products   │ ✓ 已配置   │
│ comments     │ user_id       │ users      │ ✓ 已配置   │
│ comments     │ post_id       │ posts      │ ✓ 已配置   │
│ addresses    │ user_id       │ users      │ ✓ 已配置   │
├──────────────┴───────────────┴────────────┴────────────┤
│ 维护方式: 新增逻辑外键关系时，必须同步更新扫描配置      │
└────────────────────────────────────────────────────────┘
```

可以用配置化的方式管理：

```java
/**
 * 逻辑外键关系定义。
 * 每个 entry 描述一条子表→父表的引用关系，用于孤儿记录扫描。
 *
 * childTable - 子表名
 * fkColumn   - 子表中的逻辑外键列
 * parentTable - 父表名
 * parentPk    - 父表主键列
 */
public record ForeignKeyRelation(
    String childTable,
    String fkColumn,
    String parentTable,
    String parentPk
) {}

// 注册所有逻辑外键关系
List<ForeignKeyRelation> relations = List.of(
    new ForeignKeyRelation("orders",      "user_id",    "users",    "id"),
    new ForeignKeyRelation("order_items", "order_id",   "orders",   "id"),
    new ForeignKeyRelation("order_items", "product_id", "products", "id"),
    new ForeignKeyRelation("comments",    "user_id",    "users",    "id"),
    new ForeignKeyRelation("comments",    "post_id",    "posts",    "id"),
    new ForeignKeyRelation("addresses",   "user_id",    "users",    "id")
);
```

通用扫描方法：

```java
/**
 * 通用孤儿记录扫描。
 * 根据注册的逻辑外键关系，自动生成扫描 SQL 并执行。
 *
 * @param relation 逻辑外键关系定义
 * @return 孤儿记录 ID 列表
 */
public List<Long> scanOrphans(ForeignKeyRelation relation) {
    String sql = String.format(
        "SELECT c.id FROM %s c " +
        "LEFT JOIN %s p ON c.%s = p.%s " +
        "WHERE p.%s IS NULL AND c.is_deleted = 0 " +
        "LIMIT 1000",
        relation.childTable(),
        relation.parentTable(),
        relation.fkColumn(),
        relation.parentPk(),
        relation.parentPk()
    );
    return jdbcTemplate.queryForList(sql, Long.class);
}
```

### 4.5 处理策略选择

发现孤儿记录后，不同业务场景需要不同的处理策略：

| 策略 | 适用场景 | 实现方式 |
|------|---------|---------|
| **告警 + 人工处理** | 核心业务数据（订单、支付） | 发通知给相关人员，不自动处理 |
| **自动软删除** | 非核心数据（日志、浏览记录） | 直接标记 `is_deleted=1` |
| **自动关联修复** | 可推断出正确关联的数据 | 根据业务规则修正外键值 |
| **移入隔离表** | 需要保留数据但不能影响业务 | `INSERT INTO quarantine_xxx SELECT ...` |

## 五、总结：应用层外键的完整方案

```
                 应用层逻辑外键的三层防线

  第一层: Service 层实时校验
  ┌─────────────────────────────────────────┐
  │  写操作前验证父记录存在性                 │
  │  删操作前验证无活跃子记录引用              │
  │  事务内完成，保证本次操作的一致性           │
  │  覆盖率: ~99.9% 的正常业务操作            │
  └─────────────────────────────────────────┘
                      │
                      ↓ 漏网的 0.1%（竞态/直连/Bug）
  第二层: 软删除
  ┌─────────────────────────────────────────┐
  │  父记录不物理删除，子记录永远有父可查      │
  │  消除 TOCTOU 中的"父记录消失"问题         │
  │  覆盖率: 消除大部分孤儿记录的产生条件      │
  └─────────────────────────────────────────┘
                      │
                      ↓ 仍然可能产生的不一致
  第三层: 定时任务兜底
  ┌─────────────────────────────────────────┐
  │  定期扫描所有逻辑外键关系                 │
  │  发现孤儿记录后告警 + 自动修复             │
  │  保证最终一致性                           │
  │  兜底率: 100%（只要扫描覆盖完整）          │
  └─────────────────────────────────────────┘
```

**物理外键 vs 应用层逻辑外键的本质取舍**：

```
物理外键:   强一致 + 低并发 + 低灵活性
逻辑外键:   最终一致 + 高并发 + 高灵活性 + 代码维护成本

在互联网业务中，"最终一致"的时间窗口（通常 < 1 天）
对业务的影响远小于"低并发"对用户体验的影响。
```
