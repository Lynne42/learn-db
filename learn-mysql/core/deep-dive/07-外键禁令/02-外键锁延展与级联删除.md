# 外键锁延展与级联删除

## 一、外键检查的锁延展

### 1.1 什么是锁延展

**锁延展（Lock Propagation）**：一个事务操作表 A 时，由于外键约束，InnoDB 被迫对表 B 也加锁。原本只涉及一张表的事务，锁的范围被"延展"到了另一张表。

```
正常 INSERT（无外键）:
┌─────────────────┐
│ 事务 A          │
│ INSERT orders   │ → 仅锁 orders 表的新行
│                 │
└─────────────────┘

外键 INSERT（有外键）:
┌─────────────────────────────────┐
│ 事务 A                          │
│ INSERT orders (user_id=100)     │ → 锁 orders 表的新行 (X 锁)
│                                 │ → 锁 users 表 id=100 行 (S 锁)  ← 锁延展！
│                                 │
└─────────────────────────────────┘
```

### 1.2 InnoDB 外键检查的底层锁流程

用一个完整的例子，逐步拆解 InnoDB 在外键检查时的锁行为：

```sql
-- 建表
CREATE TABLE users (
    id   INT PRIMARY KEY,
    name VARCHAR(50)
) ENGINE=InnoDB;

CREATE TABLE orders (
    id      INT PRIMARY KEY,
    user_id INT,
    amount  DECIMAL(10,2),
    FOREIGN KEY (user_id) REFERENCES users(id)
) ENGINE=InnoDB;

-- 插入父记录
INSERT INTO users VALUES (100, '张三');
```

现在执行子表插入：

```sql
-- 事务 A
BEGIN;
INSERT INTO orders (id, user_id, amount) VALUES (1, 100, 99.00);
-- 此时事务 A 未提交，持有以下锁：
--   1. orders 表：新插入行的 X 锁（Record Lock）
--   2. users 表：id=100 行的 S 锁（Record Lock）  ← 外键检查加的
```

**验证方式**——在另一个会话查看锁信息：

```sql
-- 会话 B：查看当前锁
SELECT
    ENGINE_LOCK_ID,
    ENGINE_TRANSACTION_ID,
    OBJECT_NAME,
    INDEX_NAME,
    LOCK_TYPE,
    LOCK_MODE,
    LOCK_DATA
FROM performance_schema.data_locks
WHERE OBJECT_SCHEMA = DATABASE();
```

典型输出：

```
+------------------+---------+------------+----------+-----------+--------+
| OBJECT_NAME      | INDEX   | LOCK_TYPE  | LOCK_MODE| LOCK_DATA |
+------------------+---------+------------+----------+-----------+--------+
| orders           | PRIMARY | RECORD     | X        | 1         |  ← 子表行 X 锁
| users            | PRIMARY | RECORD     | S        | 100       |  ← 父表行 S 锁
+------------------+---------+------------+----------+-----------+--------+
```

### 1.3 S 锁如何阻塞父表并发更新

S 锁（共享锁）的特性：**允许其他 S 锁并存，但阻塞 X 锁**。

```
时间线
  T1   事务 A: BEGIN;
  T2   事务 A: INSERT INTO orders (user_id=100) ...;
               → users.id=100 被加 S 锁 ✓

  T3   事务 B: BEGIN;
  T4   事务 B: UPDATE users SET name='张三丰' WHERE id=100;
               → 需要 users.id=100 的 X 锁
               → 与事务 A 的 S 锁冲突
               → 事务 B 进入等待状态 ⏳

  T5   事务 C: BEGIN;
  T6   事务 C: INSERT INTO orders (user_id=100) ...;
               → 需要 users.id=100 的 S 锁
               → S 与 S 兼容 ✓ (可以并发)

  T7   事务 A: COMMIT;
               → 释放 S 锁

  T8   事务 B: 获得 X 锁，UPDATE 执行 ✓
               → 但如果事务 C 还没提交，事务 B 仍然要等！
```

**问题的本质**：每一个子表的 INSERT 事务都在给父表行"续命"加 S 锁。只要有源源不断的子表写入，父表行的更新就被**无限期延迟**。

### 1.4 锁延展的影响范围

```
                    ┌───────────┐
                    │ users     │
                    │ id = 100  │
                    │           │
                    │ S S S S S │  ← 多个子表 INSERT 持有 S 锁
                    └─────┬─────┘
                          │
          ┌───────────────┼───────────────┐
          │               │               │
   ┌──────┴──────┐ ┌─────┴──────┐ ┌──────┴──────┐
   │  orders     │ │  comments  │ │  addresses  │
   │  user_id FK │ │  user_id FK│ │  user_id FK │
   └─────────────┘ └────────────┘ └─────────────┘

   三张子表都有外键指向 users，
   任何一张子表的 INSERT 都会对 users 行加 S 锁。
   当三张表同时高并发写入时，users 表的热点行被锁得水泄不通。
```

## 二、级联删除的 I/O 风暴

### 2.1 ON DELETE CASCADE 的工作原理

```sql
CREATE TABLE orders (
    id      INT PRIMARY KEY,
    user_id INT,
    FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
);
```

`ON DELETE CASCADE` 的含义：**删除父记录时，自动删除所有引用它的子记录**。

```sql
-- 删除用户
DELETE FROM users WHERE id = 100;

-- InnoDB 自动执行（用户不可见）:
-- DELETE FROM orders WHERE user_id = 100;
```

### 2.2 单层级联的 I/O 分析

假设用户 100 有 10,000 条订单：

```sql
DELETE FROM users WHERE id = 100;
```

InnoDB 的实际执行步骤：

```
步骤 1: 扫描 orders 表，找到所有 user_id=100 的行
        → 需要走 user_id 索引（如果有），否则全表扫描
        → 读取 I/O：索引页 + 数据页

步骤 2: 逐行删除 10,000 条 orders 记录
        → 每行删除涉及：
          a. 从聚簇索引（PRIMARY）中标记删除
          b. 从 user_id 二级索引中删除
          c. 写 Undo Log（支持回滚）
          d. 写 Redo Log（保证持久性）
        → 写入 I/O：数据页 + 索引页 + Undo + Redo

步骤 3: 删除 users 表 id=100 行
        → 正常的单行删除

实际 I/O 放大倍数：
  ┌─────────────────────────────────────────────┐
  │ 用户发起: DELETE 1 行 (users)                │
  │ 引擎实际: DELETE 10,001 行 (1 + 10,000)      │
  │                                             │
  │ Redo Log 写入: ~10,000 条日志条目             │
  │ Undo Log 写入: ~10,000 条回滚记录            │
  │ Buffer Pool 脏页: 数百到数千个                │
  │                                             │
  │ 表面上的 1 行删除 → 实际 I/O 放大数千倍        │
  └─────────────────────────────────────────────┘
```

### 2.3 事务大小与锁持有时间

级联删除在**同一个事务**内完成。事务越大，锁持有时间越长：

```
DELETE FROM users WHERE id=100 的事务时间线

  BEGIN ────────────────────────────────────────── COMMIT
    │                                               │
    ├── 锁 users.id=100 (X 锁)                      │
    ├── 锁 orders.user_id=100 的第 1 行 (X 锁)       │
    ├── 锁 orders.user_id=100 的第 2 行 (X 锁)       │
    ├── ...                                         │
    ├── 锁 orders.user_id=100 的第 10000 行 (X 锁)   │
    │                                               │
    │   所有锁从 BEGIN 一直持有到 COMMIT               │
    │   持续时间 = 10,000 行的删除时间                 │
    │   期间其他事务无法操作这些行                      │
    │                                               │
  ──────────────────────────────────────────────────→
              可能持续数秒到数十秒
```

### 2.4 对 Undo Log 和回滚段的压力

大事务产生的 Undo Log 体积可观：

```
每行 Undo 记录 ≈ 行数据大小 + 元数据开销 ≈ 200~500 字节（典型值）

10,000 行 × 300 字节 ≈ 3 MB Undo Log

如果此事务需要回滚：
  → 需要逐行 Undo，重新插入 10,000 行
  → 回滚时间 ≈ 删除时间 × 2（删除 + 重新插入）
  → 回滚期间 Undo Log 段不可被 Purge 线程清理
```

## 三、多层级联的多米诺骨牌效应

### 3.1 四层级联关联的结构

```sql
-- 层级 1: 公司
CREATE TABLE companies (
    id INT PRIMARY KEY, name VARCHAR(100)
);

-- 层级 2: 部门，外键 → 公司
CREATE TABLE departments (
    id INT PRIMARY KEY, company_id INT,
    FOREIGN KEY (company_id) REFERENCES companies(id) ON DELETE CASCADE
);

-- 层级 3: 员工，外键 → 部门
CREATE TABLE employees (
    id INT PRIMARY KEY, dept_id INT,
    FOREIGN KEY (dept_id) REFERENCES departments(id) ON DELETE CASCADE
);

-- 层级 4: 任务，外键 → 员工
CREATE TABLE tasks (
    id INT PRIMARY KEY, employee_id INT,
    FOREIGN KEY (employee_id) REFERENCES employees(id) ON DELETE CASCADE
);
```

关系图：

```
companies ──1:N──→ departments ──1:N──→ employees ──1:N──→ tasks
    │                   │                   │                │
    │              每公司 10 个         每部门 50 人       每人 20 条
    │                                                       │
    └──── DELETE 1 条 company 记录的多米诺效应 ──────────────→┘
```

### 3.2 多米诺骨牌计算

```sql
DELETE FROM companies WHERE id = 1;
```

级联展开：

```
第 1 层: DELETE companies WHERE id=1
         → 删除 1 行

第 2 层: DELETE departments WHERE company_id=1
         → 删除 10 行 (假设该公司有 10 个部门)

第 3 层: DELETE employees WHERE dept_id IN (被删的 10 个部门)
         → 删除 10 × 50 = 500 行

第 4 层: DELETE tasks WHERE employee_id IN (被删的 500 个员工)
         → 删除 500 × 20 = 10,000 行

总计: 1 + 10 + 500 + 10,000 = 10,511 行
```

可视化放大效应：

```
删除行数
    │
    │                                              ┌─────────┐
    │                                              │  10,000  │
    │                                              │  tasks   │
    │                                              │         │
    │                                              │         │
    │                                    ┌─────┐   │         │
    │                                    │ 500 │   │         │
    │                                    │emps │   │         │
    │                         ┌───┐      │     │   │         │
    │              ┌───┐      │   │      │     │   │         │
    │              │ 10│      │   │      │     │   │         │
    │   ┌─┐        │dep│      │   │      │     │   │         │
    │   │1│        │   │      │   │      │     │   │         │
    └───┴─┴────────┴───┴──────┴───┴──────┴─────┴───┴─────────┴──→
       company   departments  employees     tasks
       (层级 1)   (层级 2)     (层级 3)     (层级 4)
```

### 3.3 真实场景：数据规模更恐怖

在实际业务中，关联层级可能更深、每层基数更大：

| 层级 | 表 | 每父记录子记录数 | 累计删除行数 |
|------|--------|-----------------|-------------|
| 1 | `tenants`（租户） | 1 | 1 |
| 2 | `projects`（项目） | 50 | 50 |
| 3 | `issues`（工单） | 200 | 10,000 |
| 4 | `comments`（评论） | 30 | 300,000 |
| 5 | `attachments`（附件） | 5 | 1,500,000 |

删除 1 个租户 → 级联删除 **181 万行**。这在一个事务里完成，几乎必然导致：
- 超时 (`innodb_lock_wait_timeout`)
- 主从复制延迟（Binlog 单事务过大）
- 可能触发 OOM（Undo Log 占用过多内存）

### 3.4 级联更新的类似问题

`ON UPDATE CASCADE` 有同样的放大效应：

```sql
-- 如果修改公司主键（虽然不推荐，但技术上可行）
UPDATE companies SET id = 999 WHERE id = 1;

-- 级联展开:
-- UPDATE departments SET company_id=999 WHERE company_id=1  → 10 行
-- 但 departments 的主键变了吗？没有，所以不会触发下一层级联
-- 只有当被引用列（主键/唯一键）被更新时才触发级联

-- 但如果 departments 的外键引用的是它自己的主键被其他表引用...
-- 情况会更复杂
```

## 四、外键导致的隐式死锁

### 4.1 死锁的基本条件

死锁 = 两个或多个事务互相等待对方释放锁，形成循环等待。

外键检查创造了**跨表加锁**的路径，大幅增加死锁概率。

### 4.2 经典场景：交叉插入

```sql
-- 表结构
CREATE TABLE parents (id INT PRIMARY KEY);
CREATE TABLE children (
    id INT PRIMARY KEY,
    parent_id INT,
    FOREIGN KEY (parent_id) REFERENCES parents(id)
);

INSERT INTO parents VALUES (1), (2);
```

两个事务交叉操作：

```
时间    事务 A                                事务 B
────    ─────────────────────                ─────────────────────
 T1     BEGIN;                               BEGIN;

 T2     INSERT INTO children                 INSERT INTO children
        (id, parent_id)                      (id, parent_id)
        VALUES (10, 1);                      VALUES (20, 2);
        → children 行 10: X 锁               → children 行 20: X 锁
        → parents 行 1: S 锁                 → parents 行 2: S 锁

 T3     DELETE FROM parents                  DELETE FROM parents
        WHERE id = 2;                        WHERE id = 1;
        → 需要 parents 行 2: X 锁            → 需要 parents 行 1: X 锁
        → parents 行 2 被事务 B 持有 S 锁      → parents 行 1 被事务 A 持有 S 锁
        → 等待事务 B...                       → 等待事务 A...
        ↓                                    ↓
        ╔═══════════════════════════════════════╗
        ║          D E A D L O C K !            ║
        ║  事务 A 等待事务 B，事务 B 等待事务 A    ║
        ╚═══════════════════════════════════════╝
```

### 4.3 死锁检测的代价

InnoDB 有自动死锁检测（Wait-for Graph），检测到死锁后会回滚其中一个事务：

```
InnoDB 死锁检测流程:
  1. 事务请求锁 → 发现冲突 → 加入等待队列
  2. 构建 Wait-for Graph
  3. 检测图中是否有环
  4. 有环 → 选择回滚代价最小的事务（通常是 Undo Log 最少的）
  5. 回滚被选中的事务，释放其锁
  6. 另一个事务获得锁，继续执行
```

死锁检测本身也有开销：

| 参数 | 说明 |
|------|------|
| `innodb_deadlock_detect = ON` | 默认开启，每次锁等待都触发检测 |
| 检测算法复杂度 | O(N²)，N = 等待中的事务数 |
| 高并发下的问题 | 数百个事务同时等待锁时，死锁检测本身成为瓶颈 |

### 4.4 更隐蔽的场景：Gap Lock + 外键

InnoDB 在 `REPEATABLE READ` 隔离级别下使用 Gap Lock 防止幻读。外键检查与 Gap Lock 的交互会产生更隐蔽的死锁：

```sql
-- 父表 parents 有 id: 1, 5, 10

-- 事务 A:
INSERT INTO children (id, parent_id) VALUES (100, 5);
-- 外键检查在 parents 的主键索引上加 S 锁
-- 锁定范围: parents.id=5 的 Record Lock

-- 事务 B:
INSERT INTO parents (id) VALUES (3);
-- 在 parents 的主键索引上，(1, 5) 这个 gap 内插入
-- 需要该 gap 的 Insert Intention Lock
-- 如果事务 A 的外键检查产生了 Next-Key Lock (Record + Gap)
-- 那么事务 B 的插入可能被阻塞
```

这类死锁难以复现和排查，因为：
- 锁的范围取决于索引中现有的值分布
- Gap Lock 的行为在不同隔离级别下不同
- 错误日志中的死锁信息可能不够直观

### 4.5 查看死锁日志

```sql
-- 查看最近一次死锁信息
SHOW ENGINE INNODB STATUS\G

-- 关键输出段:
-- LATEST DETECTED DEADLOCK
-- *** (1) TRANSACTION:
-- *** (1) WAITING FOR THIS LOCK TO BE GRANTED:
-- *** (2) TRANSACTION:
-- *** (2) HOLDS THE LOCK(S):
-- *** (2) WAITING FOR THIS LOCK TO BE GRANTED:
-- *** WE ROLL BACK TRANSACTION (1)
```

更推荐开启死锁日志持久化：

```sql
-- 将所有死锁信息写入 error log
SET GLOBAL innodb_print_all_deadlocks = ON;
```

## 五、总结：外键引入的隐性成本矩阵

| 成本维度 | 具体表现 | 影响程度 |
|----------|---------|---------|
| **锁延展** | 子表 INSERT → 父表 S 锁，阻塞父表写操作 | 高：直接降低并发 TPS |
| **级联删除 I/O** | 1 行删除 → 数千~百万行删除 | 极高：可能引发服务不可用 |
| **多层级联** | N 层关联，删除量指数增长 | 极高：生产事故级别 |
| **隐式死锁** | 跨表加锁增加死锁概率 | 中高：难排查，随机出现 |
| **大事务风险** | 级联操作在单事务内，Undo/Redo 激增 | 高：主从延迟、回滚超时 |
| **不可预测性** | DBA/开发者可能不知道 DELETE 会触发级联 | 高：操作风险不透明 |

> **核心教训**：外键把"显式的应用层逻辑"变成了"隐式的引擎行为"。在小规模系统中这是便利，在大规模系统中这是定时炸弹。
