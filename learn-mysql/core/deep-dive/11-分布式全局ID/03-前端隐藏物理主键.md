# 前端隐藏物理主键

> **核心原则：前端永远不应该感知到数据库主键的存在。** 物理主键（`id`）是数据库内部的寻址工具，不是面向外部的业务标识。把它暴露给前端，等于把你家的门牌号、楼层、房间号全部告诉陌生人。

---

## 1. 暴露物理主键的风险

### 1.1 恶意爬虫遍历

自增 ID 是连续整数，攻击者只需写一个循环就能遍历你的全部数据：

```
攻击脚本伪代码：

for id in range(1, 10_000_000):
    response = requests.get(f"https://api.example.com/users/{id}")
    if response.status_code == 200:
        save(response.json())  # 拿到用户数据
    # 即使限流也可以低速持续爬取
```

```
=== 连续 ID 的遍历成本 ===

  /api/users/1      ← 存在
  /api/users/2      ← 存在
  /api/users/3      ← 已删除（404）
  /api/users/4      ← 存在
  ...
  /api/users/99999  ← 存在

  攻击者确切知道：
  1. ID 空间范围（从 1 到当前最大值）
  2. 每两个相邻 ID 之间没有其他记录
  3. 遍历效率 100%（不需要猜测）
```

即使 API 做了鉴权，攻击者仍可利用已知 ID 范围构造 IDOR（Insecure Direct Object Reference）攻击——把 URL 中的 `id=123` 改成 `id=124` 就能访问别人的数据。

### 1.2 竞品反推业务量

```
=== 竞品分析攻击 ===

  第 1 天注册账号 → 返回 user_id = 10000
  第 30 天注册账号 → 返回 user_id = 15000

  推算：
  - 30 天新增 5000 用户
  - 日均新增 ≈ 167 用户
  - 总用户数 ≈ 15000（假设从 1 开始）

  同理，订单 ID 可推算出：
  - 日订单量
  - 月 GMV 范围（如果金额字段也泄露）
  - 增长趋势
```

这些数据对竞品来说价值极高，而你只是因为把 `id` 字段传给了前端。

### 1.3 雪花 ID 同样有风险

雪花 ID 虽然不连续，但包含时间戳信息：

```
雪花 ID = 1456789012345678848

反解：
  时间戳部分(41bit) → 2024-11-06 14:30:22.123
  机器 ID(10bit)   → datacenter=3, worker=7
  序列号(12bit)    → 第 1024 个

泄露信息：
  - 记录的精确创建时间
  - 服务器部署拓扑（数据中心数、机器数）
  - 同一毫秒内的并发量
```

## 2. 方案一：接口层用业务编号替代物理 ID

### 2.1 原理

在数据库中为每条记录生成一个 **业务编号**（如 `order_sn`、`user_code`），对外只暴露这个编号，内部查询通过唯一索引定位。

### 2.2 数据库设计

```sql
CREATE TABLE orders (
    -- 内部主键：自增，不暴露
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,

    -- 外部业务编号：对前端暴露
    order_sn VARCHAR(32) NOT NULL,

    user_id BIGINT UNSIGNED NOT NULL,
    amount DECIMAL(10,2) NOT NULL,
    status TINYINT NOT NULL DEFAULT 0,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,

    PRIMARY KEY (id),
    UNIQUE KEY uk_order_sn (order_sn)   -- 唯一索引，支持高效查询
) ENGINE=InnoDB;
```

### 2.3 业务编号的生成规则

```sql
-- 示例：订单编号 = 日期 + 业务类型 + 随机/序列
-- 格式：OD20241106143022A7X3
--       ↑  ↑              ↑
--      前缀 时间戳         随机后缀

-- 注意：这个编号是在应用层生成的，不是数据库生成的
-- 编号本身不需要参与排序，排序用 created_at
```

### 2.4 接口设计

```
=== 正确做法 ===

GET /api/orders/OD20241106143022A7X3

响应：
{
    "order_sn": "OD20241106143022A7X3",   ← 外部标识
    "amount": 99.00,
    "status": "paid",
    "created_at": "2024-11-06T14:30:22Z"
    // 注意：没有 id 字段！
}


=== 错误做法 ===

GET /api/orders/12345

响应：
{
    "id": 12345,                           ← 暴露了物理主键
    "order_sn": "OD20241106143022A7X3",
    "amount": 99.00,
    ...
}
```

### 2.5 后端查询

```sql
-- 前端传来 order_sn，后端通过唯一索引查询
SELECT id, order_sn, user_id, amount, status, created_at
FROM orders
WHERE order_sn = 'OD20241106143022A7X3';

-- 内部关联查询仍然使用 id（高效的整数主键）
SELECT o.order_sn, oi.product_name, oi.quantity
FROM orders o
JOIN order_items oi ON oi.order_id = o.id
WHERE o.order_sn = 'OD20241106143022A7X3';
```

### 2.6 优缺点

| 优点 | 缺点 |
|:-----|:-----|
| 语义清晰，编号本身可包含业务含义 | 需要额外的唯一索引（存储 + 写入开销） |
| 天然防爬虫（不可遍历） | 编号生成逻辑需要保证唯一性 |
| 前端展示友好（用户可以看到订单号） | 编号较长，URL 和日志中占空间 |
| 不依赖任何加解密逻辑 | 如果编号中包含时间戳，仍有少量信息泄露 |

## 3. 方案二：Hashids / 对称加密编码

### 3.1 原理

将整数 ID **可逆地编码** 为一个看起来随机的短字符串。前端拿到的是编码后的字符串，后端收到后解码回原始 ID。

```
编码（后端 → 前端）：
  id=12345  →  encode  →  "NkK9"

解码（前端 → 后端）：
  "NkK9"   →  decode  →  id=12345

特点：
- 可逆：能编码就能解码
- 不可预测：不知道 salt 就无法从 "NkK9" 推断出 12345
- 不是加密：安全性不如 AES，但对于隐藏 ID 足够
```

### 3.2 Hashids 实现

Hashids（现更名为 Sqids）是最流行的 ID 编码库，支持几乎所有主流语言。

```
=== Hashids 编码过程 ===

输入：
  - 整数 ID = 12345
  - Salt = "my-secret-salt"（每个项目唯一）
  - 字母表 = "abcdefghijklmnopqrstuvwxyz0123456789"
  - 最小长度 = 8

过程（简化）：
  1. 用 salt 打乱字母表顺序
     原始: abcdefghijklmnopqrstuvwxyz0123456789
     打乱: k9m2p5r8t1v4x7z0b3d6f...（由 salt 决定）

  2. 将 ID 转换为打乱后的字母表的「混合进制」表示
     12345 → 对应打乱字母表的某几个字符

  3. 添加 guard 字符（防止相邻 ID 产生相似编码）

  4. 填充到最小长度

输出：
  "NkK9x3Lp"

关键安全特性：
  - 相邻 ID 的编码完全不同：
    12345 → "NkK9x3Lp"
    12346 → "Wr7mB2Qj"  ← 完全不同！
    12347 → "Yp4nD8Xv"  ← 完全不同！
```

### 3.3 对称加密方案（AES）

如果需要更高的安全性，可以用 AES 等对称加密算法：

```
编码：
  id=12345
  → 转为固定长度字节 (8 bytes)
  → AES-128-CBC 加密 (key + IV)
  → Base64URL 编码
  → "dGhpcyBpcyBhbiBlbmNyeXB0ZWQ"

解码：
  "dGhpcyBpcyBhbiBlbmNyeXB0ZWQ"
  → Base64URL 解码
  → AES-128-CBC 解密 (key + IV)
  → 得到 id=12345
```

### 3.4 接口设计

```
=== API 层的编解码 ===

     前端                    后端 API 层                     业务逻辑层
      │                        │                               │
      │  GET /users/NkK9x3Lp   │                               │
      │──────────────────────►│                               │
      │                        │  decode("NkK9x3Lp") → 12345  │
      │                        │──────────────────────────────►│
      │                        │                               │
      │                        │     SELECT * FROM users       │
      │                        │     WHERE id = 12345          │
      │                        │                               │
      │                        │◄──────────────────────────────│
      │                        │  encode(12345) → "NkK9x3Lp"  │
      │◄──────────────────────│                               │
      │                        │                               │
      │  {                     │                               │
      │    "uid": "NkK9x3Lp",  │  ← 前端永远只看到编码后的 ID  │
      │    "name": "张三",     │                               │
      │    ...                 │                               │
      │  }                     │                               │
```

### 3.5 关键实现细节

```
=== 编解码层应该放在哪里？ ===

推荐：放在 API 网关层 或 Controller 层的序列化/反序列化环节

     请求进来：
     URL/Body 中的字符串 ID → 反序列化时自动 decode → 业务层拿到整数 ID

     响应出去：
     业务层返回整数 ID → 序列化时自动 encode → 前端拿到字符串 ID

好处：
  - 业务逻辑层完全不感知编码的存在
  - 编解码逻辑集中管理，不会遗漏
  - 数据库查询始终用整数 ID（性能最优）
```

### 3.6 Hashids vs 对称加密对比

| 维度 | Hashids (Sqids) | AES 对称加密 |
|:-----|:---------------|:------------|
| 安全性 | 中等（非加密，理论上可被逆向） | 高（密码学安全） |
| 编码长度 | 短（8-12 字符） | 较长（24-44 字符，取决于块大小） |
| 性能 | 极快（简单数学运算） | 较快（但涉及加密运算） |
| URL 友好 | ✅ 默认 URL 安全 | 需要 Base64URL 编码 |
| 适用场景 | 一般业务系统 | 金融、医疗等高安全要求场景 |

## 4. 方案三：后端生成不可逆 Token

### 4.1 原理

不做编解码，而是在数据库中为每条记录生成一个 **随机的、不可逆的外部标识（token/external_id）**，用专门的字段存储并建索引。

```
=== 与 Hashids 的本质区别 ===

Hashids：id ←→ 编码字符串（可逆映射，不存数据库）
Token：  id → 随机字符串（不可逆，存在数据库中）

Hashids: id=12345 ↔ "NkK9x3Lp"  （算法可双向转换）
Token:   id=12345 → "a8f3k2m9x7"  （无法从 token 推算出 id）
         数据库：id=12345, token="a8f3k2m9x7"
```

### 4.2 数据库设计

```sql
CREATE TABLE users (
    -- 内部主键
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,

    -- 外部不可逆标识
    external_token CHAR(22) NOT NULL,  -- Base64URL 编码的 128-bit 随机值

    username VARCHAR(50) NOT NULL,
    email VARCHAR(100) NOT NULL,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,

    PRIMARY KEY (id),
    UNIQUE KEY uk_external_token (external_token)
) ENGINE=InnoDB;
```

### 4.3 Token 生成方式

```sql
-- 方式 1：应用层生成（推荐）
-- 使用密码学安全的随机数生成器
-- Python: secrets.token_urlsafe(16)  → 22 字符
-- Java: SecureRandom + Base64URL
-- Node.js: crypto.randomBytes(16).toString('base64url')

-- 方式 2：数据库层生成（MySQL 8.0+）
INSERT INTO users (external_token, username, email)
VALUES (
    TO_BASE64(RANDOM_BYTES(16)),  -- 128-bit 随机值的 Base64
    'zhangsan',
    'zhangsan@example.com'
);
```

### 4.4 接口设计

```
=== 完整请求流程 ===

1. 前端请求：
   GET /api/users/a8f3k2m9x7p4q1w6e0r2

2. 后端处理：
   SELECT id, external_token, username, email
   FROM users
   WHERE external_token = 'a8f3k2m9x7p4q1w6e0r2';

3. 内部关联查询（使用 id）：
   SELECT u.username, o.order_sn, o.amount
   FROM users u
   JOIN orders o ON o.user_id = u.id
   WHERE u.id = 12345;  -- 内部用 id，快速

4. 返回前端：
   {
       "token": "a8f3k2m9x7p4q1w6e0r2",  // 外部标识
       "username": "zhangsan",
       "email": "zhangsan@example.com"
       // 没有 id 字段
   }
```

### 4.5 优缺点

| 优点 | 缺点 |
|:-----|:-----|
| 完全不可逆，安全性最高 | 额外存储开销（每行多 22 字节 + 索引） |
| 不依赖任何加解密算法，无密钥管理 | 查询时走二级索引，多一次回表 |
| Token 可随时重新生成（轮换） | 需要在插入时生成 token 并保证唯一 |
| 与 ID 完全解耦 | 实现稍复杂（需要维护额外字段） |

## 5. 三种方案对比

| 维度 | 业务编号 | Hashids/加密 | 不可逆 Token |
|:-----|:--------|:------------|:------------|
| 安全性 | ⚠️ 编号可能含时间信息 | ⚠️ Hashids 理论可逆; AES 安全 | ✅ 完全不可逆 |
| 存储开销 | 需要额外字段 + 索引 | 零（运行时计算） | 需要额外字段 + 索引 |
| 查询性能 | 走唯一索引（一次回表） | 解码后走主键（最快） | 走唯一索引（一次回表） |
| 实现复杂度 | 低（定好编号规则即可） | 中（需要编解码层） | 低（生成随机值即可） |
| 可读性 | ✅ 高（人类可读的编号） | ❌ 低（无意义字符串） | ❌ 低（无意义字符串） |
| 密钥管理 | 无 | 需要管理 salt/密钥 | 无 |
| Token 轮换 | ❌ 业务编号通常不可变 | ❌ 换 salt 则所有编码变化 | ✅ 可单独轮换某条记录 |

## 6. 实战建议

### 6.1 决策树

```
你的 API 需要对外暴露资源标识吗？
├── 否（纯内部系统）→ 直接用 id，但仍建议不在响应中返回
└── 是 → 选择隐藏方案
         │
         ├── 业务上需要人类可读的编号？
         │   └── 是 → 方案一：业务编号（order_sn, user_code）
         │
         ├── 追求最高安全性？
         │   └── 是 → 方案三：不可逆 Token
         │            适合：金融、医疗、政务系统
         │
         └── 追求简单 + 低存储开销？
             └── 是 → 方案二：Hashids / Sqids
                      适合：一般互联网业务
```

### 6.2 通用防御清单

不管用哪种方案，以下措施都应该做到：

| 防御措施 | 说明 |
|:---------|:-----|
| **API 响应中不返回 `id` 字段** | 序列化时直接排除，从源头杜绝泄露 |
| **权限校验** | 每个请求都要验证「当前用户是否有权访问该资源」，不能仅依赖 ID 不可猜测 |
| **限流** | 对单 IP/单用户的请求频率做限制，防止暴力遍历 |
| **日志脱敏** | 日志中记录内部 ID，不记录 token/编码值（或反过来，看场景） |
| **前端代码审查** | 确保前端代码、localStorage、URL 中没有残留的物理 ID |

### 6.3 常见错误

```
❌ 错误 1：API 响应中同时返回 id 和业务编号
{
    "id": 12345,                    ← 泄露了
    "order_sn": "OD20241106A7X3",
    ...
}

❌ 错误 2：前端用 id 做路由，用业务编号做展示
/orders/12345                       ← URL 中暴露了 id
页面上显示：订单号 OD20241106A7X3

❌ 错误 3：Hashids 的 salt 硬编码在前端 JavaScript 中
const hashids = new Hashids("my-secret-salt");  ← salt 泄露
// 攻击者查看 JS 源码就能解码所有 ID

❌ 错误 4：只隐藏了主资源的 ID，关联资源仍然暴露
{
    "token": "NkK9x3Lp",           ← 主资源隐藏了
    "user_id": 67890,              ← 关联资源暴露了！
    "category_id": 5               ← 也暴露了！
}
```

## 7. 总结

| 原则 | 说明 |
|:-----|:-----|
| **物理主键是内部实现细节** | 前端不应该知道它的存在，就像用户不需要知道数据存在哪个磁盘扇区 |
| **对外只暴露业务标识** | 业务编号、编码 ID、或不可逆 Token |
| **安全不能只靠"不可猜测"** | 即使用了 Token，仍然需要权限校验和限流 |
| **编解码逻辑集中管理** | 放在 API 网关或序列化层，业务代码不感知 |
| **所有关联资源的 ID 都要隐藏** | 不能只隐藏主资源，忘了外键引用 |
