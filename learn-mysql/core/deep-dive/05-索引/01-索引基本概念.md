
# 主键与索引的关系

主键是一种"业务约束"，而索引是实现这种约束的"物理数据结构"。

概念 | 属于什么层面 | 数量限制 | 叶子节点存什么 | 核心目的 | 
| -- | -- | -- | -- | -- |
主键 (PK) | 业务逻辑层 + 物理存储层 | 一张表必须有且仅有 1 个 | 完整的整行数据 | 保证数据的唯一性与物理存储的有序性 | 
索引 (Index) | 性能优化层 (纯技术手段) | 一张表可以有 多个 (建议不超 5 个) | 主键的值 (如果是二级索引) | 为了提高查询速度，消除全表扫描 | 

## 类比：图书与目录

没有索引的表：就像一本 1000 页的字典，没有目录，所有字随机排列。你想找一个字，必须从第 1 页一页一页翻到第 1000 页（这在数据库里叫 全表扫描 Full Table Scan，高并发下必死）。

- **索引（Index）**：就是这本字典的目录。它是一个独立抽离出来的结构，帮你快速定位到数据在第几页。

- **主键（Primary Key）**：是这个目录里最特殊的一条硬性规定——"第一章的编号必须叫 1，且整本书只能有一个第 1 章，内容绝对不准重复"。

# 操作
## 创建索引

```sql
CREATE INDEX <索引名> ON <表名> (<列名>);

CREATE INDEX idx_users_created_at ON users (created_at);

```

1. **索引是有物理成本的**。每次写入、更新或删除一行记录，MySQL 都必须同步维护和改写所有相关的 B+ 二级索引树。索引过多会导致写入性能暴跌，并占用巨量磁盘空间。

2. 性别、状态等高重复、低区分度的字段绝不建议建单列索引

## 查看索引
```sql
SHOW INDEX FROM <表名>;
```

## 删除索引
```sql
DROP INDEX <索引名> ON <表名>;
```

##  查看查询计划: SQL 优化的核武器
```sql
EXPLAIN SELECT ...;

EXPLAIN SELECT * FROM users WHERE created_at > '2026-06-01 00:00:00';

```

在任何 SQL 前面加上 `EXPLAIN`，MySQL 优化器就会吐出它打算如何执行这个查询：
- **`type`**：表示访问类型。最核心的性能指标。
  - `ALL`：全表扫描，性能最烂，必须消除。
  - `index`：全索引扫描。比 ALL 强，但仍需遍历整棵树。
  - `range`：索引范围扫描。通过索引检索出特定区间的行，性能较好。
  - `ref`：非唯一性索引扫描。匹配单个非唯一索引值，非常快。
  - `const`：常数级查询。通常是通过主键或唯一索引等值过滤，性能极佳。
- **`key`**：实际走到的索引名。如果是 `NULL`，代表没有走任何索引。
- **`rows`**：预估需要扫描的记录行数。越小性能越好。
- **`Extra`**：核心附加信息。
  - `Using filesort`：说明 MySQL 需要把数据放到内存或磁盘中重新排序，性能较差，应当尽量利用索引自身的顺序性规避。


# 聚簇索引与二级索引对比
```text
┌──────────────────┬────────────────────────────┬───────────────────────────────┐
 │     物理维度     │    聚簇索引 (Primary Key)    │    二级索引 (Secondary Index)  │
 ├─────────────────┼────────────────────────────┼───────────────────────────────┤
 │ **数量限制**     │ 一张表【有且仅有 1 个】        │ 一张表可以有【多个】          │
 │ **叶子节点内容**  │ 包含【完整行记录的所有字段】    │ 仅包含【索引列字段 + 主键 ID】│
 │ **物理存储**     │ 数据实体本身，物理按主键排序    │ 独立于数据页之外的辅助 B+ 树  │
 │ **查询耗时**     │ 1 次 B+ 树寻址，直接获取数据   │ 1 次二级索引树 + 1 次回表寻址  │
 └──────────────── ┴────────────────────────────┴───────────────────────────────┘
```
