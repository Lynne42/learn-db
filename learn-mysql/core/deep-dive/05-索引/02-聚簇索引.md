# 聚簇索引（Clustered Index）
聚簇索引（Clustered Index） 是 MySQL InnoDB 存储引擎的数据组织核心。它的灵魂本质是：数据行本身与索引（B+ 树）物理存储在一起，“索引即数据，数据即索引”。

当表声明 `PRIMARY KEY` 时，InnoDB 会以主键建立聚簇索引 B+Tree。叶子节点保存完整行记录，因此主键查找可以直接取得数据，不需要再访问另一棵树。

聚簇索引的顺序同时决定数据记录的组织顺序。数据不可能同时按照两个不同的键保持聚簇排列，所以一张 InnoDB 表只能有一个聚簇索引。

# 物理存储原理：B+ 树上的数据实体
在 InnoDB 中，表是根据主键顺序组织存放的，这种表被称为索引组织表（Index-Organized Table）。聚簇索引就是这张表的主键 B+ 树。

InnoDB 根本没有单独的表物理文件，它直接用主键 B+ 树作为表的骨架，把整行整行的数据填在 B+ 树最底层的叶子节点里。寻找主键的过程，就是在整张物理表里精确定位数据的过程。

```text
                             【聚簇索引 B+ 树】
                                ┌─────────┐
                                │ Root 页 │
                                └────┬────┘
                           ┌─────────┴─────────┐
                           ▼                   ▼
                      ┌─────────┐         ┌─────────┐
                      │ 非叶节点│         │ 非叶节点│
                      └────┬────┘         └────┬────┘
                ┌──────────┴──────────┐        └──────────┐
                ▼                     ▼                   ▼
          ┌──────────┐          ┌──────────┐        ┌──────────┐
          │  叶子页  │ <──────> │  叶子页  │ <────> │  叶子页  │
          └──────────┘          └──────────┘        └──────────┘
          [ID:1|张三|20]         [ID:5|李四|25]       [ID:9|王五|30]
          ┌────────────────────────────────────────────────────┐
          │  叶子节点（Data Page）物理上直接存储了整行数据的全部字段  │
          └────────────────────────────────────────────────────┘
```


- 非叶子节点（Non-Leaf Nodes）：仅存储主键索引值与下层数据页的指针，用于在 O(\log N) 复杂度内进行快速二分查找。

- 叶子节点（Leaf Nodes）：存储了完整的行记录数据（包括所有非索引列字段），叶子节点之间通过双向链表相连，便于范围扫描。


# 聚簇索引的生成规则（MySQL 如何选择主键？）
一张 InnoDB 表有且仅有一个聚簇索引。MySQL 确定聚簇索引的优先级如下：

1. 显式主键：如果表定义了 PRIMARY KEY，InnoDB 直接使用该主键作为聚簇索引。

2. 唯一非空索引：若没有主键，InnoDB 会选择第一个定义的 非空唯一索引（UNIQUE NOT NULL） 作为聚簇索引。

3. 隐式隐形主键（RowID）：如果既无主键也无合适的唯一索引，InnoDB 会在后台自动创建一个 6 字节的隐式自增列 DB_ROW_ID 来构建聚簇索引。

所以通常在开发过程中，推荐主动创建[主键](../04-主键与唯一约束/03-自增ID与雪花算法决策.md)（PRIMARY KEY），一般可用 自增主键，如果是分布式的话，可以使用 雪花算法生成主键


# 研发准则
1. 强制推荐使用“单调递增的主键”（如 AUTO_INCREMENT / 趋势递增 Snowflake ID）
- 顺序插入（高效）：递增主键在插入时，新数据总是追加到当前聚簇索引最后一个数据页的末尾，数据页利用率接近 100%，极少触发页分裂。

- 随机插入（性能雪崩）：若采用乱序 UUID 作主键，新记录会被随机插入到 B+ 树中间的某个已满数据页中。这会强行触发 数据页分裂与物理挪动，导致磁盘 I/O 剧增、产生大量页空洞（碎片），性能暴跌。

2. 主键字段长度要“尽量小”
二级索引的叶子节点均存储了聚簇索引的主键值。主键越小（如 BIGINT 8 字节 vs VARCHAR(64) UUID），二级索引树所占用的内存和磁盘空间就越小，Buffer Pool 能缓存的数据页也就越多。

3. 利用覆盖索引（Covering Index）规避聚簇索引的回表
当只需要部分字段时，建立联合二级索引，使其包含 SELECT 所需的所有列。如此一来，查询只需在二级索引树上即可完成，无需再去触发聚簇索引的回表寻址。



# 自检

## 1. 理解 InnoDB 中“表即聚簇索引”的含义
在 InnoDB 中，根本不存在一个“单独存放数据的物理表文件”，再在旁边“另外造一个聚簇索引”。数据行本身，就是直接嵌入并构建在聚簇索引 B+ 树的叶子节点之中的。 也就是说表就创建在聚簇索引之上，聚簇索引就代表这张原始表

- 存储文件（.ibd）：整个文件内部只有一棵（或多棵）B+ 树。
- 物理结构：InnoDB 没有单独的“行数据堆”，它把所有的行记录，按照主键（PrimaryKey）的顺序，直接充当了聚簇索引 B+ 树的叶子节点（Data Page）。
- 关系：聚簇索引的骨架支撑起了整个表；把聚簇索引的所有叶子节点按顺序拼起来，物理上就是这张表的所有数据。

## 2. 理解主键叶子节点保存完整行数据的物理结构
一个又一个 16KB 的物理数据页（Page），通过双向链表首尾相连。在每一个 16KB 数据页内部，包含了页目录（二分查找槽）、单向链表指针，以及按字节紧密排列的、包含了隐藏事务列与所有业务列的真实行数据字节流。

## 3. 数据超出单页（16KB）大小时，怎么办
```text

                 ┌── 行与行累加 > 16KB ──> 触发【B+ 树页分裂】 ──> 申请新页，平分数据，重构链表
数据超 16KB 存储 ——┤
                 └── 单行字段太长 > 8KB ─> 触发【行溢出】     ──> 大字段剥离存入 Overflow Page，
                                                                  原页仅保留 20 字节物理指针

```  
因为InnoDB设计，单页至少需要保存两条行数据， 所以这里 单行字段太长 需要与 8KB 作对比，两条数据 每条占用8KB空间
