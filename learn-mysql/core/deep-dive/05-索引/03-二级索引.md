# 二级索引（Secondary Index，即辅助索引）
二级索引（Secondary Index，又称非聚簇索引 / 辅助索引） 是 MySQL InnoDB 存储引擎中，为了高效支持基于非主键字段的查询而构建的辅助 B+ 树数据结构。

如果说聚簇索引是“按主键排序的整张物理表”，那么二级索引就是“按特定非主键字段排序的索引目录”。

# 物理存储原理
```text
                             【二级索引 (如 idx_age) B+ 树】
                                      ┌─────────┐
                                      │ Root 页 │
                                      └────┬────┘
                                 ┌─────────┴─────────┐
                                 ▼                   ▼
                            ┌─────────┐         ┌─────────┐
                            │ 非叶节点 │         │ 非叶节点  │
                            └────┬────┘         └────┬────┘
                      ┌──────────┴──────────┐        └──────────┐
                      ▼                     ▼                   ▼
                ┌──────────┐          ┌──────────┐        ┌──────────┐
                │  叶子页  │ <──────> │  叶子页  │ <────> │  叶子页  │
                └──────────┘          └──────────┘        └──────────┘
                [age:20 | ID:1]       [age:25 | ID:5]      [age:30 | ID:9]
                ┌─────────────────────────────────────────────────────────┐
                │  👈 叶子节点物理上只存：【索引列自身的值】 + 【对应的主键 ID】 │
                └─────────────────────────────────────────────────────────┘
```

## 物理数据组成（叶子节点）
在二级索引的 16KB 叶子节点数据页（Data Page）中，每一条索引记录只包含两部分：

- 索引列的值：即你创建索引时指定的字段（如 age，或者联合索引的 (a, b, c)）。
- 对应的聚簇索引主键值（Primary Key）：用于指回聚簇索引（作为“物理书签”）。

> 二级索引按索引列排序，叶子节点**只存放了索引列自己的值以及对应的“主键 ID”**。它并不包含该行记录的其它字段（如邮箱、密码等）。拿到主键后，如果查询还需要其他列，就要回到聚簇索引读取完整记录。

> 唯一索引同时承担唯一性校验和检索加速；它仍然是二级索引，不会替代表的聚簇索引。


# 核心检索流程与“回表”物理本质
通过二级索引查找数据的过程，通常包含 “两次 B+ 树检索”：

1. 执行 SQL：SELECT * FROM users WHERE age = 25;

- Step 1（二级索引树检索）：
CPU 拿着 age = 25 进入 idx_age 的 B+ 树，从根节点一路往下找，到达叶子节点，拿到对应的 Primary Key = 5。

- Step 2（回表 - Bookmark Lookup）：
拿着 Primary Key = 5 重新跳到聚簇索引的 B+ 树，从聚簇索引的根节点重新往下找，到达聚簇索引的叶子节点，去提取包含 name, address, phone... 在内的 整行完整数据。

物理代价：回表意味着需要多加载至少一次磁盘数据页（增加磁盘 I/O），如果匹配到的数据量巨大，随机回表的开销甚至会超越全表扫描。

# 二级索引的分类

下面的四类都属于二级索引的具体形式；分类只描述索引键如何组织或约束数据，不包括覆盖索引。覆盖索引描述的是“某条查询是否能只使用索引完成”，因此继续单独学习。

二级索引类型 | 物理/逻辑特征 | 经典应用场景 |
--  |  --  |  --  |
普通索引（Index） | 最基础的二级索引，允许索引列值重复和为 NULL。 | 按非主键字段过滤，如 WHERE status = 1。 |
唯一索引（Unique Index） | 索引列的值必须唯一（允许存在多个 NULL）。数据库会在插入/更新时强制校验唯一性。 | 手机号、邮箱、身份证号等防重字段。 |
联合索引（Composite Index） | 包含 2 个或更多字段的二级索引（如 idx_a_b_c）。数据在树中按定义字段的顺序逐层排序。 | 多条件组合查询，如 WHERE tenant_id = 1 AND status = 2。 |
前缀索引（Prefix Index） | 对较长字符串字段（如 VARCHAR(255)）只截取前 N 个字符建立索引。 | 优化长字符串字段的索引空间，如 INDEX idx_email (email(10))。 |

## 普通索引

普通索引只负责提供检索路径，不承担唯一性约束：

```sql
CREATE INDEX idx_users_status ON users (status);
```

同一个 `status` 可以对应多行记录。二级索引叶子节点仍保存 `status` 和对应的主键值；如果查询还需要其他列，就要继续回表。

## 唯一索引

唯一索引仍然是一棵二级 B+Tree，叶子节点保存唯一列值和主键值。区别在于写入或更新时，InnoDB 必须检查同一唯一键值是否已经存在；重复值会触发 `Duplicate entry`：

```sql
CREATE UNIQUE INDEX uk_users_email ON users (email);
```

唯一性是写入约束，索引顺序则是读取路径；两者由同一棵索引结构同时承担。对于允许 `NULL` 的列，MySQL 可以保存多个 `NULL`，因为 `NULL` 不等于 `NULL`。

### 唯一索引、普通索引与主键索引

| 类型 | 数量 | 是否允许重复 | 是否允许 NULL | 物理角色 |
|---|---:|---:|---:|---|
| `PRIMARY KEY` | 最多 1 个 | 否 | 否 | 聚簇索引，叶子节点保存整行 |
| `UNIQUE INDEX` | 多个 | 否 | MySQL 中可有多个 `NULL` | 唯一二级索引，叶子节点保存索引列和主键 |
| 普通 `INDEX` | 多个 | 是 | 取决于列定义 | 普通二级索引，叶子节点保存索引列和主键 |

`UNIQUE` 约束通常会自动创建唯一索引；显式使用 `uk_<业务字段>` 命名，可以让错误日志和 `EXPLAIN` 更容易定位。


### 联合唯一索引

联合唯一索引约束的是“列组合”而不是每一列单独唯一：

```sql
CREATE UNIQUE INDEX uk_user_provider
    ON user_logins (user_id, provider);
```

同一用户不能重复绑定同一 `provider`，但不同用户可以使用同一个 `provider`。列顺序同时影响唯一性检查和查询是否命中最左前缀。

### 唯一索引的查询计划边界

对非 `NULL` 唯一键做等值查询时最多命中一行，优化器可能选择 `const` 或 `eq_ref` 访问类型。但唯一索引不代表所有查询都快：跳过最左列、对索引列做函数计算，或返回大量非索引列时，仍可能需要扫描或回表。

## 联合索引

联合索引把多个列按定义顺序写入同一棵 B+Tree，例如 `idx_tenant_status_created(tenant_id, status, created_at)`。排序和检索都遵循最左前缀

### 多列排序逻辑(不是目录树的嵌套存储，而是根据排序后存的扁平的元组)
多列排序逻辑（Lexicographical Order）：严格按照字典序排序：
- 先按 a 升序排序；
- a 相同则按 b 升序排序；
- a、b 都相同则按 c 升序排序；
- a、b、c 都相同则按 PK 升序排序。


本质：把 (a, b, c, PK) 拼成一个复合比较键（Composite Key），然后整体塞进 B+ 树的有序链表里
```
               ┌───────────────────────────────────┐
               │    [非叶子节点 (Root / Branch)]     │
               │   (1, 2, 3, id:1) -> Ptr to Page 1│
               │   (2, 1, 4, id:4) -> Ptr to Page 2│
               └───────────────┬───────────────┘
                               │
            ┌──────────────────┴──────────────────┐
            ▼                                     ▼
┌───────────────────────────────┐     ┌───────────────────────────────┐
│     [叶子节点: Page 1]        │     │     [叶子节点: Page 2]        │
│ 1. (a:1, b:2, c:3 | id:1)     │<--->│ 4. (a:2, b:1, c:4 | id:4)     │
│ 2. (a:1, b:2, c:5 | id:2)     │     │ 5. (a:2, b:1, c:4 | id:5)     │
│ 3. (a:1, b:3, c:1 | id:3)     │     │ 6. (a:3, b:1, c:2 | id:6)     │
└───────────────────────────────┘     └───────────────────────────────┘
```

## 前缀索引

前缀索引只为字符串列的前 N 个字符建立索引：

```sql
CREATE INDEX idx_users_email_prefix ON users (email(10));
```

它可以缩小索引体积，但前缀相同的值仍需继续比较，通常不能直接依靠前缀索引判断完整字符串是否相等；N 的取值应结合区分度和查询计划验证。

### 设计索引的原则
1. 先放稳定的等值过滤列，例如租户或用户 ID。
2. 再放其他等值过滤列，例如订单状态。
3. 然后放范围或排序列，例如创建时间。
4. 最后谨慎追加少量返回列以形成覆盖；不要把宽字段全部塞进索引。



### 最左前缀匹配原则（Leftmost Prefix Rule）—— 联合索引黄金律
对于联合索引 INDEX (a, b, c)，物理 B+ 树是优先按列 a 排序，在 a 相等的情况下再按 b 排序，在 b 相等的情况下再按 c 排序。


| 查询条件 | 能否利用索引定位 | 原因 |
|---|---:|---|
| `a = ?` | 是 | 命中第一层排序 |
| `a = ? AND b = ?` | 是 | 连续使用前两列 |
| `a = ? AND b = ? AND c = ?` | 是 | 使用完整索引 |
| `b = ?` | 通常不能高效定位 | 缺少最左列 `a`，相同 `b` 分散在不同 `a` 区间 |
| `a = ? AND c = ?` | 只能先按 `a` 定位 | 跳过 `b` 后，`c` 不能继续形成连续搜索边界 |

“最左前缀”描述的是 B+Tree 的有序边界，不是要求 SQL 条件必须按索引顺序书写。优化器会规范化 `WHERE` 条件，所以 `b = ? AND a = ?` 与 `a = ? AND b = ?` 通常等价。


- 范围中断效应：一旦某个列使用了范围查询（>, <, BETWEEN, LIKE 'xx%'），其右侧的列将无法使用索引筛选。例如：WHERE a = 1 AND b > 10 AND c = 3，只有 a 和 b 能走索引，c 无法走索引。
