# 索引失效场景归纳

> 前置知识：[索引设计四大铁律](./07-索引设计四大铁律.md) — 理解索引的设计原则与 B+ 树底层结构。

以下 9 大场景是导致索引失效的高频元凶。每个场景均给出**失效原因、SQL 示例、底层原理**。

---

## 1. 索引列使用函数或表达式计算

**失效原因**：对索引列施加函数或表达式后，B+ 树中存储的原始值无法直接用于比较，优化器被迫放弃索引。

```sql
-- ❌ 索引失效：对 create_time 使用了 YEAR() 函数
SELECT * FROM orders WHERE YEAR(create_time) = 2026;

-- ✅ 正确写法：用范围条件保持列干净
SELECT * FROM orders
WHERE create_time >= '2026-01-01' AND create_time < '2027-01-01';
```

**底层原理**：B+ 树的节点按 `create_time` 的原始值排序。`YEAR(create_time)` 需要先取出每行的值再计算，等价于全表扫描后逐行过滤。

---

## 2. 隐式类型转换（字符串列用数字查询）

**失效原因**：当列类型为 `VARCHAR` 而查询条件传入数字时，MySQL 会对**索引列**施加隐式的 `CAST()` 转换函数，导致索引失效。

```sql
-- ❌ 索引失效：cellphone 是 VARCHAR，传入了数字
SELECT * FROM users WHERE cellphone = 13800000000;

-- ✅ 正确写法：类型匹配
SELECT * FROM users WHERE cellphone = '13800000000';
```

**底层原理**：MySQL 的隐式转换规则是**字符串向数字转**。当列是 `VARCHAR` 而值是数字时，等价于 `WHERE CAST(cellphone AS SIGNED) = 13800000000`，函数施加在索引列上，退化为场景 1。反之，若列是 `INT` 而值是字符串 `'100'`，MySQL 将字符串转为数字，索引列未被包裹函数，索引**仍然有效**。

---

## 3. LIKE 以通配符开头（`LIKE '%xxx'`）

**失效原因**：B+ 树按照字符串从左到右的字典序排列。前缀未知时，无法确定扫描起点。

```sql
-- ❌ 索引失效：前缀通配符
SELECT * FROM users WHERE name LIKE '%明';

-- ✅ 索引有效：后缀通配符
SELECT * FROM users WHERE name LIKE '张%';
```

**底层原理**：`LIKE '张%'` 等价于范围查询 `name >= '张' AND name < '张\xff'`，可以利用 B+ 树定位起点并顺序扫描。`LIKE '%明'` 没有确定前缀，必须遍历所有叶子节点逐行匹配。

---

## 4. 使用 OR 条件且其中一侧无索引

**失效原因**：OR 要求两侧条件的结果取并集。如果其中一侧没有索引，那一侧只能全表扫描，优化器索性对整个查询都走全表扫描。

```sql
-- ❌ 索引失效：假设 remark 列没有索引
SELECT * FROM users WHERE cellphone = '13800000000' OR remark = 'VIP';

-- ✅ 解法 1：给 remark 也建索引（MySQL 可能使用 index_merge）
-- ✅ 解法 2：拆成两个查询用 UNION ALL
SELECT * FROM users WHERE cellphone = '13800000000'
UNION ALL
SELECT * FROM users WHERE remark = 'VIP' AND cellphone != '13800000000';
```

**底层原理**：优化器评估后发现，走索引只能解决 OR 的一半，另一半仍需全表扫描。两次扫描的 I/O 总和可能高于一次全表扫描，因此直接选择全表扫描。

---

## 5. 联合索引违反最左前缀

**失效原因**：联合索引 `(a, b, c)` 的 B+ 树先按 `a` 排序，`a` 相同时再按 `b`，`b` 相同时再按 `c`。跳过左侧列后，右侧列的排序无意义。

```sql
-- 假设联合索引 idx_abc(a, b, c)

-- ❌ 索引失效：跳过了最左列 a
SELECT * FROM t WHERE b = 2 AND c = 3;

-- ✅ 索引有效：从最左列开始
SELECT * FROM t WHERE a = 1 AND b = 2;

-- ⚠️ 部分有效：a 走索引，c 无法走索引（中间 b 被跳过）
SELECT * FROM t WHERE a = 1 AND c = 3;
```

**底层原理**：B+ 树的排序是嵌套的。没有 `a` 的等值约束，`b` 的值在全树范围内是无序的，无法利用树结构做二分查找。

---

## 6. 使用 `!=` / `NOT IN` / `NOT EXISTS`

**失效原因**：否定条件通常意味着需要扫描索引中"除了少数值之外的所有值"，本质上接近全量扫描。优化器评估后认为全表扫描成本更低。

```sql
-- ❌ 大概率索引失效
SELECT * FROM orders WHERE status != 1;

-- ❌ 大概率索引失效
SELECT * FROM orders WHERE status NOT IN (1, 2, 3);
```

**底层原理**：`!= 1` 等价于 `< 1 OR > 1`，即索引上的两段不连续区间。当匹配行数占比高时（如 status 只有 4 个值，`!= 1` 命中 75% 的行），优化器发现回表次数太多，随机 I/O 成本高于顺序全表扫描，于是放弃索引。

> **注意**：当 `!=` 过滤后剩余行数极少时（高选择性），优化器可能仍会选择索引。是否失效取决于数据分布和优化器的代价估算。

---

## 7. `IS NULL` / `IS NOT NULL`（取决于数据分布）

**失效原因**：与场景 6 类似，是否走索引取决于 NULL 值的占比。如果大部分行都是 NULL（或都不是 NULL），条件筛选后剩余行数太多，优化器放弃索引。

```sql
-- 如果 deleted_at 列 95% 的行为 NULL → IS NULL 命中 95% → 索引失效
SELECT * FROM users WHERE deleted_at IS NULL;

-- 如果 deleted_at 列 95% 的行为 NULL → IS NOT NULL 命中 5% → 索引有效
SELECT * FROM users WHERE deleted_at IS NOT NULL;
```

**底层原理**：InnoDB 的 B+ 树中**可以存储 NULL 值**（放在树的最前面）。索引本身不排斥 NULL，关键在于优化器的代价估算：命中行数过多时，回表的随机 I/O 成本超过全表扫描的顺序 I/O 成本。

---

## 8. 索引列参与 ORDER BY 但方向不一致（ASC/DESC 混用）

**失效原因**：联合索引中所有列默认按同一方向（ASC）排序。如果查询要求一列升序、另一列降序，B+ 树无法同时满足两个方向，退化为 FileSort。

```sql
-- 假设联合索引 idx_a_b(a, b)

-- ❌ 产生 FileSort：a 升序但 b 降序，索引无法同时满足
SELECT * FROM t ORDER BY a ASC, b DESC;

-- ✅ 解法（MySQL 8.0.1+）：创建带方向的索引
CREATE INDEX idx_a_asc_b_desc ON t(a ASC, b DESC);
```

**底层原理**：B+ 树的叶子节点链表是单向有序的。`(a ASC, b ASC)` 索引中，`a` 相同时 `b` 是升序排列。要 `b DESC` 就需要反向遍历，而跨 `a` 值的反向遍历无法通过简单的指针回溯实现。MySQL 8.0.1 引入了 Descending Index 来解决此问题。

---

## 9. 数据量太小或选择性太低导致优化器放弃索引

**失效原因**：当表的数据量极小（如几百行），或索引的选择性极低（如 `status` 列只有 3 个值），优化器评估走索引的代价（随机 I/O + 回表）高于全表扫描（顺序 I/O），直接选择全表扫描。

```sql
-- 表只有 200 行，即使 status 有索引，优化器也大概率全表扫描
SELECT * FROM small_config WHERE status = 1;
```

**底层原理**：优化器的代价模型会综合考虑：索引树的高度（随机 I/O 次数）、预估命中行数、回表次数、数据页在 Buffer Pool 中的缓存命中率。当代价估算显示索引路径总成本 > 全表扫描成本时，索引被放弃。可通过 `EXPLAIN` 的 `rows` 列和 `type` 列观察优化器的选择。

---

## 记忆口诀

> **函数计算类型转，LIKE 左匹配 OR 全扫；左缀不跳否定慎，NULL 看比例排序向；小表低选优化弃，EXPLAIN 一查全明了。**
