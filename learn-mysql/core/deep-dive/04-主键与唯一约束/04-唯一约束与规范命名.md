# 唯一约束与规范命名

> 前置知识：[主键本质与 InnoDB 强制要求](./01-主键本质与InnoDB强制要求.md) — 理解主键在 B+ 树上的物理实现。

## 学习边界

本文件只讨论业务唯一性、约束命名和应用层防重边界。UNIQUE 约束底层如何落成唯一二级索引、如何影响查询计划，统一放在[二级索引](../05-索引/03-二级索引.md)的“唯一索引”分类中学习。

## 1. `uk_` 前缀的规范命名意义

线上数据库报错时，错误信息通常是这样的：

```
ERROR 1062 (23000): Duplicate entry '13800001111' for key 'uk_cellphone'
```

如果你的唯一索引命名是随意的（如 `cellphone_index` 或更糟糕的 `idx_1`），在凌晨三点收到告警时，你需要额外去查这个索引对应的是哪个业务字段。

**规范命名 `uk_<字段名>`** 的价值：

| 场景 | 命名 `idx_1` | 命名 `uk_cellphone` |
| -- | -- | -- |
| 报错定位 | 需要查 DDL 才知道是哪个字段冲突 | 直接从报错信息看出是手机号重复 |
| 代码审查 | 看不出约束意图 | 一眼知道这是唯一约束而非普通索引 |
| 运维排查 | 无法快速判断是否可以安全删除 | 前缀标明了约束类型，防止误删 |

## 2. UNIQUE 与 PRIMARY KEY 的区别

| 维度 | PRIMARY KEY | UNIQUE |
| -- | -- | -- |
| 数量限制 | 一张表**有且仅有 1 个** | 一张表可以有**多个** |
| NULL 处理 | **绝对不允许** NULL | **允许一个 NULL**（多个 NULL 不视为重复） |
| 物理存储 | 决定聚簇索引的物理排列顺序 | 创建独立的二级索引 B+ 树 |
| 默认行为 | 自动创建聚簇索引 | 自动创建唯一二级索引 |
| 语义 | 行的唯一身份标识 | 业务字段的唯一性约束 |

> **注意**：InnoDB 中 UNIQUE 允许多个 NULL 值存在于同一列中，因为 SQL 标准规定 `NULL ≠ NULL`，所以多个 NULL 不构成重复。

## 3. 实战建议：哪些业务字段必须加唯一约束

以下业务字段如果不加 UNIQUE 约束，迟早会出现脏数据，且事后清洗代价极高：

| 业务字段 | 建议索引名 | 不加 UNIQUE 的后果 |
| -- | -- | -- |
| 手机号 | `uk_cellphone` | 同一手机号注册多个账号，登录时返回多条记录导致程序崩溃 |
| 邮箱 | `uk_email` | 密码重置邮件发给错误用户，引发安全事故 |
| 订单号 | `uk_order_sn` | 重复订单号导致支付状态混乱，资金对账失败 |
| 身份证号 | `uk_id_card` | 实名认证形同虚设，同一身份证绑定多个账号 |
| 第三方开放ID | `uk_open_id` | OAuth 登录时匹配到多条记录，用户被随机关联到错误账号 |

> **铁律**：凡是在业务层面"绝不应该重复"的字段，必须在数据库层通过 UNIQUE 约束兜底——永远不要只依赖应用层的 `if exists` 检查，因为并发场景下应用层检查存在时间窗口（TOCTOU），只有数据库的唯一约束才是原子性的最终防线。
