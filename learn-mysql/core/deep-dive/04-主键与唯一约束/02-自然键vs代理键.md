# 自然键 vs 代理键：为什么绝对不要用业务字段做主键

> 前置知识：[主键本质与 InnoDB 强制要求](./01-主键本质与InnoDB强制要求.md) — 理解主键与聚簇索引的物理绑定关系。

用业务字段做主键叫作**自然键** (Natural Key)。这在理论上看似完美（毕竟身份证号绝不重复），但在现实业务中是灾难：

## 灾难场景 1：牵一发而动全身

假设你用"手机号"做主键。某天用户换号了，要求修改。因为主键一旦变动，所有关联该主键的外键（订单表、购物车表、积分流水表）统统都要跟着级联更新！ 这种海量数据同时更新会瞬间锁死整个数据库。

## 灾难场景 2：B+ 树页分裂

如果你用无序的字符串（如普通的 UUID 或邮箱）做主键，每次插入新数据时，InnoDB 需要在树的中间强行塞入数据，导致数据页频繁分裂、移动碎片，写入性能会大幅雪崩。

## 结论

业务字段做主键存在两大不可调和的矛盾：

| 风险维度 | 具体表现 |
| -- | -- |
| 业务可变性 | 主键变更引发全链路级联更新，锁死数据库 |
| 物理无序性 | 非递增值导致 B+ 树页分裂，写入性能雪崩 |

应使用与业务完全解耦的**代理键**（Surrogate Key）——详见 [自增 ID 与雪花算法决策](./03-自增ID与雪花算法决策.md)。
