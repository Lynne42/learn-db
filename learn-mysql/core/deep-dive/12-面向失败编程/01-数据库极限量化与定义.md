# 数据库极限量化与定义

## 为什么要量化数据库极限

数据库不会在某一刻突然崩溃——它会先变慢、再变卡、然后连接堆积、最后雪崩。问题在于，"慢"和"卡"之间的边界在哪？如果你不能用数字回答这个问题，你就无法设报警、无法做容量规划、无法在故障前止血。

**量化极限的本质：把"感觉要出事了"变成"这个指标超过了 X 就必须干预"。**

---

## 一、四条红线

### 1.1 耗时红线：单条 SQL 执行时间

**核心原则：一条 SQL 占用数据库资源的时间越长，能同时服务的请求就越少。**

| 级别 | 耗时阈值 | 说明 |
|------|----------|------|
| 正常 | < 50ms | OLTP 业务的健康水平 |
| 预警 | 50ms ~ 200ms | 需要优化，但不影响可用性 |
| 危险 | 200ms ~ 1s | 高并发下可能导致连接池耗尽 |
| 致命 | > 1s | 必须立即 kill 或熔断 |

**为什么 1 秒是致命线？** 算一笔账：

```
假设连接池大小 = 20
每个请求占用一个连接
正常 SQL 耗时 = 10ms → 每秒可处理 20 × (1000/10) = 2000 QPS
一条慢 SQL 耗时 = 5s → 这条连接 5 秒内无法释放
如果 10 个请求命中这条慢 SQL → 占用 10 个连接长达 5 秒
剩余 10 个连接承载所有流量 → QPS 腰斩 → 响应时间上升 → 更多连接被占用 → 雪崩
```

**MySQL 中查看 SQL 执行时间：**

```sql
-- 开启慢查询日志
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 0.2;  -- 200ms 以上记录

-- 查看当前正在执行的 SQL 及其耗时
SELECT id, user, host, db, command, time, state, info
FROM information_schema.processlist
WHERE command != 'Sleep'
ORDER BY time DESC;

-- 使用 performance_schema 获取更精确的统计
SELECT digest_text,
       count_star AS exec_count,
       ROUND(avg_timer_wait / 1000000000, 2) AS avg_ms,
       ROUND(max_timer_wait / 1000000000, 2) AS max_ms,
       sum_rows_examined AS total_rows_scanned
FROM performance_schema.events_statements_summary_by_digest
ORDER BY avg_timer_wait DESC
LIMIT 20;
```

### 1.2 算力红线：CPU 使用率

**核心原则：数据库的 CPU 不是用来跑满的，必须留余量应对突发流量。**

```
                    CPU 使用率
  100% ┤ ████████████████████████████████████  ← 系统卡死，无法 SSH 登录
       │
   90% ┤ ████████████████████████████████      ← 查询排队，响应时间飙升
       │
   70% ┤ █████████████████████████             ← ⚠️ 红线：必须扩容或优化
       │
   50% ┤ ██████████████████                    ← 健康水平
       │
   30% ┤ ████████████                          ← 低负载
       │
    0% ┤
```

**为什么是 70% 而不是 90%？**

- 数据库 CPU 不是均匀消耗的，有毛刺（spike）。日常 70% 意味着毛刺可能到 90%+。
- CPU 打满后，MySQL 内部的 mutex 竞争加剧，性能不是线性下降，而是指数级恶化。
- 留 30% 余量用于：突发流量、后台任务（如 binlog dump）、运维操作（如 ALTER TABLE）。

**CPU 消耗的主要来源：**

| 来源 | 典型特征 | 排查方式 |
|------|----------|----------|
| 全表扫描 | `rows_examined` 远大于 `rows_sent` | EXPLAIN 看 type = ALL |
| 排序 | filesort，临时表 | EXPLAIN 看 Extra: Using filesort |
| 复杂 JOIN | 多表笛卡尔积 | EXPLAIN 看 rows 列的乘积 |
| 函数计算 | WHERE 条件中对列使用函数 | 检查 WHERE 子句 |
| 锁等待导致的重试 | 大量 deadlock、lock wait timeout | `SHOW ENGINE INNODB STATUS` |

**查看 CPU 消耗最高的 SQL：**

```sql
-- 按 CPU 时间排序（performance_schema 必须开启）
SELECT digest_text,
       count_star,
       ROUND(sum_timer_wait / 1000000000000, 2) AS total_sec,
       ROUND(avg_timer_wait / 1000000000, 2)    AS avg_ms,
       sum_rows_examined
FROM performance_schema.events_statements_summary_by_digest
ORDER BY sum_timer_wait DESC
LIMIT 10;
```

### 1.3 并发红线：活跃连接数与连接池

**核心原则：数据库能同时处理的请求数是有限的，连接池是保护数据库的第一道防线。**

```
                        连接的生命周期

  应用层        连接池              MySQL
  ┌───┐       ┌──────┐           ┌──────┐
  │请求│──────→│借连接│──────────→│处理SQL│
  │   │       │      │           │      │
  │   │←──────│还连接│←──────────│返回结果│
  └───┘       └──────┘           └──────┘
                 │
                 │ 所有连接被借完？
                 ▼
              请求排队等待（或直接拒绝）
```

**关键参数：**

| 参数 | 含义 | 建议值 |
|------|------|--------|
| `max_connections` | MySQL 允许的最大连接数 | 根据实例规格设定，通常 500~2000 |
| 连接池 `maximumPoolSize` | 单个应用实例的最大连接数 | 10~30（见后文黄金法则） |
| 连接池 `minimumIdle` | 空闲连接保持数 | 与 maximumPoolSize 相同（HikariCP 推荐） |
| `wait_timeout` | 空闲连接超时时间 | 300s（5 分钟） |
| `interactive_timeout` | 交互式连接超时 | 300s |

**致命场景——连接泄漏：**

```java
// ❌ 错误：异常时连接不会归还
Connection conn = dataSource.getConnection();
PreparedStatement ps = conn.prepareStatement(sql);
ResultSet rs = ps.executeQuery();
// 如果这里抛异常，conn 永远不会 close
process(rs);
conn.close();

// ✅ 正确：try-with-resources 保证归还
try (Connection conn = dataSource.getConnection();
     PreparedStatement ps = conn.prepareStatement(sql);
     ResultSet rs = ps.executeQuery()) {
    process(rs);
}
```

**监控活跃连接数：**

```sql
-- 查看当前连接状态
SHOW STATUS LIKE 'Threads_connected';   -- 当前连接数
SHOW STATUS LIKE 'Threads_running';     -- 当前活跃（执行中）连接数
SHOW STATUS LIKE 'Max_used_connections'; -- 历史最大连接数

-- 关键：Threads_running 才是真正消耗资源的
-- Threads_connected = 100 但 Threads_running = 5 → 健康
-- Threads_connected = 100 且 Threads_running = 80 → 危险
```

**并发红线的判断标准：**

| 指标 | 安全 | 预警 | 危险 |
|------|------|------|------|
| Threads_running | < 核心数 × 2 | 核心数 × 2 ~ × 4 | > 核心数 × 4 |
| 连接池等待时间 | < 10ms | 10ms ~ 100ms | > 100ms |
| 连接池排队数 | 0 | 1~5 | > 5 |

### 1.4 容量红线：单表行数与磁盘空间

**核心原则：数据量超过阈值后，索引效率下降，DDL 操作变得危险，备份恢复时间不可控。**

**单表行数的经验阈值：**

| 行数 | 状态 | 影响 |
|------|------|------|
| < 500 万 | 安全 | 正常使用，无需特别处理 |
| 500 万 ~ 2000 万 | 预警 | 需要确认索引覆盖率，准备分表方案 |
| 2000 万 ~ 5000 万 | 危险 | ALTER TABLE 可能锁表数小时，查询性能显著下降 |
| > 5000 万 | 必须拆分 | B+ Tree 层级增加（3 层 → 4 层），随机 IO 增多 |

> **注意：** 这些数字不是绝对的，取决于行宽（每行数据的字节数）。一张只有 3 个 INT 列的表，5000 万行可能完全没问题；一张有 20 个 VARCHAR(255) 列的表，500 万行就可能很慢。核心指标是 **B+ Tree 的高度和单页存储的行数**。

**B+ Tree 层级与行数的关系：**

```
InnoDB 默认页大小 = 16KB

假设主键为 BIGINT (8 bytes)，指针 6 bytes，每个非叶子节点可存：
  16384 / (8 + 6) ≈ 1170 个指针

假设每行数据 200 bytes，每个叶子节点可存：
  16384 / 200 ≈ 80 行

B+ Tree 层级:
  2 层: 1170 × 80 = 93,600 行
  3 层: 1170 × 1170 × 80 ≈ 1 亿行
  4 层: 1170 × 1170 × 1170 × 80 ≈ 1280 亿行

  层级    磁盘 IO 次数（最坏情况）
  ─────   ──────────────────────
  2 层    2 次随机 IO
  3 层    3 次随机 IO（绝大多数场景）
  4 层    4 次随机 IO（性能下降明显）
```

**磁盘空间的红线：**

| 指标 | 安全 | 预警 | 危险 |
|------|------|------|------|
| 磁盘使用率 | < 60% | 60% ~ 80% | > 80% |
| 单表数据文件大小 | < 10GB | 10GB ~ 50GB | > 50GB |
| binlog 空间增长 | 日增 < 总空间 5% | 5% ~ 10% | > 10% |

**为什么磁盘 80% 是红线？**

- InnoDB 需要临时空间做排序、ALTER TABLE 等操作
- binlog、relay log、undo log 需要空间
- 磁盘满了会导致 MySQL 直接崩溃（无法写 redo log），数据可能损坏

```sql
-- 查看各表的数据量和大小
SELECT table_name,
       table_rows,
       ROUND(data_length / 1024 / 1024, 2)  AS data_mb,
       ROUND(index_length / 1024 / 1024, 2) AS index_mb,
       ROUND((data_length + index_length) / 1024 / 1024, 2) AS total_mb
FROM information_schema.tables
WHERE table_schema = 'your_database'
ORDER BY data_length + index_length DESC;
```

## 二、如何通过压测获得这些数字

### 2.1 压测的目的

压测不是为了"看系统能扛多少"，而是为了找到 **拐点**——性能开始非线性下降的那个点。

```
  响应时间
  (ms)
   │
   │                              ╱  ← 拐点之后：响应时间指数级上升
   │                            ╱
   │                          ╱
   │                        ╱
   │          ─────────────╱  ← 拐点：这就是你的极限
   │         ╱
   │        ╱
   │ ──────╱  ← 线性增长阶段
   │
   └──────────────────────────── QPS / 并发数
```

### 2.2 压测工具选择

| 工具 | 适用场景 | 特点 |
|------|----------|------|
| sysbench | 数据库基准测试 | 专业、可重复、支持 OLTP 标准场景 |
| mysqlslap | 快速验证 | MySQL 自带，简单但功能有限 |
| BenchmarkSQL | TPC-C 模拟 | 模拟真实事务负载 |
| 自研脚本 + JMeter | 业务级压测 | 贴合真实业务场景 |

### 2.3 sysbench 压测实操

**第一步：准备测试数据**

```bash
# 创建测试数据库
mysql -e "CREATE DATABASE sbtest;"

# 准备 10 张表，每张 100 万行
sysbench oltp_read_write \
  --mysql-host=127.0.0.1 \
  --mysql-port=3306 \
  --mysql-user=root \
  --mysql-password=yourpassword \
  --mysql-db=sbtest \
  --tables=10 \
  --table-size=1000000 \
  prepare
```

**第二步：逐步增加并发，找到拐点**

```bash
# 从 8 并发开始，逐步翻倍
for threads in 8 16 32 64 128 256; do
  echo "=== Testing with $threads threads ==="
  sysbench oltp_read_write \
    --mysql-host=127.0.0.1 \
    --mysql-port=3306 \
    --mysql-user=root \
    --mysql-password=yourpassword \
    --mysql-db=sbtest \
    --tables=10 \
    --table-size=1000000 \
    --threads=$threads \
    --time=60 \
    --report-interval=10 \
    run
  echo ""
  sleep 10  # 每轮之间给数据库恢复时间
done
```

**第三步：分析压测结果**

```
典型的 sysbench 输出关键指标：

  并发数    QPS      P95 延迟(ms)    P99 延迟(ms)    CPU%
  ─────    ─────    ───────────    ───────────    ────
  8        12,000   3.5            5.2            25%
  16       22,000   4.1            6.8            45%
  32       35,000   5.8            12.3           65%
  64       42,000   12.5           35.7           82%   ← ⚠️ CPU 超过 70%
  128      38,000   45.2           120.3          95%   ← ❌ QPS 反而下降！
  256      25,000   180.5          520.8          99%   ← ❌ 系统崩溃边缘

  拐点在 32~64 并发之间
  安全极限：QPS ≈ 35,000，P95 < 10ms，CPU < 70%
```

### 2.4 压测注意事项

1. **在与生产环境相同规格的机器上压测**，否则数字没有参考价值
2. **压测数据量要接近生产**，空表和千万级表的表现完全不同
3. **压测时间至少 5 分钟**，太短无法暴露 Buffer Pool 缓存失效后的真实性能
4. **同时采集数据库指标**，光看客户端延迟不够，要看 CPU、IO、锁等待
5. **压测期间不要有其他负载**，确保结果可重复

## 三、报警阈值设置的最佳实践

### 3.1 分层报警模型

```
  ┌─────────────────────────────────────────────┐
  │              P0 - 致命 (立即响应)              │
  │  • Threads_running > CPU核心数 × 4            │
  │  • 磁盘使用率 > 90%                           │
  │  • 主从延迟 > 60s                             │
  │  • 连接池耗尽（等待队列 > 0 持续 30s）          │
  ├─────────────────────────────────────────────┤
  │              P1 - 严重 (15 分钟内响应)          │
  │  • CPU 持续 > 70% 超过 5 分钟                  │
  │  • 慢查询数 > 50/分钟                          │
  │  • 磁盘使用率 > 80%                           │
  │  • 主从延迟 > 10s                             │
  ├─────────────────────────────────────────────┤
  │              P2 - 预警 (工作时间处理)           │
  │  • CPU 持续 > 50% 超过 30 分钟                 │
  │  • 慢查询数 > 10/分钟                          │
  │  • 磁盘使用率 > 60%                           │
  │  • 单表行数超过 1000 万                        │
  └─────────────────────────────────────────────┘
```

### 3.2 报警规则设计原则

**原则一：报警必须可操作（Actionable）**

```
❌ 坏的报警：CPU 使用率 > 50%
  → 触发频繁，运维疲劳，最终被忽略

✅ 好的报警：CPU 使用率 > 70% 持续 5 分钟
  → 过滤了毛刺，触发时确实需要处理
```

**原则二：用持续时间过滤毛刺**

| 指标 | 阈值 | 持续时间 | 报警级别 |
|------|------|----------|----------|
| CPU% | > 70% | 5 min | P1 |
| CPU% | > 90% | 1 min | P0 |
| Threads_running | > 核心数 × 2 | 3 min | P1 |
| 慢查询 (>200ms) | > 10/min | 持续 2 个周期 | P1 |
| 磁盘使用率 | > 80% | 即时 | P1 |

**原则三：同一问题收敛为一条报警**

```
❌ 10 条慢查询 → 10 条报警 → 运维手忙脚乱
✅ 10 条慢查询 → 1 条报警（附带 Top 5 慢 SQL 列表）
```

**原则四：报警内容必须包含诊断信息**

```
❌ [P1] MySQL CPU 使用率 85%
✅ [P1] MySQL CPU 使用率 85% 持续 5min
   实例: db-prod-01 (8C32G)
   当前 QPS: 15,000 (基线: 8,000)
   Top 慢 SQL: SELECT * FROM orders WHERE create_time > '2024-01-01' (avg 2.3s, 执行 230次/min)
   Threads_running: 35 (正常: 8)
```

### 3.3 Prometheus + Grafana 报警示例

```yaml
# Prometheus 报警规则示例
groups:
  - name: mysql_alerts
    rules:
      # P0: 活跃线程过多
      - alert: MySQLThreadsRunningCritical
        expr: mysql_global_status_threads_running > on(instance)
              (mysql_info_schema_threads * 0 + 32)  # 假设 8 核，阈值 = 8 × 4
        for: 1m
        labels:
          severity: critical
        annotations:
          summary: "MySQL 活跃线程过多: {{ $value }}"
          runbook: "https://wiki.internal/runbook/mysql-threads-running"

      # P1: CPU 持续过高
      - alert: MySQLCPUHigh
        expr: rate(process_cpu_seconds_total{job="mysqld"}[5m]) * 100 > 70
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "MySQL CPU 使用率 {{ $value }}% 持续超过 5 分钟"

      # P1: 磁盘空间不足
      - alert: MySQLDiskSpaceLow
        expr: (1 - node_filesystem_avail_bytes{mountpoint="/data"}
               / node_filesystem_size_bytes{mountpoint="/data"}) * 100 > 80
        for: 0m
        labels:
          severity: warning
        annotations:
          summary: "MySQL 数据盘使用率 {{ $value }}%"

      # P1: 慢查询过多
      - alert: MySQLSlowQueries
        expr: rate(mysql_global_status_slow_queries[1m]) > 0.8  # 约 50/min
        for: 2m
        labels:
          severity: warning
        annotations:
          summary: "慢查询频率: {{ $value }}/秒"
```

## 四、实战：从零建立一个项目的数据库极限档案

### 4.1 模板

每个项目/数据库实例应该维护一份极限档案：

```markdown
## 数据库极限档案 - 订单服务

### 实例信息
- 实例规格：8C 32G，500GB SSD
- MySQL 版本：8.0.35
- 存储引擎：InnoDB，innodb_buffer_pool_size = 24G

### 压测基线（2024-03-15）
- 最大安全 QPS：35,000（混合读写，读写比 7:3）
- P95 延迟上限：10ms
- P99 延迟上限：30ms
- CPU 安全上限：70%
- 最大安全并发连接：48（Threads_running）

### 容量规划
| 表名 | 当前行数 | 月增长量 | 预计到达红线时间 |
|------|----------|----------|------------------|
| orders | 1200 万 | 150 万/月 | 2024-09 (2000万) |
| order_items | 3500 万 | 500 万/月 | 2024-06 (5000万) ← 紧急 |
| payments | 800 万 | 100 万/月 | 2025-02 (2000万) |

### 报警配置
| 指标 | P2 阈值 | P1 阈值 | P0 阈值 |
|------|---------|---------|---------|
| CPU% | >50% 30min | >70% 5min | >90% 1min |
| Threads_running | >16 | >32 | >48 |
| 慢查询/分 | >10 | >50 | >100 |
| 磁盘使用率 | >60% | >80% | >90% |
```

### 4.2 维护节奏

| 频率 | 动作 |
|------|------|
| 每周 | 检查慢查询 Top 10，确认是否有新增 |
| 每月 | 更新各表行数和增长趋势 |
| 每季度 | 重新压测，更新基线数字 |
| 每次大版本上线前 | 全链路压测，验证新 SQL 不超过红线 |

---

## 总结

```
量化极限 = 找到拐点 + 设定红线 + 建立报警 + 持续更新

  耗时红线 → 单条 SQL < 200ms（OLTP）
  算力红线 → CPU < 70%
  并发红线 → Threads_running < 核心数 × 2
  容量红线 → 单表 < 2000 万行，磁盘 < 80%

  不是拍脑袋定的，是压测出来的。
  不是定一次就完的，是持续更新的。
```
