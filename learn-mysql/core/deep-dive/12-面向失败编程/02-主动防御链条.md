# 主动防御链条

## 核心理念

数据库故障不是"运气不好"，而是防御链条上某一环失守的必然结果。一条烂 SQL 从开发者键盘敲出到击穿生产数据库，中间至少经过 4 个阶段——每个阶段都有机会拦截它。

```
研发阶段        测试阶段        上线阶段        运维阶段
  │               │               │               │
  ▼               ▼               ▼               ▼
SQL 静态扫描    全链路压测      超时熔断        慢查询报警
代码 Review    慢查询基线对比   Kill 慢查询      值班响应
  │               │               │               │
  ▼               ▼               ▼               ▼
 成本最低        成本中等        成本较高        成本最高
 拦截率最高      验证最充分      止血最快        兜底最后

越早拦截，代价越小。到了运维阶段才发现，你已经在灭火了。
```

## 一、研发阶段：把问题消灭在 IDE 里

### 1.1 SQL 静态扫描

**什么是 SQL 静态扫描？**

在 SQL 执行之前，通过语法分析和规则匹配，自动检测潜在问题。类似于代码的 lint 工具，但针对的是 SQL。

**主流工具对比：**

| 工具 | 定位 | 核心能力 | 接入方式 |
|------|------|----------|----------|
| Yearning | SQL 审核平台 | DDL/DML 审核、工单流程、权限管理 | Web 平台，集成 CI/CD |
| SQLAdvisor（美团） | SQL 优化建议 | 基于 MySQL 源码解析，给出索引建议 | 命令行工具 |
| SQLE（爱可生） | SQL 审核平台 | 规则丰富、支持多数据库 | Web 平台 |
| Soar（小米） | SQL 优化评分 | 对 SQL 打分（0-100），给出优化建议 | 命令行工具 |
| pt-query-digest | 慢查询分析 | 解析慢查询日志，统计分析 | 命令行工具 |

**Soar 使用示例：**

```bash
# 安装
go install github.com/XiaoMi/soar@latest

# 分析一条 SQL
echo "SELECT * FROM orders WHERE user_id = 123 ORDER BY create_time DESC" | \
  soar -online-dsn "root:password@tcp(127.0.0.1:3306)/order_db"

# 输出示例：
# ★ ★ ★ ☆ ☆  评分: 55
#
# ■ SELECT *
#   建议: 不要使用 SELECT *，应该明确指定需要的列
#   影响: 增加网络传输、无法使用覆盖索引
#
# ■ 缺少 LIMIT
#   建议: 对于可能返回大量数据的查询，添加 LIMIT 限制
#   影响: 可能返回大量数据导致内存溢出或网络拥塞
```

**应该检查的规则清单：**

| 规则 | 严重级别 | 说明 |
|------|----------|------|
| 禁止 SELECT * | ERROR | 必须明确列名 |
| 禁止无 WHERE 的 UPDATE/DELETE | ERROR | 防止全表更新/删除 |
| WHERE 条件必须命中索引 | WARNING | 通过 EXPLAIN 验证 |
| 禁止在 WHERE 中对索引列使用函数 | ERROR | 导致索引失效 |
| JOIN 表数不超过 3 张 | WARNING | 过多 JOIN 导致执行计划不稳定 |
| 新建表必须有主键 | ERROR | InnoDB 无主键会使用隐藏 ROW_ID，性能差 |
| 索引数量不超过 5 个 | WARNING | 过多索引影响写入性能 |
| 新增字段必须有默认值 | WARNING | 避免 ALTER TABLE 触发全表重写 |
| 禁止使用 FORCE INDEX | WARNING | 写死执行计划，后续维护困难 |

### 1.2 代码 Review 中的 SQL 质量检查

**Review 清单——每个包含 SQL 变更的 PR 必须检查：**

**1) EXPLAIN 截图/输出必须附在 PR 中**

```sql
-- │ Extra      │ 无 temporary │ Using temporary（临时表） │
-- └────────────┴──────────┴────────────────────────────┘
```

**2) 数据量评估**

```
Review 问题模板：

Q: 这张表当前有多少行？月增长多少？
Q: 这条 SQL 在百万级/千万级数据量下的 EXPLAIN 结果如何？
Q: 是否需要分页？如果返回行数超过 1000 行怎么办？
Q: 有没有用到 OR？能否用 UNION ALL 替代？
```

**3) 事务范围检查**

```java
// ❌ 事务中包含了不必要的操作
@Transactional
public void processOrder(Long orderId) {
    Order order = orderDao.findById(orderId);    // DB 操作
    PayResult result = payService.pay(order);     // RPC 调用（可能耗时数秒）
    order.setStatus("PAID");
    orderDao.update(order);                       // DB 操作
}
// 问题：RPC 调用期间一直持有数据库连接和事务锁

// ✅ 缩小事务范围
public void processOrder(Long orderId) {
    Order order = orderDao.findById(orderId);     // 事务外读取
    PayResult result = payService.pay(order);      // RPC 调用

    // 只有真正需要事务的部分才开事务
    transactionTemplate.execute(status -> {
        order.setStatus("PAID");
        orderDao.update(order);
        orderLogDao.insert(new OrderLog(orderId, "PAID"));
        return null;
    });
}
```

**4) 是否存在 N+1 查询**

```java
// ❌ 典型的 N+1 问题
List<Order> orders = orderDao.findByUserId(userId);  // 1 次查询
for (Order order : orders) {
    // 每个订单再查一次商品 → N 次查询
    List<OrderItem> items = orderItemDao.findByOrderId(order.getId());
    order.setItems(items);
}
// 如果有 100 个订单 → 1 + 100 = 101 次查询

// ✅ 用 IN 批量查询
List<Order> orders = orderDao.findByUserId(userId);  // 1 次查询
List<Long> orderIds = orders.stream().map(Order::getId).collect(toList());
// 1 次批量查询
List<OrderItem> allItems = orderItemDao.findByOrderIds(orderIds);
// 内存中 group by
Map<Long, List<OrderItem>> itemMap = allItems.stream()
    .collect(groupingBy(OrderItem::getOrderId));
orders.forEach(o -> o.setItems(itemMap.getOrDefault(o.getId(), emptyList())));
// 总共只有 2 次查询
```

## 二、测试阶段：用压力验证你的信心

### 2.1 全链路压测

**什么是全链路压测？**

不是单接口压测，而是模拟真实用户行为，同时对所有关联服务施压。因为单接口压测可能遗漏的问题：

```
单接口压测                     全链路压测
┌───────┐                    ┌───────┐
│订单接口│ ← 只压这个          │下单   │ ← 同时压
└───┬───┘                    └───┬───┘
    │                            │
    ▼                            ▼
┌───────┐                    ┌───────┐
│库存接口│ ← 没压，没问题      │扣库存  │ ← 发现锁竞争
└───┬───┘                    └───┬───┘
    │                            │
    ▼                            ▼
┌───────┐                    ┌───────┐
│支付接口│ ← 没压，没问题      │扣款    │ ← 发现连接池耗尽
└───────┘                    └───────┘
```

**全链路压测的关键步骤：**

| 步骤 | 说明 | 注意事项 |
|------|------|----------|
| 1. 构造压测数据 | 影子表/影子库，或打标识的压测数据 | 数据量必须接近生产 |
| 2. 流量录制 | 从生产环境录制真实流量 | 注意脱敏 |
| 3. 流量回放 | 按倍率回放（1x、2x、5x、10x） | 逐步加压，不要直接打满 |
| 4. 监控采集 | 同时采集所有服务和数据库指标 | 关注级联效应 |
| 5. 结果分析 | 找到瓶颈点和拐点 | 重点看 P99 而非平均值 |

### 2.2 慢查询基线对比

**基线的含义：** 用当前版本的慢查询表现作为基准，新版本上线前必须与基线对比。

**建立基线的方法：**

```sql
-- 1. 开启 performance_schema 的 statement digest 统计
-- (MySQL 8.0 默认开启)

-- 2. 导出当前版本的 SQL 基线
SELECT digest,
       digest_text,
       count_star        AS exec_count,
       ROUND(avg_timer_wait / 1000000000, 2)  AS avg_ms,
       ROUND(quantile_95  / 1000000000, 2)    AS p95_ms,
       ROUND(quantile_99  / 1000000000, 2)    AS p99_ms,
       sum_rows_examined  AS total_rows_scanned,
       sum_rows_sent      AS total_rows_returned
FROM performance_schema.events_statements_summary_by_digest
WHERE schema_name = 'order_db'
  AND count_star > 100  -- 只关注高频 SQL
ORDER BY avg_timer_wait DESC;

-- 3. 保存为基线文件（JSON/CSV）
-- 4. 新版本压测后，与基线对比
```

**对比时关注的指标：**

```
对比维度              合格标准                     不合格动作
──────────          ────────────                 ──────────
avg_ms 变化          新值 < 旧值 × 1.2（20%以内）  需优化后重测
p99_ms 变化          新值 < 旧值 × 1.5             需优化后重测
rows_examined 变化   新值 < 旧值 × 2               检查索引是否失效
新增慢 SQL           不应有新增 > 200ms 的 SQL      必须优化
消失的 SQL           确认是功能下线，不是漏测        检查测试覆盖率
```

**自动化对比脚本框架（Python 伪代码）：**

```python
def compare_baselines(old_baseline, new_baseline, thresholds):
    """对比两个版本的 SQL 性能基线"""
    issues = []

    for digest, new_stats in new_baseline.items():
        old_stats = old_baseline.get(digest)

        if old_stats is None:
            # 新增的 SQL
            if new_stats['p95_ms'] > 200:
                issues.append({
                    'type': 'NEW_SLOW_SQL',
                    'severity': 'ERROR',
                    'sql': new_stats['digest_text'],
                    'p95_ms': new_stats['p95_ms']
                })
            continue

        # 性能退化检查
        if new_stats['avg_ms'] > old_stats['avg_ms'] * thresholds['avg_ratio']:
            issues.append({
                'type': 'PERFORMANCE_REGRESSION',
                'severity': 'WARNING',
                'sql': new_stats['digest_text'],
                'old_avg_ms': old_stats['avg_ms'],
                'new_avg_ms': new_stats['avg_ms'],
                'change': f"+{((new_stats['avg_ms']/old_stats['avg_ms'])-1)*100:.0f}%"
            })

    return issues
```

### 3.1 超时熔断

**超时控制的三层防线：**

```
┌──────────────────────────────────────────────────┐
│  第 1 层：应用层超时（最重要）                       │
│  connectTimeout = 3s    建立连接超时                │
│  socketTimeout  = 5s    等待数据超时（读写超时）       │
│  queryTimeout   = 3s    单条 SQL 执行超时            │
├──────────────────────────────────────────────────┤
│  第 2 层：连接池超时                                │
│  connectionTimeout = 3s  从连接池借连接的等待时间      │
│  maxLifetime       = 30min  连接最大存活时间          │
│  idleTimeout       = 10min  空闲连接超时回收          │
├──────────────────────────────────────────────────┤
│  第 3 层：数据库层超时                              │
│  wait_timeout        = 300s   空闲连接超时            │
│  max_execution_time  = 10s    SQL 最大执行时间        │
│  lock_wait_timeout   = 5s     锁等待超时              │
│  innodb_lock_wait_timeout = 5s InnoDB 行锁等待超时    │
└──────────────────────────────────────────────────┘
```

**HikariCP 配置示例（Java / Spring Boot）：**

```yaml
spring:
  datasource:
    hikari:
      # 连接池大小
      maximum-pool-size: 20
      minimum-idle: 20          # HikariCP 推荐与 maximum-pool-size 相同

      # 超时控制
      connection-timeout: 3000  # 3s，从连接池获取连接的等待时间
      max-lifetime: 1800000     # 30min，连接最大存活时间
      idle-timeout: 600000      # 10min，空闲连接超时

      # JDBC URL 中的超时参数

        ?connectTimeout=3000
        &socketTimeout=5000
        &useSSL=false
        &characterEncoding=utf8mb4
```

**熔断机制的实现思路（伪代码）：**

```java
/**
 * 数据库熔断器
 * 当数据库异常率超过阈值时，自动熔断，拒绝新请求
 * 避免异常请求继续打击已经不健康的数据库
 */
public class DBCircuitBreaker {
    private final AtomicInteger failCount = new AtomicInteger(0);
    private final AtomicInteger totalCount = new AtomicInteger(0);
    private volatile State state = State.CLOSED;  // CLOSED=正常, OPEN=熔断, HALF_OPEN=试探

    // 每次 SQL 执行前检查熔断状态
    public void checkState() {
        if (state == State.OPEN) {
            throw new CircuitBreakerOpenException("数据库熔断中，请稍后重试");
        }
    }

    // SQL 执行失败时记录
    public void recordFailure() {
        failCount.incrementAndGet();
        totalCount.incrementAndGet();
        if (getFailureRate() > 0.5) {  // 失败率 > 50%
            state = State.OPEN;
            // 10 秒后切换到半开状态，允许少量请求试探
            scheduler.schedule(() -> state = State.HALF_OPEN, 10, SECONDS);
        }
    }

    // SQL 执行成功时记录
    public void recordSuccess() {
        totalCount.incrementAndGet();
        if (state == State.HALF_OPEN) {
            // 半开状态下执行成功 → 恢复
            failCount.set(0);
            totalCount.set(0);
            state = State.CLOSED;
        }
    }
}
```

### 3.2 Kill 慢查询的开销与副作用

**`KILL` 命令的真相：**

```sql
-- 查看慢查询
SELECT id, user, host, db, command, time, state, info
FROM information_schema.processlist
WHERE command != 'Sleep'
  AND time > 10  -- 执行超过 10 秒
ORDER BY time DESC;

-- 终止指定连接
KILL <connection_id>;       -- 终止连接（断开）
KILL QUERY <connection_id>; -- 只终止当前 SQL，保持连接
```

**KILL 不是免费的，它有代价：**

| 场景 | KILL 后的代价 | 严重程度 |
|------|-------------|----------|
| SELECT 查询 | 几乎无代价，立即终止 | 低 |
| UPDATE/DELETE 大量行 | 需要回滚已修改的数据，可能耗时很久 | 高 |
| ALTER TABLE (copy 模式) | 需要清理临时表，可能占用大量磁盘空间 | 高 |
| 持有大量锁的事务 | 回滚期间锁不会释放，其他事务继续等待 | 高 |
| INSERT ... SELECT 大表 | 回滚 undo log 可能耗时等于甚至超过执行时间 | 高 |

**核心要理解的一点：**

```
KILL 一个正在执行的 DML（UPDATE/DELETE/INSERT），MySQL 不是"停下来"，
而是"撤回已做的工作"（rollback）。

例如：一条 UPDATE 已经修改了 500 万行中的 300 万行
KILL 后：MySQL 需要把这 300 万行改回去
这个回滚过程可能比原来的执行还慢，而且回滚期间：
  - 行锁不会释放
  - undo log 持续增长
  - CPU 和 IO 继续飙高

所以 KILL 不是万能药，有时候让它跑完反而比 KILL 更快。
```

**自动 Kill 慢查询的脚本：**

```bash
#!/bin/bash
# auto_kill_slow_queries.sh
# 自动 Kill 执行超过指定秒数的非系统查询

THRESHOLD=30  # 超过 30 秒的查询
MYSQL_CONN="mysql -u monitor_user -p'password' -h 127.0.0.1"

# 找到慢查询的 connection id
slow_queries=$($MYSQL_CONN -N -e "
  SELECT id
  FROM information_schema.processlist
  WHERE command = 'Query'
    AND time > $THRESHOLD
    AND user NOT IN ('system user', 'repl_user')
    AND info NOT LIKE '%processlist%'
")

for id in $slow_queries; do
  # 只 kill query，不断开连接
  echo "[$(date)] Killing query on connection $id"
  $MYSQL_CONN -e "KILL QUERY $id" 2>/dev/null

  # 记录被 kill 的 SQL（用于事后分析）
  $MYSQL_CONN -N -e "
    SELECT id, user, db, time, info
    FROM information_schema.processlist
    WHERE id = $id
  " >> /var/log/killed_queries.log 2>/dev/null
done
```

**决策流程——遇到慢查询时怎么决定是否 Kill：**

```python
# 报警聚合逻辑（Python 伪代码）
class SlowQueryAlertAggregator:
    """
    慢查询报警聚合器
    将相同指纹的慢查询聚合为一条报警，避免报警轰炸
    """

    def __init__(self, window_seconds=300):
        self.window = window_seconds  # 5 分钟聚合窗口
        self.buffer = defaultdict(list)

    def ingest(self, slow_query):
        """接收一条慢查询记录"""
        fingerprint = self.normalize(slow_query.sql)
        self.buffer[fingerprint].append(slow_query)

    def evaluate(self):
        """评估当前窗口，决定是否发报警"""
        alerts = []
        for fingerprint, queries in self.buffer.items():
            count = len(queries)
            avg_time = sum(q.query_time for q in queries) / count
            max_time = max(q.query_time for q in queries)
            total_rows = sum(q.rows_examined for q in queries)

            # 判断是否需要报警
            if count > 50 or max_time > 5.0 or avg_time > 1.0:
                severity = 'P0' if max_time > 10.0 else 'P1'
                alerts.append({
                    'severity': severity,
                    'fingerprint': fingerprint,
                    'sample_sql': queries[0].sql,
                    'count': count,
                    'avg_time_ms': round(avg_time * 1000),
                    'max_time_ms': round(max_time * 1000),
                    'total_rows_examined': total_rows,
                    'affected_hosts': list(set(q.host for q in queries)),
                })

        self.buffer.clear()
        return alerts
```

### 4.3 值班响应 SOP（Standard Operating Procedure）

**收到数据库报警后的标准处理流程：**

```
收到报警
  │
  ▼
Step 1: 确认影响范围（30 秒内）
  • 哪个实例？主库还是从库？
  • 业务是否已受影响？（看错误率、延迟指标）
  • 是否在变更窗口内？（是否有上线操作）
  │
  ▼
Step 2: 快速诊断（2 分钟内）
  │
  ├── CPU 高？
  │   └─→ SHOW PROCESSLIST 看 Threads_running
  │       └─→ 找到耗 CPU 最高的 SQL
  │
  ├── 连接数高？
  │   └─→ SHOW STATUS LIKE 'Threads_%'
  │       └─→ 检查是否有连接泄漏或慢查询堆积
  │
  ├── 磁盘满？
  │   └─→ df -h && du -sh /data/mysql/*
  │       └─→ 检查 binlog、临时文件、大表
  │
  └── 主从延迟？
      └─→ SHOW SLAVE STATUS\G
          └─→ 检查 Seconds_Behind_Master 和 SQL_thread
  │
  ▼
Step 3: 止血操作（5 分钟内）
  │
  ├── Kill 慢查询（仅限 SELECT 或影响行数少的 DML）
  ├── 切换到从库（如果主库不可用）
  ├── 限流 / 降级（通过配置中心关闭非核心功能）
  └── 回滚变更（如果是上线导致的）
  │
  ▼
Step 4: 根因分析（事后）
  • 为什么 SQL 变慢？索引失效？数据量增长？
  • 为什么没有在研发/测试阶段拦截？
  • 防御链条哪一环失守了？
  • 产出改进措施和时间表
```

**快速诊断的 SQL 命令速查：**

```sql
-- 1. 看当前在跑什么
SHOW FULL PROCESSLIST;

-- 2. 看 InnoDB 状态（锁、事务、IO）
SHOW ENGINE INNODB STATUS\G

-- 3. 看关键状态指标
SHOW GLOBAL STATUS WHERE Variable_name IN (
  'Threads_connected', 'Threads_running',
  'Slow_queries', 'Questions',
  'Innodb_row_lock_waits', 'Innodb_row_lock_time_avg',
  'Created_tmp_tables', 'Created_tmp_disk_tables'
);

-- 4. 看锁等待
SELECT * FROM information_schema.innodb_lock_waits;

-- 5. 看长事务
SELECT trx_id, trx_state, trx_started,
       TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS duration_sec,
       trx_rows_locked, trx_rows_modified, trx_query
FROM information_schema.innodb_trx
ORDER BY trx_started ASC;

-- 6. 看表空间使用
SELECT table_schema,
       ROUND(SUM(data_length + index_length) / 1024 / 1024 / 1024, 2) AS size_gb
FROM information_schema.tables
GROUP BY table_schema
ORDER BY size_gb DESC;
```
