# 顶级开发者的呼吸习惯

## 什么是"呼吸习惯"

不需要思考就会做的事情，叫呼吸习惯。顶级开发者写数据库相关代码时，以下几件事是条件反射——不是"知道"，而是"做不到就浑身不舒服"。

---

## 一、拒绝 SELECT *

### 1.1 SELECT * 的三重代价

**代价一：多余列增加网络传输**

```sql
-- 假设 orders 表有 30 个列，但你只需要 3 个
SELECT * FROM orders WHERE user_id = 10086;
-- 返回 30 列 × 1000 行 = 假设每行 2KB → 传输 2MB

SELECT order_id, amount, status FROM orders WHERE user_id = 10086;
-- 返回 3 列 × 1000 行 = 假设每行 50B → 传输 50KB

-- 网络传输量差了 40 倍
```

看一个更具体的计算：

```
假设 orders 表结构：
  order_id      BIGINT        8B
  user_id       BIGINT        8B
  amount        DECIMAL(10,2) 5B
  status        VARCHAR(20)   ~10B
  address       VARCHAR(500)  ~200B    ← 你不需要
  remark        TEXT          ~500B    ← 你不需要
  extra_json    JSON          ~1000B   ← 你不需要
  ... (其他 20+ 列)

  SELECT * : 每行 ≈ 2000B
  SELECT order_id, amount, status : 每行 ≈ 25B

  查询 10,000 行：
    SELECT *     : 20MB 网络传输 + 20MB 应用内存
    精确列       : 250KB 网络传输 + 250KB 应用内存
```

**代价二：无法利用覆盖索引（Covering Index）**

```sql
-- 假设有索引: idx_user_status (user_id, status, amount)

-- ❌ SELECT * 无法覆盖索引 → 必须回表
EXPLAIN SELECT * FROM orders WHERE user_id = 10086 AND status = 'PAID';
-- type: ref, Extra: NULL (需要回表读取完整行)

-- ✅ 精确列可以覆盖索引 → 不需要回表
EXPLAIN SELECT status, amount FROM orders WHERE user_id = 10086 AND status = 'PAID';
-- type: ref, Extra: Using index (直接从索引返回，不需要回表)
```

**覆盖索引 vs 回表的性能差异：**

```
覆盖索引（Using index）：
  B+ Tree 索引 → 直接返回数据
  只需要读索引页，不需要读数据页
  IO 次数 = B+ Tree 高度（通常 2~3 次）

回表：
  B+ Tree 索引 → 拿到主键 → 再去主键索引找完整行
  需要读索引页 + 数据页
  IO 次数 = B+ Tree 高度 + 1（最好情况）

  如果查询 1000 行：
    覆盖索引：可能只需要几次顺序 IO（索引页连续）
    回表：1000 次随机 IO（数据页分散）→ 性能差 10~100 倍
```

**代价三：DDL 变更的隐形风险**

```sql
-- 当前代码：SELECT * FROM orders → 返回 30 列
-- 某天 DBA 加了一列：ALTER TABLE orders ADD COLUMN internal_note TEXT;

-- SELECT * 自动返回 31 列，而你的代码可能：
-- 1. ORM 映射出错（新列没有对应字段）
-- 2. 缓存 key 计算变了（缓存全部失效）
-- 3. 序列化大小变了（触发网络超时）
-- 4. 前端展示了不应该暴露的内部备注

-- 如果你写的是 SELECT order_id, amount, status → 不受影响
```

### 1.2 唯一合理使用 SELECT * 的场景

| 场景 | 是否可以用 SELECT * | 原因 |
|------|---------------------|------|
| 日常查询调试（命令行） | ✅ | 临时使用，不入代码 |
| 数据迁移/ETL 脚本 | ✅ | 需要所有列，且通常不走索引 |
| 业务代码 | ❌ | 必须明确列名 |
| ORM 的默认查询 | ❌ | 应覆盖默认行为，指定列 |

## 二、禁止循环查库（N+1 问题）

### 2.1 N+1 问题的本质

```
N+1 = 1 次查询获取列表 + N 次查询获取详情

  查询 100 个订单的商品：
  ┌────────────────────────────────────────────┐
  │ SELECT * FROM orders WHERE user_id = 123   │  ← 第 1 次
  │                                            │
  │ SELECT * FROM items WHERE order_id = 1001  │  ← 第 2 次
  │ SELECT * FROM items WHERE order_id = 1002  │  ← 第 3 次
  │ SELECT * FROM items WHERE order_id = 1003  │  ← 第 4 次
  │ ...                                        │
  │ SELECT * FROM items WHERE order_id = 1100  │  ← 第 101 次
  └────────────────────────────────────────────┘

  总共 101 次数据库往返
  每次往返 = 网络延迟 + SQL 解析 + 执行 + 结果传输
  假设每次 2ms → 总共 202ms

  用 IN 批量查询：
  ┌────────────────────────────────────────────┐
  │ SELECT * FROM orders WHERE user_id = 123   │  ← 第 1 次
  │                                            │
  │ SELECT * FROM items                         │  ← 第 2 次
  │   WHERE order_id IN (1001,1002,...,1100)    │
  └────────────────────────────────────────────┘

  总共 2 次数据库往返
  假设每次 3ms（IN 查询稍慢） → 总共 6ms

  性能差距：202ms vs 6ms = 33 倍
```

### 2.2 各种场景的解决方案

**场景一：一对多关联查询**

```java
// ❌ N+1
List<Order> orders = orderDao.findByUserId(userId);
for (Order order : orders) {
    List<OrderItem> items = itemDao.findByOrderId(order.getId());
    order.setItems(items);
}

// ✅ 批量 IN 查询 + 内存 group
List<Order> orders = orderDao.findByUserId(userId);
if (orders.isEmpty()) return orders;

List<Long> orderIds = orders.stream().map(Order::getId).toList();
Map<Long, List<OrderItem>> itemMap = itemDao.findByOrderIds(orderIds)
    .stream()
    .collect(Collectors.groupingBy(OrderItem::getOrderId));

orders.forEach(o -> o.setItems(itemMap.getOrDefault(o.getId(), List.of())));
```

对应的 SQL：

```sql
-- ❌ 循环中的单条查询
SELECT item_id, product_name, quantity, price
FROM order_items
WHERE order_id = 1001;

-- ✅ 批量 IN 查询
SELECT item_id, order_id, product_name, quantity, price
FROM order_items
WHERE order_id IN (1001, 1002, 1003, ..., 1100);
```

**场景二：IN 列表过大怎么办？**

MySQL 没有硬性限制 IN 列表的大小，但实践中需要注意：

```java
/**
 * 分批查询工具方法
 * 将大的 IN 列表拆分为多个小批次执行，避免 SQL 过长或查询过慢
 *
 * @param ids      完整的 ID 列表
 * @param batchSize 每批大小，建议 500~1000
 * @param queryFn  单批查询函数
 * @return 合并后的完整结果
 */
public static <ID, R> List<R> batchQuery(
        List<ID> ids, int batchSize, Function<List<ID>, List<R>> queryFn) {
    if (ids == null || ids.isEmpty()) {
        return List.of();
    }
    List<R> result = new ArrayList<>();
    for (int i = 0; i < ids.size(); i += batchSize) {
        List<ID> batch = ids.subList(i, Math.min(i + batchSize, ids.size()));
        result.addAll(queryFn.apply(batch));
    }
    return result;
}

// 使用方式
List<OrderItem> items = batchQuery(orderIds, 500, itemDao::findByOrderIds);
```

**场景三：MyBatis 中如何避免 N+1**

```xml
<!-- ❌ MyBatis 嵌套查询（会产生 N+1） -->
<resultMap id="orderWithItems" type="Order">
    <id column="order_id" property="id"/>
    <collection property="items" column="order_id"
                select="com.example.dao.ItemDao.findByOrderId"/>
    <!-- 每个 Order 都会触发一次 findByOrderId 查询 -->
</resultMap>

<!-- ✅ MyBatis 嵌套结果（一次 JOIN 查询） -->
<resultMap id="orderWithItems" type="Order">
    <id column="order_id" property="id"/>
    <result column="amount" property="amount"/>
    <collection property="items" ofType="OrderItem">
        <id column="item_id" property="id"/>
        <result column="product_name" property="productName"/>
        <result column="quantity" property="quantity"/>
    </collection>
</resultMap>

<select id="findOrdersWithItems" resultMap="orderWithItems">
    SELECT o.order_id, o.amount,
           i.item_id, i.product_name, i.quantity
    FROM orders o
    LEFT JOIN order_items i ON o.order_id = i.order_id
    WHERE o.user_id = #{userId}
</select>
```

### 2.3 如何检测 N+1 问题

```java
// 方法一：开启 SQL 日志，观察重复模式
// application.yml
// logging:
//   level:
//     com.example.dao: DEBUG  # 打印所有 SQL
// 如果看到大量结构相同、只是参数不同的 SQL → N+1

// 方法二：在测试中统计 SQL 执行次数
// 使用 p6spy 或自定义 JDBC 拦截器
public class SqlCounter implements StatementInterceptor {
    private static final ThreadLocal<AtomicInteger> counter =
        ThreadLocal.withInitial(AtomicInteger::new);

    public static int getCount() { return counter.get().get(); }
    public static void reset()   { counter.get().set(0); }

    @Override
    public void beforeQuery(String sql) {
        counter.get().incrementAndGet();
    }
}

// 在测试中使用
@Test
void testNoNPlusOne() {
    SqlCounter.reset();
    List<Order> orders = orderService.findOrdersWithItems(userId);
    // 期望最多 2 次查询（一次查订单，一次查商品）
    assertThat(SqlCounter.getCount()).isLessThanOrEqualTo(2);
}
```

## 三、强超时控制

### 3.1 为什么超时控制是"呼吸级"要求

```
没有超时控制的代码就像没有安全绳的攀岩者：
大多数时候不会有问题，但一旦出问题就是致命的。

一个没有超时的数据库调用：
  1. 数据库变慢（如锁等待、磁盘 IO 抖动）
  2. SQL 执行时间从 10ms 变成 30s
  3. 应用线程一直等待 → 线程池耗尽
  4. 新请求无法处理 → 服务不可用
  5. 上游服务也超时 → 级联故障
  6. 整个系统雪崩

整个过程可能只需要 30 秒。
```

### 3.2 三个必须设置的超时参数

```
┌─────────────────────────────────────────────────────────┐
│                    超时参数三件套                          │
│                                                         │
│  connectTimeout          socketTimeout                  │
│  ┌──────────┐           ┌──────────────────────────┐   │
│  │建立 TCP   │           │等待数据库返回数据           │   │
│  │连接的超时  │           │（读写超时）                 │   │
│  │          │           │                          │   │
│  │建议: 3s   │           │建议: 5s（OLTP）            │   │
│  └──────────┘           └──────────────────────────┘   │
│                                                         │
│  statement_timeout / max_execution_time                  │
│  ┌──────────────────────────────────────────────────┐   │
│  │单条 SQL 在数据库端的最大执行时间                      │   │
│  │超过后数据库主动终止该 SQL                             │   │
│  │                                                  │   │
│  │MySQL: max_execution_time (毫秒级)                  │   │
│  │PostgreSQL: statement_timeout (毫秒级)              │   │
│  │建议: 10s（兜底，正常业务 SQL 应该远低于此值）          │   │
│  └──────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────┘
```

### 3.3 各语言/框架的超时配置

**Java + JDBC（直接连接）：**

```java
// JDBC URL 中设置超时
String url = "jdbc:mysql://db-host:3306/mydb"
    + "?connectTimeout=3000"     // 建立连接超时 3s
    + "&socketTimeout=5000";     // 读写超时 5s

// 代码中设置单条 SQL 超时
try (PreparedStatement ps = conn.prepareStatement(sql)) {
    ps.setQueryTimeout(3);  // 单位：秒。3 秒后超时
    ResultSet rs = ps.executeQuery();
}
```

**Java + HikariCP（连接池）：**

```yaml
# application.yml
spring:
  datasource:
    hikari:
      connection-timeout: 3000    # 从连接池获取连接的等待时间
      maximum-pool-size: 20       # 最大连接数
      minimum-idle: 20            # 最小空闲连接
      max-lifetime: 1800000       # 连接最大存活时间 30 分钟
      idle-timeout: 600000        # 空闲连接超时 10 分钟
      data-source-properties:
        connectTimeout: 3000      # TCP 连接超时
        socketTimeout: 5000       # 读写超时
```

**Go + database/sql：**

```go
import (
    "context"
    "database/sql"
    "time"

    _ "github.com/go-sql-driver/mysql"
)

// DSN 中设置连接和读写超时
dsn := "user:password@tcp(db-host:3306)/mydb?timeout=3s&readTimeout=5s&writeTimeout=5s"

db, err := sql.Open("mysql", dsn)
if err != nil {
    log.Fatal(err)
}

// 连接池配置
db.SetMaxOpenConns(20)          // 最大连接数
db.SetMaxIdleConns(20)          // 最大空闲连接数
db.SetConnMaxLifetime(30 * time.Minute) // 连接最大存活时间
db.SetConnMaxIdleTime(10 * time.Minute) // 空闲连接超时

// 每次查询使用 context 控制超时
ctx, cancel := context.WithTimeout(context.Background(), 3*time.Second)
defer cancel()

rows, err := db.QueryContext(ctx, "SELECT order_id, amount FROM orders WHERE user_id = ?", userId)
if err != nil {
    // 超时会返回 context.DeadlineExceeded
    log.Printf("query failed: %v", err)
    return
}
defer rows.Close()
```

**MySQL 服务端超时（兜底）：**

```sql
-- 对 SELECT 语句设置最大执行时间（MySQL 5.7.8+）
-- 超过此时间，MySQL 主动终止该查询
SET GLOBAL max_execution_time = 10000;  -- 10 秒

-- 对单条查询设置超时（MySQL 8.0 Hint 语法）
SELECT /*+ MAX_EXECUTION_TIME(3000) */
    order_id, amount, status
FROM orders
WHERE user_id = 10086;
-- 如果执行超过 3 秒，MySQL 会返回 ERROR 3024:
-- Query execution was interrupted, maximum statement execution time exceeded

-- 锁等待超时
SET GLOBAL innodb_lock_wait_timeout = 5;  -- 行锁等待最多 5 秒
SET GLOBAL lock_wait_timeout = 5;         -- MDL 锁等待最多 5 秒
```

### 3.4 超时配置的层次关系

```
  请求进入
      │
      ▼
  ┌───────────────────────────────┐
  │ HTTP 层超时（如 Nginx）         │  timeout = 30s
  │                               │  最外层兜底，防止请求无限等待
  └───────────────┬───────────────┘
                  │
      ▼
  ┌───────────────────────────────┐
  │ 应用层超时（如 Spring）         │  @Transactional(timeout=5)
  │                               │  业务层面的超时控制
  └───────────────┬───────────────┘
                  │
      ▼
  ┌───────────────────────────────┐
  │ 连接池超时（如 HikariCP）       │  connectionTimeout = 3s
  │                               │  获取连接的等待时间
  └───────────────┬───────────────┘
                  │
      ▼
  ┌───────────────────────────────┐
  │ JDBC 超时                      │  socketTimeout = 5s
  │                               │  网络层的读写超时
  └───────────────┬───────────────┘
                  │
      ▼
  ┌───────────────────────────────┐
  │ MySQL 服务端超时                │  max_execution_time = 10s
  │                               │  数据库层的兜底超时
  └───────────────────────────────┘

  原则：外层超时 > 内层超时
  确保内层超时先触发，外层超时作为兜底
```

## 四、分布式 Trace 日志审计

### 4.1 为什么要在链路追踪中标记 SQL

```
用户请求: GET /api/orders?userId=10086

  没有 SQL Trace:
  ┌─────────────────────────────────────────────┐
  │ [订单服务] GET /orders 响应时间: 850ms        │
  │                                             │
  │ ...发生了什么？不知道。                        │
  └─────────────────────────────────────────────┘

  有 SQL Trace:
  ┌─────────────────────────────────────────────┐
  │ [订单服务] GET /orders 响应时间: 850ms        │
  │                                             │
  │ ├─ [MySQL] SELECT order_id, amount...        │
  │ │  耗时: 5ms | 影响行: 50 | 索引: idx_user   │
  │ │                                           │
  │ ├─ [MySQL] SELECT item_id, product_name...   │
  │ │  耗时: 800ms | 影响行: 50000 | 索引: NONE  │  ← 问题在这！
  │ │                                           │
  │ └─ [Redis] GET user:10086:profile            │
  │    耗时: 2ms                                 │
  └─────────────────────────────────────────────┘
```

### 4.2 需要记录的 SQL 指标

| 指标 | 含义 | 为什么重要 |
|------|------|----------|
| SQL 文本（脱敏后的模板） | 执行了什么查询 | 定位问题 SQL |
| 执行耗时（ms） | 花了多长时间 | 判断是否为慢查询 |
| 影响行数 / 扫描行数 | 实际操作了多少数据 | 判断是否全表扫描 |
| 数据库实例 | 连接的哪个数据库 | 定位到具体实例 |
| 是否命中索引 | 查询是否走了索引 | 发现索引失效 |
| traceId | 请求链路标识 | 串联上下游调用 |
| spanId | 当前操作标识 | 定位具体操作 |

### 4.3 实现方式

**方式一：JDBC 拦截器（推荐，侵入性最低）**

```java
/**
 * SQL 链路追踪拦截器
 * 通过 JDBC Statement 拦截器自动记录每条 SQL 的执行信息
 * 无需修改业务代码
 */
public class SqlTraceInterceptor implements StatementInterceptorV2 {

    @Override
    public ResultSetInternalMethods preProcess(String sql,
            com.mysql.jdbc.Statement interceptedStatement,
            com.mysql.jdbc.Connection connection) {
        // 记录开始时间
        TraceContext.setStartTime(System.nanoTime());
        return null;
    }

    @Override
    public ResultSetInternalMethods postProcess(String sql,
            com.mysql.jdbc.Statement interceptedStatement,
            com.mysql.jdbc.Connection connection,
            ResultSetInternalMethods originalResultSet,
            int warningCount, boolean noIndexUsed, boolean noGoodIndexUsed) {

        long durationMs = (System.nanoTime() - TraceContext.getStartTime()) / 1_000_000;
        long affectedRows = interceptedStatement.getUpdateCount();

        // 获取当前链路信息
        Span currentSpan = Tracer.currentSpan();
        if (currentSpan != null) {
            currentSpan.tag("db.type", "mysql");
            currentSpan.tag("db.statement", truncateSql(sql, 1000));
            currentSpan.tag("db.duration_ms", String.valueOf(durationMs));
            currentSpan.tag("db.affected_rows", String.valueOf(affectedRows));
            currentSpan.tag("db.instance", connection.getHost() + ":" + connection.getPort());

            if (noIndexUsed) {
                currentSpan.tag("db.no_index", "true");
            }

            // 慢查询标记
            if (durationMs > 200) {
                currentSpan.tag("db.slow_query", "true");
                currentSpan.tag("db.slow_threshold_ms", "200");
            }
        }

        // 写入结构化日志
        log.info("SQL_TRACE traceId={} sql={} duration={}ms rows={} noIndex={}",
            TraceContext.getTraceId(),
            truncateSql(sql, 500),
            durationMs,
            affectedRows,
            noIndexUsed
        );

        return null;
    }

    /**
     * 截断过长的 SQL，避免日志膨胀
     *
     * @param sql    原始 SQL
     * @param maxLen 最大长度
     * @return 截断后的 SQL
     */
    private String truncateSql(String sql, int maxLen) {
        if (sql == null) return "";
        return sql.length() > maxLen ? sql.substring(0, maxLen) + "...[TRUNCATED]" : sql;
    }
}
```

**方式二：MyBatis 插件**

```java
/**
 * MyBatis SQL 追踪插件
 * 拦截所有 SQL 执行，自动记录到链路追踪系统
 */
@Intercepts({
    @Signature(type = Executor.class, method = "update",
               args = {MappedStatement.class, Object.class}),
    @Signature(type = Executor.class, method = "query",
               args = {MappedStatement.class, Object.class, RowBounds.class,
                       ResultHandler.class})
})
public class SqlTracePlugin implements Interceptor {

    @Override
    public Object intercept(Invocation invocation) throws Throwable {
        MappedStatement ms = (MappedStatement) invocation.getArgs()[0];
        Object parameter = invocation.getArgs()[1];

        // 获取 SQL
        BoundSql boundSql = ms.getBoundSql(parameter);
        String sql = boundSql.getSql().replaceAll("\\s+", " ").trim();

        // 创建 Span
        Span span = Tracer.nextSpan().name("mysql:" + ms.getId()).start();
        long startTime = System.currentTimeMillis();

        try {
            Object result = invocation.proceed();

            // 记录影响行数
            long affectedRows = 0;
            if (result instanceof List) {
                affectedRows = ((List<?>) result).size();
            } else if (result instanceof Integer) {
                affectedRows = (Integer) result;
            }

            span.tag("db.rows", String.valueOf(affectedRows));
            return result;

        } catch (Exception e) {
            span.tag("db.error", e.getMessage());
            throw e;

        } finally {
            long duration = System.currentTimeMillis() - startTime;
            span.tag("db.statement", sql.length() > 1000 ? sql.substring(0, 1000) : sql);
            span.tag("db.duration_ms", String.valueOf(duration));
            span.tag("db.mapper", ms.getId());
            span.finish();
        }
    }
}
```

### 4.4 基于 Trace 数据的自动化审计

```python
# SQL 审计规则引擎（Python 伪代码）
class SqlAuditEngine:
    """
    基于链路追踪数据，自动检测 SQL 问题
    定期从 Trace 存储（如 Elasticsearch、Jaeger）中拉取数据分析
    """

    # 审计规则定义
    RULES = [
        {
            'name': 'SLOW_QUERY',
            'condition': lambda span: span['duration_ms'] > 200,
            'severity': 'WARNING',
            'message': 'SQL 执行时间超过 200ms'
        },
        {
            'name': 'NO_INDEX',
            'condition': lambda span: span.get('db.no_index') == 'true',
            'severity': 'ERROR',
            'message': 'SQL 未使用索引'
        },
        {
            'name': 'LARGE_RESULT_SET',
            'condition': lambda span: int(span.get('db.rows', 0)) > 1000,
            'severity': 'WARNING',
            'message': '返回行数超过 1000，考虑分页'
        },
        {
            'name': 'N_PLUS_ONE',
            'condition': lambda span: False,  # 需要在 trace 级别检测
            'severity': 'ERROR',
            'message': '疑似 N+1 查询'
        },
    ]

    def detect_n_plus_one(self, trace):
        """
        检测 N+1 查询：同一个 traceId 下，相同模板的 SQL 出现次数过多

        参数：
            trace: 同一个 traceId 下的所有 SQL span 列表
        返回：
            检测到的 N+1 问题列表
        """
        sql_counter = Counter()
        for span in trace:
            # 将 SQL 中的具体参数替换为 ?，得到 SQL 模板
            template = re.sub(r"'[^']*'|\d+", "?", span['db.statement'])
            sql_counter[template] += 1

        issues = []
        for template, count in sql_counter.items():
            if count > 5:  # 同一模板出现超过 5 次
                issues.append({
                    'type': 'N_PLUS_ONE',
                    'severity': 'ERROR',
                    'sql_template': template,
                    'count': count,
                    'message': f'同一请求中相同 SQL 执行了 {count} 次，疑似 N+1'
                })
        return issues
```

## 五、连接池配置的黄金法则

### 5.1 公式

```
connections = (core_count * 2) + effective_spindle_count
```

这个公式来自 PostgreSQL 官方 wiki 和 HikariCP 作者 Brett Wooldridge 的文章。

**参数解释：**

| 参数 | 含义 | 示例 |
|------|------|------|
| core_count | 数据库服务器的 CPU 核心数（物理核心，非超线程） | 8 核 |
| effective_spindle_count | 有效磁盘轴数。SSD 通常按 1 计算（因为没有寻道等待） | SSD = 1 |

**计算示例：**

```
数据库服务器: 8 核 CPU + SSD
connections = (8 × 2) + 1 = 17

数据库服务器: 16 核 CPU + SSD
connections = (16 × 2) + 1 = 33

数据库服务器: 8 核 CPU + 4 块 HDD (RAID 10)
connections = (8 × 2) + 4 = 20
```

### 5.2 为什么这个公式有效

**直觉解释：**

```
CPU 核心数 × 2 的原因：
  每个核心在同一时刻只能执行一个线程
  但 SQL 执行涉及磁盘 IO，线程会在等待 IO 时让出 CPU
  所以每个核心可以同时服务约 2 个连接：
    一个在 CPU 上执行
    一个在等待 IO

effective_spindle_count 的原因：
  磁盘 IO 是瓶颈。每个磁盘轴可以并行服务一个 IO 请求
  SSD 虽然没有机械轴，但内部队列深度有限
  这个参数补偿了 IO 等待的额外并发能力
```

**反直觉但正确的事实：**

```
❌ "连接数越多越好"
✅ "连接数过多反而会变慢"

原因：
  假设 CPU = 8 核，连接数 = 200

  200 个连接同时执行 SQL：
  ├─ 8 个线程在 CPU 上执行
  ├─ ~20 个线程在等待 IO
  └─ ~172 个线程在竞争 CPU → context switch 开销
      每次 context switch ≈ 5~10μs
      172 个线程频繁切换 → CPU 时间浪费在切换上
      + 缓存失效（L1/L2 cache miss）
      + mutex 竞争（InnoDB 内部锁）

  结果：吞吐量反而低于 20 个连接的情况
```

### 5.3 多应用实例共享数据库时的计算

```
总连接数预算 = (core_count × 2) + effective_spindle_count

假设数据库 8 核 SSD，总预算 = 17

┌──────────────────────────────────────────────┐
│            数据库: 总预算 17 连接               │
├──────────────────────────────────────────────┤
│                                              │
│  应用实例 1    应用实例 2    应用实例 3          │
│  pool = 5     pool = 5     pool = 5          │
│                                              │
│  总计: 5 + 5 + 5 = 15 ≤ 17 ✅                │
├──────────────────────────────────────────────┤
│  预留 2 个连接给：                             │
│  • 监控系统（1 个）                            │
│  • DBA 运维操作（1 个）                        │
└──────────────────────────────────────────────┘

如果你有 10 个应用实例：
  每个实例的连接池 = 17 / 10 ≈ 1~2
  这显然不够用 → 说明需要：
    1. 升级数据库规格（增加 CPU 核心数）
    2. 读写分离（读请求分散到从库）
    3. 分库（不同业务使用不同数据库实例）
```

### 5.4 HikariCP 的最佳实践配置

```yaml
spring:
  datasource:
    hikari:
      # ============ 连接池大小 ============
      # 按黄金法则计算（假设 DB 为 8 核 SSD）
      maximum-pool-size: 17
      # HikariCP 推荐 minimumIdle = maximumPoolSize
      # 省去连接的创建/销毁开销
      minimum-idle: 17

      # ============ 超时控制 ============
      # 从连接池获取连接的最大等待时间
      # 超过则抛出 SQLTransientConnectionException
      connection-timeout: 3000  # 3 秒

      # 连接的最大存活时间，到期后连接被关闭并重建
      # 必须比数据库的 wait_timeout 短（通常设为其 2/3）
      max-lifetime: 1800000  # 30 分钟

      # 空闲连接最大存活时间（仅在 minimumIdle < maximumPoolSize 时生效）
      idle-timeout: 600000  # 10 分钟

      # ============ 连接验证 ============
      # 每次从连接池取连接时是否验证可用性
      # HikariCP 默认使用 Connection.isValid()，比 testQuery 更高效
      connection-test-query: null  # 不需要设置，HikariCP 默认机制更好

      # 连接验证超时
      validation-timeout: 1000  # 1 秒

      # ============ 泄漏检测 ============
      # 如果一个连接被借出超过此时间未归还，记录告警日志
      # 设为 0 禁用。建议设为预期最长查询时间的 2 倍
      leak-detection-threshold: 10000  # 10 秒

      # ============ JDBC 参数 ============
      data-source-properties:
        connectTimeout: 3000    # TCP 连接超时
        socketTimeout: 5000     # 读写超时
        useServerPrepStmts: true     # 使用服务端预编译
        cachePrepStmts: true         # 缓存预编译语句
        prepStmtCacheSize: 250       # 预编译语句缓存数量
        prepStmtCacheSqlLimit: 2048  # 预编译语句最大长度
```

### 5.5 连接池配置的检查清单

| 检查项 | 正确 | 错误 |
|--------|------|------|
| pool size 是否根据 DB CPU 计算 | (core × 2) + spindle | 拍脑袋设 100、200 |
| 所有实例 pool 总和是否超出 DB 承载 | 总和 ≤ max_connections × 80% | 不考虑其他应用 |
| connection-timeout 是否设置 | ≤ 3s | 不设置或设很大 |
| max-lifetime 是否小于 DB wait_timeout | max-lifetime < wait_timeout | 大于或等于 |
| leak-detection 是否开启 | 开启并设合理阈值 | 不开 |
| 是否有监控 | 接入连接池 metrics | 无监控 |

## 总结

```
五个呼吸习惯的关系：

  SELECT * ──────────────→ 减少单次查询的数据传输
       │
       ▼
  禁止 N+1 ──────────────→ 减少查询次数
       │
       ▼
  强超时控制 ─────────────→ 限制单次查询的最大代价
       │
       ▼
  Trace 审计 ─────────────→ 让每条 SQL 的代价可见
       │
       ▼
  连接池黄金法则 ──────────→ 在源头控制并发上限


  它们不是孤立的技巧，而是一个完整的防御体系：
  降低单次代价 → 控制总次数 → 限制最大代价 → 让代价可见 → 控制并发上限
```
