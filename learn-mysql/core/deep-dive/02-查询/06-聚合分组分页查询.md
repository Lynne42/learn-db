# 聚合函数
常用聚合函数：
- COUNT()（计数）、
- SUM()（求和）、
- AVG()（均值）、
- MAX()（最大值）、
- MIN()（最小值）、
- GROUP_CONCAT()。

| 函数 | 语义 | NULL 行为 |
|---|---|---|
| `COUNT(*)` | 统计行数 | 包含列值为 NULL 的行 |
| `COUNT(col)` | 统计非 NULL 值数量 | 忽略 NULL |
| `SUM(col)` | 求和 | 忽略 NULL；无有效值时返回 NULL |
| `AVG(col)` | 平均值 | 忽略 NULL，分母是非 NULL 数量 |
| `MIN(col)` / `MAX(col)` | 最小值 / 最大值 | 忽略 NULL |
| GROUP_CONCAT() | 把多行文本数据“压缩拼接成一个字符串” | |

1. `AVG(amount)` 等价于非 NULL 金额的 `SUM(amount) / COUNT(amount)`，不是除以 `COUNT(*)`。

2. GROUP_CONCAT([DISTINCT] 字段名 [ORDER BY 排序字段 ASC/DESC] [SEPARATOR '分隔符'])


```sql
-- 统计商品数量超过 50 个的“商品类型”，及其平均价格
SELECT 
    product_type, 
    COUNT(*) AS total_count, 
    AVG(price) AS avg_price
FROM temp_products_preview
WHERE is_deleted = 0                       -- 1. 先排除已被删除的数据
GROUP BY product_type                      -- 2. 按商品类型分组
HAVING total_count > 50;                   -- 3. 筛选出分组后数量大于 50 的类型
```

## COUNT(*)、COUNT(1)、COUNT(col)

- `COUNT(*)` 明确表示统计行数，是首选。
- `COUNT(1)` 统计常量表达式的非 NULL 次数，优化器通常产生与 `COUNT(*)` 相同的计划。
- `COUNT(col)` 用于统计该列有值的行数，语义不同。

不要以“`COUNT(1)` 一定更快”为依据写代码。现代 MySQL 优化器会针对行计数优化；应先表达正确语义，再用 `EXPLAIN` 和基准验证性能。


# WHERE 与 HAVING 的核心区别

1. `WHERE` 过滤单条订单，发生在分组前，通常能更早减少数据量并利用索引。
2. `HAVING` 过滤聚合后的组，可引用聚合表达式。
3. 能放在 `WHERE` 的明细条件不要无故推迟到 `HAVING`。


# 分组
## WITH ROLLUP (MySQL 8.0 之后使用)
在标准分组聚合的基础上，自动在结果集的末尾为你“赠送”一行或多行高层级的“小计（Subtotal）”与“全计/总计（Grand Total）”。

### 执行规律
WITH ROLLUP 汇总的层级，完全取决于你在 GROUP BY 后面写的字段顺序（从左到右）。

如果你写 GROUP BY A, B, C WITH ROLLUP，数据库在底层会按照从右到左的顺序递归上卷，相当于一次性为你算了 4 个层级的聚合：

- GROUP BY A, B, C（最细明细）

- GROUP BY A, B（忽略 C，计算 A+B 小计）

- GROUP BY A（忽略 B+C，计算 A 小计）

- 全集聚合（忽略所有字段，计算全计）

### 配合 COALESCE 转换NULL为指定名称

```sql
SELECT 
    COALESCE(department, '【全公司总计】') AS department,
    COALESCE(quarter, '【部门小计】') AS quarter,
    SUM(amount) AS total_sales
FROM sales
GROUP BY department, quarter WITH ROLLUP;
```

# 分页
类别：
1. 传统 LIMIT offset, size
2. Keyset Pagination（键集分页 / 寻求分页 Seek Pagination）

通过记录上一页最后一行的唯一排序键（如 id 或 created_at + id），在翻页时利用 B+ 树索引直接定位到目标位置，从而完美避开了传统深度分页（大 OFFSET）导致数据库性能雪崩的致命问题

## 传统 LIMIT offset, size 分页
```sql
SELECT * FROM temp_products_preview ORDER BY id ASC LIMIT 20 OFFSET 1000000;
```

MySQL执行操作
1. 全量读取：InnoDB 必须沿着 B+ 树的叶子节点链表，从头读取并扫描 1,000,020 条数据。

2. 物理回表与抛弃：如果走的二级索引，还要回表 100 万次，然后 把前 1,000,000 条数据白白丢弃，只保留最后 20 条。

3. 结果：随着翻页越来越深（页码越大），耗时呈线性暴增（甚至响应超慢超时），彻底拖垮磁盘 I/O 和 CPU。

## Keyset Pagination 键集分页
Keyset Pagination 的核心思想是：拒绝盲目偏移（OFFSET），改用索引边界值精准 Seek（寻找）。

不再向数据库问：“请帮我跳过前 100 万条数据，拿后面的 20 条”；

而是拿着上一页最后一条数据的唯一标志（如 last_id = 1000000）告诉数据库：“请从 id > 1000000 开始，往后扫描 20 条”。

```sql
SELECT id, preview_title, price 
FROM temp_products_preview 
WHERE id > 100                          -- 👈 依靠 B+ 树索引瞬间精准定位, 这里的id就是前端记录的上一页最后一条数据的id
ORDER BY id ASC 
LIMIT 20;
```


### 联合唯一键（Order Key + Tie-breaker Key）
如果排序是多字段或者非唯一字段，需要建立联合索引

建立联合索引 idx_created_id (created_at, id)

```sql
-- 假设上一页最后一条数据的 created_at 是 '2026-08-03 12:00:00'，id 是 8888
SELECT id, created_at, preview_title
FROM temp_products_preview
WHERE (created_at < '2026-08-03 12:00:00') 
   OR (created_at = '2026-08-03 12:00:00' AND id < 8888)  -- 👈 用 id 消除重复时间的歧义
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

## 两种分页方式对比

维度 | Keyset Pagination（键集分页） | "传统 LIMIT OFFSET, size" | 
| --   |  --  |  --  | 
性能 | "恒定 O(1)（无论翻到第 1 页还是第 10,000 页，耗时都是 1ms）" | 随着页码增加呈线性恶化 O(N) | 
数据一致性 | 高。翻页过程中，即使有人插入/删除了新数据，也不会导致重复读或漏读。 |  低。如果在翻第 2 页时有人插了新数据，原第 1 页的数据会被推到第 2 页，导致重复读取。 | 
跳转能力 | 不支持跳页（不能直接点第 50 页，只能顺着下一页/上一页往下滚）。 | 支持任意跳页（直接输入第 50 页）。 | 
典型应用  |  移动端无限滚动（Feed流/小红书/抖音/微信聊天记录）、大数据导出。 | PC 端后台管理系统的固定页码列表（前提是数据量小）。 |
