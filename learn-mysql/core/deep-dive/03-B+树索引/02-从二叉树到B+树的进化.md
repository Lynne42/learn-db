# 从二叉树到 B+ 树的进化

> **前置阅读**：[InnoDB 页结构基础](01-InnoDB页结构基础.md)——你需要知道"页是 16KB，是磁盘 I/O 的最小单位"。
> **本文目标**：搞清楚为什么数据库不用二叉树、红黑树、B 树，而偏偏选了 B+ 树。

---

## 一、核心矛盾：磁盘 I/O 是性能瓶颈

在展开任何树结构的对比之前，你必须先建立一个认知：

**数据库索引的设计目标不是"减少比较次数"，而是"减少磁盘 I/O 次数"。**

原因很简单——内存中比较一次约 100ns，而从磁盘读一个页约 10ms（HDD）或 100μs（SSD）。差距是 **1000 到 100000 倍**。所以哪怕你在内存中多比较 100 次，也比多读一次磁盘快。

树结构的每个节点存储在一个磁盘页中。**树的高度 = 从根到叶的磁盘 I/O 次数**（最坏情况）。所以一切优化都指向一个方向：**把树压矮**。

---

## 二、二叉搜索树（BST）：最朴素，也最危险

### 原理

每个节点最多两个子节点，左小右大：

```
        8
       / \
      3   10
     / \    \
    1   6    14
       / \   /
      4   7 13
```

查找 key=7：8 → 3 → 6 → 7，比较 4 次。

### 致命问题：退化

如果数据按顺序插入（比如主键自增 1, 2, 3, 4, 5...），BST 退化成链表：

```
1
 \
  2
   \
    3
     \
      4
       \
        5
```

此时查找 key=5 需要 5 次比较 → **O(n)**。100 万条数据最坏需要 100 万次磁盘 I/O。

**结论：BST 完全不可控，直接否决。**

---

## 三、AVL 树 / 红黑树：自平衡，但太高

### 改进

AVL 树和红黑树通过旋转操作保持平衡，避免了退化问题。树高被严格控制在 **O(log₂N)**。

### 问题：对磁盘场景来说，还是太高

100 万条数据：

```
树高 = log₂(1,000,000) ≈ 20
```

**20 层 = 最坏 20 次磁盘 I/O。** 每次 I/O 读一个节点（可能只有几十字节的 key + 两个指针），浪费了 16KB 页的绝大部分空间。

形象理解：你有一个 16KB 的卡车，但每次只搬了一个 20 字节的包裹（一个 key + 两个指针）。卡车的装载率不到 0.2%。

```
AVL/红黑树节点 vs InnoDB 页大小：

┌──────────────────────────── 16 KB 页 ──────────────────────────┐
│ [key|left|right]  空空空空空空空空空空空空空空空空空空空空空空空 │
│  ← ~20 字节 →     ← 剩余 16000+ 字节全浪费 →                  │
└───────────────────────────────────────────────────────────────┘
```

**结论：二叉树每个节点只存 1 个 key，太浪费磁盘页空间，导致树太高。**

---

## 四、B 树（B-Tree）：多路搜索，终于把树压矮了

### 核心思想

既然每次 I/O 都要读一整个 16KB 页，那就**把一个页塞满 key**——不再是"二叉"，而是"多叉"。

一个 B 树节点可以存 **m 个 key** 和 **m+1 个子指针**（m 称为阶/度数）。

```
B 树节点（一个 16KB 页）：

┌───────────────────────────────────────────────┐
│ [key1|data1] [key2|data2] ... [keyM|dataM]    │
│ [ptr0] [ptr1] [ptr2]     ... [ptrM]           │
└───────────────────────────────────────────────┘
  ↓ 每个 ptr 指向一个子节点（另一个页）
```

### B 树的特点

1. **每个节点存多个 key**：充分利用 16KB 页空间
2. **所有叶子节点在同一层**：树是平衡的
3. **非叶子节点也存数据（data）**：key 和 data 在所有层级都可能出现

### 为什么 B 树比二叉树矮？

假设每个 B 树节点能装 1000 个 key：

```
树高 = log₁₀₀₀(1,000,000) ≈ 2
```

**从 20 层直接压到 2 层！** I/O 次数从 20 次降到 2 次。

---

## 五、B+ 树：B 树的终极进化

B+ 树是 B 树的变种，但正是这些"微小"的变化，让它成为数据库索引的最终选择。

### B+ 树 vs B 树的三个关键区别

#### 区别 1：非叶子节点**只存 key 不存 data**

```
B 树的非叶子节点：
┌──────────────────────────────────────────┐
│ [key1|DATA1] [key2|DATA2] [key3|DATA3]   │  ← data 占空间，能装的 key 少
│ [ptr0]  [ptr1]  [ptr2]  [ptr3]           │
└──────────────────────────────────────────┘

B+ 树的非叶子节点：
┌──────────────────────────────────────────────────────────────┐
│ [key1] [key2] [key3] [key4] [key5] ... [key1170]            │  ← 没有 data，能装的 key 多得多
│ [ptr0] [ptr1] [ptr2] [ptr3] [ptr4] ... [ptr1170]            │
└──────────────────────────────────────────────────────────────┘
```

**影响**：同样 16KB 页，B+ 树的非叶子节点能装更多 key → **扇出度（fanout）更大 → 树更矮 → I/O 更少**。

#### 区别 2：**所有数据都在叶子节点**

- B 树：数据可能在根、中间、叶子任何一层被找到 → 查询路径长度不稳定
- B+ 树：无论查什么数据，都必须走到叶子层 → **查询路径恒定 = 性能稳定可预测**

#### 区别 3：叶子节点之间有**双向链表**

```
B 树叶子节点：各自独立，没有横向连接
[叶1]   [叶2]   [叶3]   [叶4]   [叶5]

B+ 树叶子节点：通过双向链表首尾相连
[叶1] ←→ [叶2] ←→ [叶3] ←→ [叶4] ←→ [叶5]
```

**影响**：范围查询（`BETWEEN`, `>`, `<`, `ORDER BY`）时，B+ 树找到起始叶子后可以**顺着链表横向扫描**，不需要回到上层重新导航。B 树则必须反复中序遍历，每一条都要从根开始。

## 六、具体数字对比：100 万条数据

### 假设条件

- 页大小：16 KB = 16384 Bytes
- 主键：BIGINT = 8 Bytes
- 页内指针：6 Bytes
- 每行数据：约 1 KB

### 各种树的高度对比

| 树类型 | 每节点存的 key 数 | 100万行的树高 | 最坏 I/O 次数 |
| --- | --- | --- | --- |
| **BST（退化）** | 1 | 1,000,000 | 1,000,000 |
| **AVL / 红黑树** | 1 | ≈ 20 | 20 |
| **B 树** | ≈ 16（key+data 各占大量空间） | ≈ 5 | 5 |
| **B+ 树** | 非叶子: ≈ 1170，叶子: ≈ 16 | **≈ 3** | **3**（实际 1~2） |

### B+ 树的计算过程

**非叶子节点**每页能装的 key 数量：

```
每个 key+指针 = 8 + 6 = 14 Bytes
每页 key 数 = 16384 / 14 ≈ 1170
```

**叶子节点**每页能装的行数：

```
每行 ≈ 1000 Bytes
每页行数 = 16384 / 1000 ≈ 16
```

**各层能存的总行数**：

```
1 层（只有根页 = 叶子页）：       16 行
2 层（1 根 + 叶子）：             1170 × 16 = 18,720 行
3 层（1 根 + 中间层 + 叶子）：    1170 × 1170 × 16 ≈ 2190 万行
```

100 万行只需要 3 层。而且根页和中间层常驻 Buffer Pool，**实际 I/O 通常只有 1 次**（读叶子页）。

> 详细的数学推导见 → [三层撑起两千万数据的数学证明](05-扇出度和树高的计算.md)

## 七、总结：进化路线图

```
BST                AVL/红黑树           B 树              B+ 树
 │                    │                  │                  │
 │ 问题：退化为链表    │ 问题：太高(20层)  │ 问题：             │ ✅ 数据库最终选择
 │ O(n)              │ 每个节点只存1个key │ ①非叶子存data      │
 │                   │ 浪费16KB页空间    │   → 扇出度不够大   │ 非叶子只存key
 │                   │                  │ ②查询路径不稳定    │ → 扇出度最大化
 │                   │                  │ ③范围查询需要      │ 所有数据在叶子
 │                   │                  │   反复走树        │ → 查询路径恒定
 │                   │                  │                  │ 叶子双向链表
 ▼                   ▼                  ▼                  │ → 范围查询极快
不可用              不适合磁盘          接近但不够优         ▼
                                                        完美适配磁盘I/O
```

**一句话总结**：B+ 树的每一个设计决策——非叶子不存 data、数据全在叶子、叶子双向链表——都是为了在 16KB 页的物理约束下，把树压到最矮、让范围查询最快。
