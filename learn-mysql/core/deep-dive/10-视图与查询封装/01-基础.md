
# 视图是什么

视图就是一条被预先编译并赋予名称的 SQL 查询语句（本质是一个“虚表 Virtual Table”）。视图本身在物理磁盘上默认不保存任何行数据，它的数据是在用户对视图发起查询时，由数据库物理引擎动态从底层基础表（Base Table）中实时拉取并计算生成的。

```sql
CREATE VIEW v_paid_orders AS
SELECT id, user_id, order_no, total_amount
FROM orders
WHERE status = 'PAID';

SELECT user_id, SUM(total_amount)
FROM v_paid_orders
GROUP BY user_id;
```

普通视图不会复制底层数据，也不会因为创建视图而获得新的索引。底层表的数据变化会反映在后续视图查询中。

# 视图的四大核心价值（为什么要用视图？）
## 1. 物理安全防护（列级/行级数据脱敏与隔离）
如果直接将 users 表放开给数据分析师或测试人员，可能会泄露 password、bank_card 等敏感信息。

解法：通过视图只暴露非敏感字段。

```sql
CREATE VIEW v_public_users AS
SELECT id, username, email -- 隐去敏感列
FROM users; 
```

## 2. 简化复杂的 SQL（逻辑封装）
对于包含 5 表联查、大量 CASE WHEN 或聚合计算的复杂查询，如果写在后端代码里，维护成本极高。

解法：将其封装为视图，后端查询时直接 SELECT * FROM v_complex_report，就像查单表一样简单。

## 3. 数据重构与架构解耦（兼容历史代码）
假设原有的 user_profile 表因为架构演进，被拆分成了 user_base 和 user_detail 两张表。

解法：为了不修改上游上百个老系统的代码，可以创建一个叫 user_profile 的视图（内部通过 JOIN 拼合两张新表），上游系统完全无感知。

## 4. 逻辑定制（支持多租户/多维视图）
可以为不同的部门或租户创建定制化的视图，如为市场部创建 v_market_data，为财务部创建 v_finance_data，底层公用一套基础数据。

# 适用场景

- 固定并复用稳定的查询口径。
- 向不同账户暴露经过裁剪的行和列。
- 隔离有限的表结构变化，向调用方提供稳定接口。
- 为报表查询提供清晰名称，降低重复 SQL 的维护成本。

## 不适用场景

- 用视图缓存昂贵查询结果：MySQL 普通视图不是 Materialized View。
- 用多层嵌套视图隐藏复杂业务流程：依赖链会增加排查成本。
- 期待视图自动优化慢 SQL：性能仍取决于展开后的查询、索引和数据量。
- 在高频写入链路中依赖复杂可更新视图：写入规则不直观，失败边界难维护。

## 决策原则

视图适合承担“稳定查询接口”，不适合承担“计算缓存”和“业务服务层”。使用前必须能够回答：展开后的 SQL 是否可解释、权限是否最小化、依赖是否可追踪。


# 操作
## 创建视图

```sql
CREATE OR REPLACE VIEW v_order_summary AS
SELECT
    o.id,
    o.order_no,
    o.user_id,
    SUM(oi.quantity * oi.unit_price) AS item_amount
FROM orders AS o
JOIN order_items AS oi ON oi.order_id = o.id
GROUP BY o.id, o.order_no, o.user_id;
```

视图列名应稳定且无歧义。计算列应显式指定别名，避免调用方依赖自动推导的表达式名称。

## 修改视图

```sql
CREATE OR REPLACE VIEW v_order_summary AS
SELECT
    o.id,
    o.order_no,
    o.user_id,
    o.status,
    SUM(oi.quantity * oi.unit_price) AS item_amount
FROM orders AS o
JOIN order_items AS oi ON oi.order_id = o.id
GROUP BY o.id, o.order_no, o.user_id, o.status;
```

`CREATE OR REPLACE VIEW` 会替换定义，但不会自动验证所有调用方是否兼容。删除、改名或改变列语义前，应先检查依赖。

需要保留已有定义中的部分属性时，也可以使用 `ALTER VIEW`：

```sql
ALTER VIEW v_paid_orders AS
SELECT id, user_id, order_no, total_amount
FROM orders
WHERE status = 'PAID' AND deleted_at IS NULL;
```

## 查看与删除

```sql
SHOW CREATE VIEW v_paid_orders;

DROP VIEW IF EXISTS v_paid_orders;
```

删除视图只删除视图定义，不删除底层表数据。生产变更应将视图定义纳入版本迁移，禁止仅在数据库控制台手工修改。

## 数据更新
可以对视图执行 INSERT、UPDATE、DELETE 等 DML 操作来反向修改底层基础表的数据，但是这种操作 **极其受限！通常绝大部分视图都是“只读”的**

要使一个视图物理上可更新（Updatable View），视图的定义必须满足 1 对 1 的基表映射关系。如果视图定义中包含了以下任何元素，该视图将彻底变为不可更新（Read-Only）：

- 聚合函数：SUM(), AVG(), COUNT(), MAX(), MIN() 等。
- 分组与去重：GROUP BY, HAVING, DISTINCT。
- 集合操作：UNION 或 UNION ALL。
- 子查询：SELECT 列表或 FROM 中包含子查询。
- 多表 JOIN：（只有极少数特定规则下的单表更新允许）。

> WITH CHECK OPTION 约束：
如果视图是可更新的，可以加上 WITH CHECK OPTION。当通过视图更新/插入数据时，数据库会校验该数据必须依然满足视图的 WHERE 条件，否则拒绝修改。
