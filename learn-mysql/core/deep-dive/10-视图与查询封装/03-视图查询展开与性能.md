# 10.03 视图查询展开与性能

## 两种处理方式

MySQL 处理视图时主要采用两类算法：

- `MERGE`：把视图定义合并到外层查询，再统一优化。
- `TEMPTABLE`：先物化视图结果到内部临时表，再执行外层查询。

```sql
CREATE ALGORITHM = MERGE VIEW v_active_users AS
SELECT id, name
FROM users
WHERE status = 1;
```

`ALGORITHM` 是期望，不是性能保证。当定义不满足合并条件时，实际执行方式仍受 MySQL 规则约束。

## 用执行计划验证

```sql
EXPLAIN
SELECT *
FROM v_active_users
WHERE id = 1001;

EXPLAIN ANALYZE
SELECT *
FROM v_order_summary
WHERE user_id = 1001;
```

验证时重点检查：

- 外层过滤条件是否下推到底层表。
- 底层表是否命中预期索引。
- 是否出现全表扫描、临时表或额外排序。
- 实际扫描行数是否明显大于返回行数。

## 性能风险

视图本身不能创建独立索引。要优化视图查询，通常应优化底层表索引或改写视图定义。多层视图会隐藏真实访问路径；每增加一层依赖，都增加定位列来源和执行计划的成本。

高频核心查询应至少保存一条展开后 SQL 的基准执行计划。数据量或版本变化后重新运行 `EXPLAIN ANALYZE`，不能仅凭视图名称判断性能。
