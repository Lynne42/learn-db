# 底层运行机制
```text
            ┌─────────────────────────────────────────┐
            │         用户发起的查询 SQL                │
            │   SELECT * FROM v_active_user_orders;   │
            └────────────────────┬────────────────────┘
                                 │
                                 ▼ 【视图展开与合并 (View Resolution)】
            ┌─────────────────────────────────────────┐
            │    数据库执行器将视图定义替换为真实的表     │
            │   SELECT u.name, o.order_no             │
            │   FROM users u                          │
            │   JOIN orders o ON u.id = o.user_id     │
            │   WHERE u.status = 'ACTIVE';            │
            └────────────────────┬────────────────────┘
                                 │
                                 ▼ 【磁盘物理检索】
            ┌─────────────────────────────────────────┐
            │       InnoDB 存储引擎 (users.ibd)        │
            └─────────────────────────────────────────┘
```

## 1. 磁盘上存了什么？

- 物理表：在磁盘上占据具体的 .ibd 数据页（包含行记录的数据）。

- 视图：在磁盘上只占用微小的元数据文件（存储的是视图的定义 SQL，如 CREATE VIEW ... AS SELECT ...）。

## 2. 处理算法（View Processing Algorithm）：
在 MySQL 中，视图有两种主要的物理处理方式：

- MERGE（视图合并算法，默认）：数据库把用户查询视图的 SQL 和视图定义的 SQL 合并融合成一条大 SQL，然后去查底层表。不产生临时表，性能极佳。

- TEMPTABLE（临时表算法）：数据库先执行视图定义 SQL，将结果提取出来存入一张内存/磁盘临时表，再对临时表执行用户的查询。无法使用底层表的索引，性能较差。
