# 10.06 视图的工程实践与反模式

## 推荐实践

- 使用 `v_` 前缀和稳定的业务名称，例如 `v_monthly_order_summary`。
- 显式列出字段，不使用 `SELECT *`。
- 将创建、替换、授权和删除操作纳入数据库迁移。
- 使用 `SHOW CREATE VIEW` 保存可审计定义。
- 对核心查询执行 `EXPLAIN ANALYZE`，记录扫描行数与耗时基线。
- 修改视图列之前，检查报表、导出任务和应用查询等调用方。

## 典型反模式

### 把视图当缓存

普通视图每次查询仍需访问底层数据。需要预计算结果时，应评估汇总表、定时任务或缓存，而不是期待视图物化数据。

### 多层嵌套

`v_a` 依赖 `v_b`，`v_b` 再依赖 `v_c`，会快速放大排查成本。核心链路应限制依赖深度，并优先保留可直接解释的 SQL。

### 隐藏低效查询

视图名称简洁不代表执行成本低。未索引的关联、聚合和排序仍会消耗 CPU、内存与临时空间。

### 承载业务写入规则

通过复杂可更新视图写数据会把约束分散在数据库对象中。核心业务规则应保留在清晰、可测试的写入入口。

## 上线检查清单

1. 列名、类型和语义是否形成稳定契约。
2. 展开后的 SQL 是否命中预期索引。
3. `DEFINER` 是否存在且权限最小化。
4. 调用账户是否仅获得必要权限。
5. 替换或删除视图时是否已检查依赖。
6. 回滚脚本是否能恢复上一版定义。
