# 建表规则
## 规则一：字段数量的“生死线”（控制表的宽度）

服务端看数据页是纵向的。字段越少，一页存的数据越多，性能就呈指数级提升。

* **常规控制（潜意识上限）**：单表字段数尽量控制在 **20 ~ 30 个** 以内。
* **黄色预警（40 个字段）**：一旦发现字段奔着 40 个去了，后端会立刻警惕，开始反思：*“这里面是不是混入了高频和低频混杂的数据？是否该拆分了？”*
* **终止开关（垂直拆分）**：一旦超过 **50 个字段**，或者表里有 3 个以上大文本/宽字段，优秀后端**一定会强制拆表**。将高频的核心索引字段（如状态、ID、主键、类型）放在主表，将低频的详情、配置项等挪到扩展表（Extension Table）。

## 规则二：数据类型隐形对齐

后端的原则是：**能用小的，绝不用大的；能用数字，绝不用字符串。** 每一字节的节省，在亿级数据面前都是巨大的内存红利。

### 1. 整数家族：别老是用 `INT` 到底

用错类型，索引树会直接胖一圈：

* **状态值/枚举（如：`status`, `type`）**：坚决不用 `INT`（4 字节），更不用字符串。潜意识默认使用 `TINYINT`（1 字节）或者 `TINYINT UNSIGNED`（无符号，0~255）。
* **常规数量/排序（如：`view_count`, `sort_order`）**：使用 `INT`（4 字节）。
* **主键/分布式 ID/金额分（如：`id`, `user_id`, `amount_cents`）**：统一、无条件使用 `BIGINT`（8 字节），防止业务爆发时主键溢出。

### 2. 字符串与文本：255 是一条神奇的物理分界线

前端传描述、标题，后端在定 `VARCHAR(N)` 时，`N` 的选择极有讲究：

* **为什么到处都是 `VARCHAR(255)`？**
因为当 $N \le 255$ 时，InnoDB 在行格式中只需要 **1 个字节** 来记录字符串的实际长度；而一旦 $N > 255$（比如 `VARCHAR(256)`），行内就必须使用 **2 个字节** 来记录长度。所以，255 是潜意识里的“高密度存储压榨线”。
* **常见潜意识对齐**：
* 状态编码/固定简写：`VARCHAR(32)` 或 `VARCHAR(64)`
* 标题/姓名/普通输入框：`VARCHAR(128)` 或 `VARCHAR(255)`
* 长备注/地址/短内容：`VARCHAR(512)` 或 `VARCHAR(1000)`
* 无上限长文本：超过 2000 字符，直接放弃 VARCHAR，申请 `TEXT` 或 `MEDIUMTEXT` 并启动垂直拆表。

#### 字符串在实际项目中的应用
如果产品给出的需求是title最长20个字符
- 在前端， 直接限定 title <= 20
- 在后端， 接入层也会先检验字段长度 title <= 20
- 在数据库层，如何定义title字段类型
在mySQL中， 直接定义 VARCHAR(N)， N代表的是字符数, 因此也是 VARCHAR(20), 不过通常再定义的时候也会故意放大一些限制，防止需求变更， 比如这里写成 VARCHAR(32), VARCHAR(64), 因为
1. 在业务接口层，通常会校验title， 如果字段大于20绝不会进入到数据库层，这个时候一旦需求变更了，只改下业务接口层判断即可，不存在繁杂的数据库操作
2. 对齐 2 的幂次方， 通常定义 16, 32, 64, 128, 255这种的长度， 因为在长度255下，都要分配1字节的空间，那么从20到32多出几个字节的冗余空间作为弹性缓冲空间，性价比极高



### 3. 时间存储：`DATETIME` 与 `TIMESTAMP` 的博弈

* 过去后端喜欢用 `TIMESTAMP`（4 字节，带时区自动转换），但它的致命缺陷是**最多只能支持到 2038 年**。
* **现在的隐形约定**：在 2026 年的今天，新项目大家已经默认全面倒向 `DATETIME`（8 字节，支持到 9999 年）。时区问题一律由后端在全球化架构中通过代码或系统级 UTC 时区来抹平。

时间字段：
- created_at
- updated_at
- started_at
- finished_at
- business_time
- effective_time
- expired_at
- deleted_at

### 4. json类型规则
#### 在关系型数据库中，哪些场景需要存成JSON?
1. 
- 场景
电商平台的商品属性。比如买衣服有“尺码、材质、领型”，买手机有“内存、CPU、屏幕刷新率”。这些属性不同品类完全不同，且不断变动。

- 做法
主表留固定字段（id, spu_no, price），扩展属性直接存 JSON：
```
"specs": { "color": "星空灰", "ram": "16G", "refresh_rate": "120Hz" }
```

2. 多语言/国际化文案
3. 复合配置项
- 场景：用户的偏好设置（通知开关、主题颜色、页面展示习惯），或者后台某个插件的复杂规则配置。
- 为什么：这些配置通常是整体读取、整体修改的，前端直接传一个对象过来，后端原样落库，不需要拆分成十几个单独的数据库列。

#### 设计原则
```
               ┌──────────────────────────────────────┐
               │         拿到一个新的业务字段需求         │
               └────────────────────┬─────────────────┘
                                    │
                         [ 是否需要做 WHERE 过滤? ]
                               /          \
                         (是) /            \ (否)
                             v              v
                  ┌─────────────────┐   [ 结构是否高度动态/非结构化? ]
                  │ 必须作为普通列   │         /             \
                  │ (INT, VARCHAR)  │   (是) /               \ (否)
                  └─────────────────┘       v                 v
                                   ┌─────────────────┐   ┌─────────────────┐
                                   │ 允许定义为 JSON │   │ 拆分成普通列    │
                                   └─────────────────┘   └─────────────────┘


```

总结：
- 查询过滤、关联 Join、聚合统计的用普通列（物理列）；
- 整体存取、动态扩展、接口快照的用 JSON 列。

## 规则三：每张表必须具备的 5 个“空气字段”

一个资深后端在建新表时，哪怕业务只有一个字段，他敲完 `CREATE TABLE` 后，也会本能地、肌肉记忆般地先补齐以下 5 个**元数据管理字段**：

```sql
CREATE TABLE my_table (
    -- 1. 主键：无条件自增、无符号、长整型
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    
    -- 业务字段放中间...
    
    -- 2. 逻辑删除标志：严禁物理删除真实业务数据
    is_deleted TINYINT UNSIGNED NOT NULL DEFAULT 0,
    
    -- 3. 创建时间：数据库自动灌入，精确到秒
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    
    -- 4. 更新时间：数据库层面的物理自动更新，排查 Bug、同步增量数据的神级字段
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    
    -- 5. 乐观锁版本号（高并发表必备）：防止前端并发提交导致高频数据相互覆盖
    version INT UNSIGNED NOT NULL DEFAULT 1
);

```

乐观锁版本号 主要用来做高并发预防的，在以下几种情况下必须存在：
1. 财务与计费模块（Finance）：比如企业充值、扣减授信额度、调整返利比例。一旦发生覆盖，可能会导致账目对不上，直接引发法律或财务审计灾难。

2. 库存与供应链（WMS/SCM）：两个仓管员同时修改某批货物的盘点库存，如果发生相互覆盖，物理世界的货和数字世界的数对不上，整个物流链条直接瘫痪。

3. 审批流节点变更（Workflow）：当一个合同需要一二级主管审批，两个主管同时点击“同意”或“驳回”，如果产生覆盖导致审批状态错乱，属于严重的系统级 Bug。

但是其他普通的ToB项目中， 基本依据 “最后写入覆盖” + 操作流水 的方式，谁最后修改就修改成功，通过操作流水的形式 去追溯操作记录

## 规则四：面向索引与查询的“反向防守”

优秀的后端在设计表的时候，眼睛是看着前端的**产品原型图和交互流向**的。他们会在潜意识里做高并发和弱网环境的压力测试：

1. **“唯快不破”的索引前置**：
只要前端交互上有“根据用户 ID 查列表”、“根据状态筛选”、“根据时间倒序”，后端在建表时就会默默把 `user_id`、`status`、`created_at` 加上索引，或者直接组合成**联合索引**。
2. **严禁 NULL 值（无条件 DEFAULT）**：
除了 `TEXT` 这种大对象，所有的普通字段（INT、VARCHAR）隐形约定里都会加上 `NOT NULL DEFAULT ''` 或 `NOT NULL DEFAULT 0`。
> **为什么？** 因为在 InnoDB 中，允许为 NULL 的字段会导致行格式引入额外的 `NULL值列表` 空间。更严重的是，给包含 NULL 值的列建索引，它的复合索引 B+ 树判空逻辑非常恶心，极易导致索引失效，引发全表扫描。


# 建表原则
## 1. 主表与明细表
当一个业务对象包含“一次任务、多条数据”时，应拆成主表和明细表。

- 主表以任务为基线， 一条任务，一行表数据
- 明细表以数据内容为基线，一条数据内容，一行表数据

适用场景：
- 订单与订单明细。
- 批次与批次数据。
- 文件与文件记录。

## 2. 业务主键与数据库主键分离
id：数据库自增主键，负责关联和数据库稳定性

业务编号负责展示、检索和跨系统识别

## 3. 索引必须跟查询条件对应
设计顺序：
```
先确认查询模式
→ 确认过滤条件和排序
→ 分析数据量与选择性
→ 再设计索引
```
